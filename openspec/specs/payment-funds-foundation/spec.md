# 支付资金底座生产交付规格

## 一、目标

本规格是支付资金底座的稳定交付摘要。它不记录历史计划、过程状态、临时结论或版本演进，只保留当前生产交付需要遵守的能力边界、资金语义和验证门禁。

核心目标：

> 每一笔资金事实都能被解释、被核对、被重建，并能通过测试证明状态、主体、账目、route、posting、ledger entry、余额投影、幂等和失败无副作用成立。

## 二、能力范围

| 顺序 | 能力域 | 规格范围 |
| --- | --- | --- |
| 1 | 账本、账目、余额投影 | 账本交易、账本分录、账本周期、posting plan、借贷平衡、余额桶、余额日志、余额投影、账本余额快照和只读派生边界。 |
| 2 | 钱包账户 | 资金账户、信用账户、平台账户角色、账户能力、资金责任解析、预算控制范围、Spend Rule 决策控制事实、支付工具管理和主体余额查询。 |
| 3 | 交易层 | 直接交易、授权交易、余额控制、让利出资记账交易、外部确认入金、route snapshot、Route Replay、交易投影和幂等摘要。 |
| 4 | 清结算与对账 | 清分明细、清算候选、清算批次、结算单、出款单、对账批次、差错单、追偿、调账核销和人工处理证据。 |
| 5 | 资金数据治理 | 事实留存、归档 Manifest、checkpoint、watermark、余额重建、差异报告、治理读取或导出快照、脱敏、digest 和审计。 |
| 6 | 支付工具、VCC、全球账户和外部轨道 | 只作为业务能力包使用资金底座能力；资金底座承接归一资金事实、账户、账本、清结算、对账和审计，不内置轨道协议、风控模型或合规结论。 |
| 7 | 收单能力 | 保留产品和系统设计边界；默认不进入生产实现范围。 |

## 三、非目标

1. 不恢复历史过程规格、旧工程计划或旧测试断言。
2. 不把通道协议、卡组织规则、ACH/Nacha 规则、银行协议、外部风控或合规结论写成资金底座默认实现。
3. 不把上层业务编排场景下沉为资金底座默认 DSL 场景，例如退款待处理、业务取消、乱序事件、通道预处理和营销规则计算。
4. 不在资金底座内实现报表指标模块的计算、调度、存储和展示。
5. 不在交易、钱包、账本主链路中顺手实现清结算、对账、归档、治理或完整运营后台。
6. 不在资金底座内实现优惠计算、最优券选择、券包生命周期、活动状态查询或权益库存管理。

## 四、统一资金语义

| 概念 | 生产口径 |
| --- | --- |
| 可入账主体 | 资金账户、信用账户，以及平台账户角色解析后的平台资金账户。业务主体、订单、支付工具、外部账户、预算控制范围和 Spend Rule 不能直接成为 ledger subject。 |
| 资金账户 | 承载真实资金余额，参与 route、posting、ledger entry 和余额投影。 |
| 信用账户 | 承载授信额度、已用额度和信用责任，按信用账目规则参与账务事实。 |
| 预算控制范围 | 预算和规则控制 scope，历史字段名可继续保留 `BudgetGroup` 兼容含义；不得生成资金交易、route、posting、ledger entry 或账本余额。 |
| Spend Rule | 授权前控制规则和决策证据；可以记录控制事实和派生控制投影，不表达真实资金转移。 |
| 支付工具 | 卡、VA、外部账户、虚拟卡、外部钱包端点或通道 token 的路由输入和审计快照；不表达内部余额，不作为账本主体。 |
| 资金责任解析 | 将支出主体、支付工具、预算控制范围、Spend Rule 上下文解析为最终资金账户、信用账户或平台资金账户。 |
| `transactionType` | 稳定资金业务类型，例如 `TOPUP`、`TRANSFER`、`PAY`、`FEE`、`REFUND`、`WITHDRAW`、`ADJUSTMENT`；不承载生命周期事件。 |
| `eventType` | 生命周期事件，例如授权、完成、撤销、退款、冻结、解冻、清算确认、结算锁定等。 |
| 授权过期 | 到期、超时或通道未返回是不可信运营状态，不生成资金交易、route、posting、ledger entry 或余额变化。释放占用必须来自可信撤销、余额调整或对账差错补事实。 |
| 无授权直接退款 | 无前置内部授权但存在可追溯外部引用时，通过退款入口承接；必须携带外部引用、原因、操作者和审计，不补造内部授权占用。 |
| 让利出资记账交易 | `FundsBenefitContributionTransactionService` 只记录已决策让利出资结果：谁承担成本、成本落到哪个可记账承接主体、金额是多少。它不计算券、不判断最优优惠、不维护券生命周期、不做分账、不保存营销来源归因。 |
| 外部资金事件 | `ExternalFundsEventApplicationService` 属于交易层应用入口，当前仅支持外部确认入金到资金账户，并委派标准 topup 链路。 |
| 清结算与对账 | 只通过 face/core 消费交易和账本事实；若追加资金事实，必须有来源单据、审批、幂等、原事实引用、操作者、原因、可撤销边界和失败无副作用证据。 |
| 治理能力 | 只读治理、归档、重放、差异报告和生产修复控制面；不得反写交易、账本、钱包事实或余额投影。 |

## 五、模块边界

| 模块 | 生产职责 |
| --- | --- |
| `core` | 资金 DSL、枚举、值对象和端口契约；不依赖 DAL、Web、消息或具体实现。 |
| `ledger-face` / `ledger-impl` | 账本、账本交易、分录、余额投影和账本查询；不反向持有交易生命周期。 |
| `wallet-face` / `wallet-impl` | 钱包账户、支付工具、资金责任、Spend Rule、预算控制和账本事实只读聚合；不创建资金交易事实。 |
| `transaction-face` / `transaction-impl` | 资金交易、授权交易、余额控制、让利出资、外部资金事件、交易路由、交易记录、生命周期和交易投影。 |
| `reconciliation-face` / `reconciliation-impl` | 清结算与对账能力，通过 face/core 消费交易和账本事实。 |
| `governance-face` / `governance-impl` | 数据治理、归档、重放、差异报告和生产修复控制面，通过 face/core 只读或受控编排。 |
| `tests` | 契约测试、服务流程测试、资金红线测试、架构边界测试和 H2 schema。 |

强制依赖方向：

```text
transaction-impl -> transaction-face / wallet-face / core
wallet-impl      -> wallet-face / ledger-face / core
ledger-impl      -> ledger-face / core
reconciliation   -> reconciliation-face / transaction-face / ledger-face / core
governance       -> governance-face / transaction-face / ledger-face / reconciliation-face / core
tests            -> impl / face / core
```

禁止方向：

1. `*-face` 依赖 `*-impl`。
2. 生产模块依赖 `tests`。
3. `wallet-impl` 依赖 `transaction-face` 或创建交易事实。
4. `transaction-impl` 依赖 `wallet-impl`、钱包 DAL、Mapper 或钱包内部实现包。
5. `reconciliation-impl`、`governance-impl` 依赖其他模块实现、DAL、Mapper，或反写交易、账本、钱包事实。

## 六、关键场景规格

| 场景 | 规格要求 |
| --- | --- |
| 直接交易 | 充值、付款、转账、提现、退款、手续费、退费和受控负余额必须通过标准 route、posting、ledger entry 和余额投影形成证据链。 |
| 授权交易 | 授权批准只做占用，授权拒绝无 route/posting/entry，可信撤销释放剩余占用，完成转实际消费，退款沿原完成路径反向。 |
| 余额控制 | 冻结/解冻只表达同主体余额桶控制；资金账户余额调整、信用额度调整和预算控制调整必须区分资金事实和控制事实。 |
| 让利出资 | 一笔出资方一笔交易；退款必须引用原让利出资交易流水；多方出资由上游拆成多次 settle，本服务不做批量分摊。 |
| 支付工具交易 | 支付工具入口位于 application facade，先解析工具、绑定、账户能力、资金责任和规则证据，再委派账户主体型交易内核。 |
| 外部确认入金 | 当前只支持 confirmed credit 到资金账户；外部受理、处理中或未知状态不得提前入账。 |
| 清结算与对账 | 清分、清算、结算、出款、对账差错和追偿分层处理；结算策略必须区分中间户、冻结和账单模式，出款必须区分结算去向和触发方式；对账必须标明交易数据、账务数据、清分清算数据和外部资金数据分段；不得把清分确认、外部受理、对账候选或账单模式展示为最终资金结果。 |
| 归档与重放 | 通过 Manifest、checkpoint、watermark、差异报告和只读快照治理事实；缺快照、范围或权限时阻断或生成差异报告。 |

## 七、测试和验证门禁

有资金变化的实现必须证明：

1. 状态流转正确。
2. route snapshot 可追溯。
3. posting plan 借贷平衡。
4. ledger transaction 和 ledger entry 可回查。
5. 相关主体余额桶变化正确。
6. 同幂等键重复提交不重复入账。
7. 同流水不同摘要冲突失败且无副作用。
8. 拒绝、校验失败、缺快照、错币种、超额、无权限和外部规则未确认时无 route/posting/entry/余额副作用。
9. 涉及持久化时，生产 DDL、H2 schema、Entity、Mapper、唯一键和索引同步闭合。
10. 涉及模块边界时，架构边界测试覆盖允许依赖和禁止依赖。

推荐验证命令：

```bash
just compile
just verify-slice <TestClass>[,<TestClass>] [module]
just test-boundary
just pmd
```

跨模块资金语义、表结构、验证矩阵或发布前收口时执行：

```bash
just verify-cad
```

仅修改文档时，可使用残留扫描和 `git diff --check` 作为文档验证，并在交付说明中写明未运行编译的原因。

## 八、交付说明要求

每次交付必须说明：

1. 修改了哪些模块和文件。
2. 覆盖了哪些设计入口、测试清单或红线场景。
3. 执行了哪些验证命令。
4. 验证是否通过。
5. 未覆盖范围、残余风险和外部确认状态。

不能用“文档齐备”“局部测试通过”“局部实现存在”替代生产可用结论。
