# 支付资金底座系分设计

## 目录定位

本目录是支付资金底座的系统分析设计入口。完整设计包入口见 [../README.md](../README.md)。它承接产品设计和 DSL 设计，把产品目标、资金概念、业务流程、验收红线转成可编码、可测试、可观测、可审计的系统设计。

本目录只描述最终系统设计、职责边界和交付验收口径，不保留过程管理信息、阶段讨论结论或临时任务拆解。

业务接入方需要从使用者视角理解“如何接入、如何验收、如何解释资金结果”时，先读 [../用户接入指南/README.md](../用户接入指南/README.md)。用户接入指南只做接入翻译和准入检查，系统职责和工程边界仍以本目录为准。

## MVP 系分约规

系分设计默认先落最小可用实现切片。一个 MVP 切片必须具备明确服务入口、状态机、事务边界、幂等键、账务断言、查询解释和失败无副作用；不要求一次性补齐完整运营后台、完整批处理平台、完整报表、完整外部协议适配或所有业务能力包。

系统扩展必须服务于当前切片的资金安全和可验证性。若扩展只是为了未来可能的业务变化，先写成不覆盖范围、后续评审条件和回归影响，不在 MVP 中提前设计表结构、公共契约、状态机或模块。

## 系统能力优先级

系分设计承接产品侧能力保障顺序。任何能力落地都必须先保护资金底座不变量，再考虑交易入口和业务专项扩展。

| 顺序 | 能力范围 | 系分落地要求 |
| --- | --- | --- |
| P0 | 钱包、账本、账目、余额投影、对账、清分、清算、结算、大数据归档、账本余额快照。 | 稳定可记账主体、账目 bucket、账本周期、ledger entry、余额投影、对账差错、清分清算对象、结算单、归档 Manifest、checkpoint、watermark、差异报告和账本余额快照。 |
| P1 | 直接交易、授权交易、余额控制、交易投影。 | 在 P0 的账户、账本、账目和运营账务闭环之上承接资金动作入口、幂等、生命周期、route snapshot、冻结/解冻/调整和只读交易视图。 |
| P2 | VCC 发卡业务、全球账户收付款、收单业务支持。 | 通过场景交易 capability pack 适配外部业务事实，不新增平行钱包、平行账本、平行清结算、平行对账或平行归档链路。 |

如果同一能力同时影响多个层级，必须优先证明 P0 能力没有被破坏，再证明 P1 交易入口正确，最后证明 P2 业务语义适配正确。

系统能力优先级不是编码授权清单。P0 能力可以是必须优先保护的系统不变量，也可以是仍处于目标态系分或 TDD 分析状态的能力。每个工程任务只能承接一个可验证的 MVP 闭环，超出首切片的服务契约、状态机、表结构和公共枚举必须进入不覆盖范围或独立任务。

| 成熟度口径 | 系分判断 | 工程动作 |
| --- | --- | --- |
| 系分目标态 | 模块边界、状态机、表职责、事务和观测口径已定义。 | 可以用于评审和估算，不直接写代码。 |
| 编码准入 | 服务入口、写入表、幂等键、事务边界、H2 schema、首批 Red 和停止条件明确。 | 可以申请单一 Execution Grant。 |
| 数据库级完成 | Entity、Mapper、DDL/H2、迁移、服务级测试和回归验证通过。 | 才能声明对应能力已落库验证。 |
| 生产准入 | NFR、容量、告警、Runbook、权限审计、回滚和外部规则确认齐备。 | 才能进入上线或生产启用评审。 |

## 系分交付评估口径

系分设计的目标是证明产品和 DSL 已经能落到可编码、可测试、可观测、可审计的系统边界。完整跨文档门禁见 [../README.md#设计准入评估总控](../README.md#设计准入评估总控)。

| 评估维度 | 系分侧必须证明 | 阻断信号 |
| --- | --- | --- |
| 可用性 | 每个业务能力有服务入口、状态机、失败路径、人工处理入口和只读查询口径。 | 只有流程图，没有接口、状态、表或失败处理落点。 |
| 资金安全 | 事务边界、唯一约束、幂等键、余额桶、账本周期、分录平衡、快照回放和失败无副作用均可落地。 | 失败路径会产生半截 route、posting、entry 或投影；错账只能人工改库。 |
| 金融红线 | 权限、审批、审计、敏感字段、导出、外部协议、规则版本和待确认项有系统承接。 | 高危操作无审批审计；敏感信息进入普通日志、快照、导出或报表。 |
| 易用性 | 用户账单、商户账单、运营时间线、差错处理台、告警和错误原因能解释资金状态。 | 查询视图无法区分授权、冻结、清算、结算、争议、退款和退汇。 |
| 可理解性 | 模块边界、依赖方向、状态和数据对象承接产品/DSL 术语。 | 钱包、交易、路由、账本、清结算、归档或指标职责交叉写入事实。 |
| 可开发性 | Request/Query/DTO、表结构、索引、状态迁移、事务、重试、补偿、观测和生产安全口径明确。 | 实现时还需要临时决定公共契约、核心表结构或跨模块依赖方向。 |
| 可测试性 | 每个服务入口能映射到 TDD 用例、数据准备、断言事实、观测指标和红线失败。 | 只描述实现步骤，无法证明余额、分录、投影、审计和无副作用。 |

## 工程承接清单

研发落地时需要把本清单转成任务边界和验收证据。缺项时，系分视为带条件通过，不得声明生产交付完成。

| 承接项 | 必须明确 | 证据入口 |
| --- | --- | --- |
| 服务契约 | 新增或修改的 face 接口、Request、Query、DTO、枚举和错误码；未触碰公共契约时说明沿用既有契约。 | 对应系分分册服务契约章节、TDD 正反向用例。 |
| MVP 范围 | 本任务的 `mvpScenario`、最小服务入口、最小数据落点、明确不做范围和后续扩展门禁。 | 产品输出项、MVP 任务准入卡、TDD 首批 Red。 |
| 状态机 | 对象状态、合法迁移、失败终态、人工终态、幂等重复处理和并发冲突结果。 | 产品验收矩阵、系分状态机、TDD 正反向用例。 |
| 表和索引 | 表职责、唯一键、幂等键、查询索引、审计字段、摘要字段和不可变字段。 | 系分表设计章节、DDL 影响说明、H2 测试。 |
| H2 schema | 触碰数据库、Mapper、Entity、查询或状态持久化时，同步维护 tests/src/test/resources/jdbc-schema.sql 或说明只读不落库；清结算、归档、重放和治理表未进入 schema 前，不得宣称对应能力已具备数据库级验证。 | DDL 影响说明、H2 测试。 |
| 架构边界测试 | 证明 face 模块不依赖 impl 模块、生产模块不依赖 tests、wallet 不写交易事实、route 不写账本事实、ledger 不持有业务交易生命周期。 | TDD L5、模块依赖检查、边界测试类、just test-boundary。 |
| 事务和补偿 | 同事务内完成什么，外部调用和批量扫描不放入什么事务，失败后如何补偿或重试。 | 系分一致性章节、TDD 幂等和失败无副作用用例。 |
| 观测和审计 | 指标、日志、traceId、审批号、凭证、告警、差异报告和人工处理入口。 | 系分 05、各分册非功能设计、TDD 运营权限和红线用例。 |
| 外部边界 | 通道、银行、卡组织、FX、报表指标、合规、会计、税务未确认部分是否排除在自动资金处理外。 | 产品待确认项、外部规则确认台账。 |

### A0 系分准入复核卡

A0 系分复核只确认产品场景能否落到现有系统边界和测试入口，不写生产代码、测试代码、DDL/H2 schema 或运行时配置。复核结论必须能回答：本轮是继续做 TDD、申请单一 Execution Grant，还是回到产品/DSL/系分补设计。

| 字段 | 系分侧填写口径 | 阻断信号 |
| --- | --- | --- |
| `systemLanding` | 场景落在哪个 face/core/impl 模块、服务入口、领域对象、状态机和只读查询。 | 需要临时新增平行钱包、平行账本、平行清结算、平行对账或平行归档。 |
| `contractChange` | 是否需要新增或修改 face 接口、Request、Query、DTO、枚举、错误码、DSL fixture 或公共值对象。 | 公共契约要改但 Execution Grant 未显式授权。 |
| `dataChange` | 是否需要新增或修改表、索引、唯一键、Entity、Mapper、H2 schema、测试数据或迁移说明。 | 资金事实要落库但没有表/H2/幂等/唯一约束设计。 |
| `transactionBoundary` | 同事务内写入哪些事实，外部调用、批量扫描、投影、归档和出款提交如何隔离。 | 外部调用或批量任务包在资金事实事务内，或失败会半截入账。 |
| `idempotencyAndLock` | 幂等键、重复请求、并发冲突、余额锁定、范围锁和重跑策略。 | 重复请求、重复出款、重复归档或并发释放会改变资金结果。 |
| `observabilityAndAudit` | traceId、业务引用、审批号、凭证、差异报告、操作者、告警和 Runbook 触发。 | 生产失败只能查库定位，或高危操作无法追责。 |
| `redLanding` | 首批 Red 目标测试类、真实执行路径、H2/fixture 需求和验证命令。 | 只能写 Mock 单测，无法证明余额、分录、投影、审计和无副作用。 |
| `stopCondition` | 何时停止并回到产品、DSL、系分、外部规则或用户确认。 | 发现清结算、归档、P2、外部协议、敏感数据越界仍继续编码。 |

## 核心系统结论

1. 写入链路必须从资金事实进入交易或余额控制契约，再经过路由、账务计划、账本过账和投影派生。
2. 钱包账户只管理主体、工具、账本初始化和余额查询，不直接表达资金交易成功。
3. 路由只解析参与方、账户、账目、周期和快照，不写交易事实或账本事实。
4. 账本分录是余额事实源；余额投影、余额变更日志、交易投影和指标都是只读派生。
5. 对账清算模块统一承载对账、清分、清算、结算、出款、差错和追偿，但对账批次、匹配结果、差错单、可清分明细、清分批次、清算候选、清算批次、结算单、出款单和追偿单必须分别建模；对账任务、匹配结果和差错闭环是清分、清算、结算、出款和追偿的基础准入能力。
6. 资金数据治理逻辑能力 governance 只负责资金事实、投影、归档、重放、差异和生产修复证据链治理；归档只改变冷热位置，不改变事实身份；重放只修复读模型或投影，不重新入账；异常人工处理只能审批、补证据、调整范围、重跑或关闭差异；指标项只作为报表指标模块输入边界。
7. 所有资金变化必须能被测试同时证明：状态、金额、账目、账本、投影、幂等、审计和异常路径。

## 术语落地约定

授权交易分册中保留的“授权结算”“部分结算”“已结算金额”等表达，是对产品侧业务语言的承接。进入接口、事件、表字段、测试命名和状态机时，优先使用“授权完成”“部分完成”“已完成金额”和 AUTHORIZATION_TRANSACTION / SETTLE。商户清结算分册中的“结算锁定”和 SETTLEMENT 账目只表示出款前锁定金额，不表示授权完成事件。
