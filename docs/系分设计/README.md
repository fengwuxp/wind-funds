# 支付资金底座系分设计

## 目录定位

本目录是支付资金底座的最终版系统分析设计入口。完整设计包入口见 [../README.md](../README.md)。它承接产品设计和 DSL 设计，把产品目标、资金概念、业务流程、验收红线转成可编码、可测试、可观测、可审计的系统设计。

本目录只描述最终态系统设计。

## 系分准入评估口径

系分设计的准入目标是证明产品和 DSL 已经能落到可编码、可测试、可观测、可审计的系统边界。完整跨文档门禁见 [../README.md#设计准入评估总控](../README.md#设计准入评估总控)。

| 评估维度 | 系分侧必须证明 | 阻断信号 |
| --- | --- | --- |
| 可用性 | 每个业务能力有服务入口、状态机、失败路径、人工处理入口和只读查询口径。 | 只有流程图，没有接口、状态、表或失败处理落点。 |
| 资金安全 | 事务边界、唯一约束、幂等键、余额桶、账本周期、分录平衡、快照回放和失败无副作用均可落地。 | 失败路径会产生半截 route、posting、entry 或投影；错账只能人工改库。 |
| 金融红线 | 权限、审批、审计、敏感字段、导出、外部协议、规则版本和待确认项有系统承接。 | 高危操作无审批审计；敏感信息进入普通日志、快照、导出或报表。 |
| 易用性 | 用户账单、商户账单、运营时间线、差错处理台、告警和错误原因能解释资金状态。 | 查询视图无法区分授权、冻结、清算、结算、争议、退款和退汇。 |
| 可理解性 | 模块边界、依赖方向、状态和数据对象承接产品/DSL 术语。 | 钱包、交易、路由、账本、清结算、归档或指标职责交叉写入事实。 |
| 可开发性 | Request/Query/DTO、表结构、索引、状态迁移、事务、重试、补偿、观测和生产安全口径明确。 | 实现时还需要临时决定公共契约、核心表结构或跨模块依赖方向。 |
| 可测试性 | 每个服务入口能映射到 TDD 用例、数据准备、断言事实、观测指标和红线失败。 | 只描述实现步骤，无法证明余额、分录、投影、审计和无副作用。 |

## 实现承接清单

进入任一编码批次前，研发需要把本清单落到任务说明或 Execution Grant。缺项时，系分视为带条件通过，不得直接开工。

| 承接项 | 必须明确 | 证据入口 |
| --- | --- | --- |
| 服务契约 | 本批次新增或修改的 face 接口、Request、Query、DTO、枚举和错误码；未允许触碰公共契约时只能在 impl 内闭合。 | 对应系分分册服务契约章节、OpenSpec 批次授权。 |
| 状态机 | 对象状态、合法迁移、失败终态、人工终态、幂等重复处理和并发冲突结果。 | 产品验收矩阵、系分状态机、TDD 正反向用例。 |
| 表和索引 | 表职责、唯一键、幂等键、查询索引、审计字段、摘要字段和不可变字段；若本批次涉及 03、04 分册新表，必须声明是否允许同步新增 DDL 和 H2 schema。 | 系分表设计章节、tests/src/test/resources/jdbc-schema.sql、DDL 变更说明。 |
| H2 schema 准入 | 编码批次触碰数据库、Mapper、Entity、查询或状态持久化时，必须同步更新 tests/src/test/resources/jdbc-schema.sql 或说明只读不落库；清结算、归档、重放和治理表未进入 schema 前，不得宣称对应能力已具备数据库级验证。 | DDL 变更说明、H2 测试、Execution Grant 写入范围。 |
| 架构边界测试 | 本批次是否新增或复用 LayerBoundaryTests，以及如何证明 face 模块不依赖 impl 模块、生产模块不依赖 tests、wallet 不写交易事实、route 不写账本事实、ledger 不持有业务交易生命周期。 | TDD L5、模块依赖检查、边界测试类、just test-boundary。 |
| 事务和补偿 | 同事务内完成什么，外部调用和批量扫描不放入什么事务，失败后如何补偿或重试。 | 系分一致性章节、TDD 幂等和失败无副作用用例。 |
| 观测和审计 | 指标、日志、traceId、审批号、凭证、告警、差异报告和人工处理入口。 | 系分 05、各分册非功能设计、TDD 运营权限和红线用例。 |
| 外部边界 | 通道、银行、卡组织、FX、报表指标、合规/会计/税务未确认部分是否排除在本批次外。 | 产品待确认项、docs 总入口批次准入卡。 |

## 系分模板约定

核心业务分册遵循“文档定位、需求背景、目标、概要设计、详细设计、非功能设计、实施切片与准入门禁、参考资料”的结构。05 是横切专项，服务于所有模块的测试、观测、安全和金融红线，不重复承载业务表设计。

表设计落点：

| 分册 | 表设计章节 |
| --- | --- |
| 01 | 数据表分册总览和通用约束。 |
| 02 | 主链路、账户、账本、余额投影、余额日志和交易投影表。 |
| 03 | 对账批次、对账匹配结果、差错单、操作审计；并承载可清分明细、清分批次、清算候选、清算批次、结算单、出款单、追偿表。 |
| 04 | governance 模块表设计：资金归档申请、资金归档 Manifest、重放任务和差异报告；余额检查点和余额水位归属账本模块，04 只描述引用、校验和协作边界；指标只列产品和业务关心的指标项、业务问题和建议事实来源，不设计指标表。 |

## 统一边界

| 层级 | 职责 | 禁止 |
| --- | --- | --- |
| core | 资金 DSL、枚举、值对象、路由、账本端口和共享契约。 | 依赖 DAL、Web、消息、具体实现或测试模块。 |
| wallet-face | 钱包账户、信用账户、预算组、支付工具、主体余额查询契约。 | 暴露 Entity、Mapper 或交易实现细节。 |
| wallet-impl | 钱包账户建模、支付工具绑定、显式账本初始化和余额查询实现。 | 直接写交易事实、账本事实或在交易路径自动建账。 |
| transaction-face | 直接交易、授权交易、余额控制、生命周期和查询契约。 | 暴露 DAL 实现或承载账本落地细节。 |
| transaction-impl | 资金指令转换、路由解析、快照保存、生命周期记录和交易编排。 | 直接修改余额投影或绕过账本写分录。 |
| ledger-face | 账本、账本交易、分录查询和账本写入契约。 | 承载业务订单、清结算单据或交易生命周期状态。 |
| ledger-impl | 账本、账务计划、分录、余额投影和余额变更事件实现。 | 重新路由、处理业务订单或把投影视为事实源。 |
| 对账清算模块 | 对账批次、匹配结果、差错单、可清分明细、清分批次、清算候选、清算批次、结算单、出款单、追偿单和操作审计。 | 直接写账本分录、直接改余额、绕过交易层触发资金变化、替代持牌清算网络或外部机构规则。 |
| governance 逻辑能力 | 归档申请、Manifest、余额重建编排、交易投影重放任务和差异报告的能力边界；物理落点必须保持独立逻辑边界和 face/port 依赖。 | 暴露 Entity、Mapper、冷区实现、调度器细节、指标计算 API、报表查询 API 或导出订阅 API；直接修改交易事实、账本分录、余额投影事实、清结算对象或报表指标结果。 |
| tests | 契约测试、流程测试、架构边界测试和数据一致性测试。 | 被生产模块依赖。 |

## 核心系统结论

1. 写入链路必须从资金事实进入交易或余额控制契约，再经过路由、账务计划、账本过账和投影派生。
2. 钱包账户只管理主体、工具、账本初始化和余额查询，不直接表达资金交易成功。
3. 路由只解析参与方、账户、账目、周期和快照，不写交易事实或账本事实。
4. 账本分录是余额事实源；余额投影、余额变更日志、交易投影和指标都是只读派生。
5. 对账清算模块统一承载对账、清分、清算、结算、出款、差错和追偿，但对账批次、匹配结果、差错单、可清分明细、清分批次、清算候选、清算批次、结算单、出款单和追偿单必须分别建模；对账任务、匹配结果和差错闭环是后续清分、清算、结算、出款和追偿的基础准入能力。
6. 资金数据治理逻辑能力 governance 只负责资金事实、投影、归档、重放、差异和生产修复证据链治理；归档只改变冷热位置，不改变事实身份；重放只修复读模型或投影，不重新入账；指标项只作为报表指标模块输入边界。
7. 所有资金变化必须能被测试同时证明：状态、金额、账目、账本、投影、幂等、审计和异常路径。

## 术语落地约定

授权交易分册中保留的“授权结算”“部分结算”“已结算金额”等表达，是对产品侧业务语言的承接。进入接口、事件、表字段、测试命名和状态机时，优先使用“授权完成”“部分完成”“已完成金额”和 AUTHORIZATION_TRANSACTION / SETTLE。商户清结算分册中的“结算锁定”和 SETTLEMENT 账目只表示出款前锁定金额，不表示授权完成事件。
