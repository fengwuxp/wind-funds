## 文档定位

本文是支付资金底座系统分析设计的总览入口，负责说明整体目标、模块分工、架构分层、数据对象、一致性、测试、观测、安全和生产准入边界。各业务域的详细流程、状态机和表设计见 02、03、04，横切测试观测和金融红线见 05。

## 一、需求背景

支付资金底座需要把钱包账户、账本账目、余额投影、对账、清分、清算、结算、账本余额快照、资金数据治理证据、交易接入、资金路由、交易投影和三类业务补充接入收敛成一套可复用的资金系统。产品设计已经明确：每一笔金额都必须能被解释、被核对、被重建。

系统设计的底层目标同样只有三问：谁的钱、多少钱、怎么变的。模块、接口、表、状态机和测试都必须服务于这三问，不能用业务入口、支付工具、投影、报表或外部状态替代账务事实。

| 三问 | 系分落点 |
| --- | --- |
| 谁的钱 | `wallet` 负责账户、支付工具、资金责任和控制证据解释；`transaction` 只能消费已解析主体；`ledger` 只接受可记账主体。 |
| 多少钱 | 金额、币种、账目 bucket、账本周期、金额组件和累计处理约束进入交易、路由、posting 和余额投影。 |
| 怎么变的 | 交易事实、route snapshot、posting plan、ledger transaction、ledger entry、projection、审计和幂等形成证据链。 |

系统落地优先级按资金底座不变量排序：优先保障钱包、账本、账目、余额投影、对账、清分、清算、结算、账本余额快照和资金数据治理证据；其次保障直接交易、授权交易、余额控制和交易投影；再次保障 VCC、全球账户收付款和收单业务支持。交易层是资金动作入口，但不能反向主导钱包、账本、清结算和资金数据治理的统一模型。

系统分析设计的任务，是把这个产品目标转成研发可以落地的模块边界、接口契约、状态机、数据约束、一致性方案、测试策略和可观测能力。

### 1.1 背景与问题

| 问题 | 不解决的风险 |
| --- | --- |
| 交易、路由、账本、投影和对账清算运营对象容易混用。 | 余额无法解释，退款、争议、调账和对账闭环失真。 |
| 账本周期、清算账期、报表周期、归档水位和 spend-rule window 容易混用。 | 发生跨周期串账、余额查询不一致或规则误拒绝。 |
| 余额日志、交易投影和指标结果容易被误当事实源。 | 运营修复绕过账本，破坏审计和重建能力。 |
| 归档和重放任务缺少水位、检查点、清单和差异报告。 | 生产修复不可回滚，历史余额不可证明。 |
| 为 VCC、全球账户或收单提前定制交易模型。 | 交易层被过度通用或过度业务化，钱包、账本、清结算、对账和归档难以复用。 |

## 二、目标

### 2.1 业务目标

| 目标 | 系分落地要求 |
| --- | --- |
| 资金语义统一 | 交易、钱包、路由、账本、投影和对账清算模块使用同一套主体、账目、周期和事实口径。 |
| 写入链路可信 | 业务资金事实必须经过资金指令、路由快照、账务计划、账本分录和余额投影。 |
| 查询链路可解释 | 钱包余额、用户账单、商户账单、运营时间线和报表都能追溯到事实源。 |
| 异常闭环可审计 | 退款、撤销、冻结、调账、差错、出款失败和追偿必须追加事实，不直接改历史。 |
| 大数据量可治理 | 资金数据治理逻辑能力 governance 负责归档、余额重建编排和交易投影重放，拥有独立水位、检查点引用、清单和差异报告；指标项只作为报表指标模块的可信输入，不承接指标计算和报表实现。 |
| 工程交付可验证 | 每个设计点都有测试类型、断言事实、观测指标和红线用例承接。 |

### 2.1.1 系统能力落地优先级

| 优先级 | 能力域 | 系分落地重点 | 编码准入判断 |
| --- | --- | --- | --- |
| P0 | 钱包、账本、账目、余额投影、对账、清分、清算、结算、账本余额快照和资金数据治理证据。 | 先稳定可记账主体、账目 bucket、账本周期、ledger entry、余额投影、对账差错、清分清算对象、结算单、Manifest、checkpoint、watermark、差异报告和账本余额快照。 | 未证明这些能力的边界和测试前，不进入业务场景 pack 编码；清结算、对账和资金数据治理不得只停留在目标态描述。 |
| P1 | 直接交易、授权交易、余额控制、交易投影。 | 在 P0 事实源和余额桶之上落资金动作入口、幂等、生命周期、route snapshot、冻结/解冻/调整和只读交易视图。 | 交易失败必须无 P0 副作用；授权、冻结和调整不得绕过账本和余额投影。 |
| P2 | VCC、全球账户收付款、收单业务支持。 | 通过场景交易 capability pack 保留业务状态机、外部引用和异常原因，再适配成 P1 资金动作并复用 P0 统一内核。 | 不允许为单一业务新增平行钱包、平行账本、平行清结算或平行资金数据治理链路。 |

P0/P1/P2 是系统依赖和风险优先级，不是一次性编码范围。进入编码前必须把目标态能力拆成单一最小交付切片，并确认服务入口、公共契约、数据变更、事务边界、幂等锁、观测审计、首批 Red 和停止条件。

| 成熟度层级 | 系分证据 | 本阶段结论 |
| --- | --- | --- |
| 目标态系分 | 模块边界、对象、状态机、表职责、NFR 和红线定义完整。 | 01 至 05 可作为设计评审和工程拆解输入。 |
| 工程准入 | 单一最小交付场景、写入范围、H2/DDL 影响、目标测试类和验证命令明确。 | 02 主链路优先做准入复核；03、04 需独立确认首切片和数据落点。 |
| 数据库级完成 | 真实表、Entity、Mapper、H2 schema、迁移和服务级测试齐备。 | 未纳入 schema 的清结算、归档和治理表不得声明数据库级完成。 |
| 生产准入 | 容量、告警、Runbook、权限审计、回滚、外部规则和专业确认齐备。 | 系分通过不等于生产启用。 |

系分主文档只记录目标架构、模块边界、服务契约、数据职责和工程准入标准。局部代码和测试基线只能作为工程计划或交付说明中的证据，不表示含权益 route/posting/replay、清结算、对账、归档、治理重放或 P2 业务生产流已经闭合。

系分准入只确认一个最小交付能否落到现有模块、服务入口、公共契约、H2/DDL 范围、事务边界、幂等锁、观测审计和首批 Red；若命中公共契约、表结构、外部规则、敏感数据、清结算、资金数据治理或 P2 业务专项，必须在独立工程边界中单独列明。

### 2.2 技术目标

1. 固化 core、wallet、transaction、ledger、对账清算模块、资金数据治理逻辑能力和报表指标模块输入之间的边界；指标计算、报表看板、导出订阅和 OLAP 宽表不属于 wind-funds。
2. 固化资金交易、冻结单、账本交易、posting plan、ledger entry、余额投影、交易投影和运营单据的数据边界。
3. 固化幂等、状态机、事务边界、补偿、对账、归档、重放和审计的工程约束。
4. 固化测试驱动设计入口，让产品验收用例可以下钻到接口、表、状态和断言。

### 2.2.1 架构设计目标

| 架构目标 | 系分落点 | 验证方式 |
| --- | --- | --- |
| 可解释 | 资金交易、余额控制事实、route snapshot、posting plan、账本交易、ledger entry 和投影证据链。 | 单笔链路查询、流程测试、账务断言。 |
| 可核对 | 对账清算对象独立建模，差错、审批、调账、核销和重新对账闭环。 | 对账清算 TDD、差错 must-fail、重跑审计。 |
| 可重建 | 余额投影、交易投影、Manifest、checkpoint、watermark 和差异报告边界清楚。 | 归档重放 TDD、投影重放、差异报告校验。 |
| 可演进 | 以 face/core 契约隔离外部调用，以工程任务边界控制公共契约、枚举、状态机和表结构变更。 | 契约测试、架构边界测试、任务边界复核。 |
| 可用性 | 失败无副作用、幂等可重试、补偿可追踪、告警可定位、人工兜底可审计。 | 失败分类、观测指标、Runbook 检查、红线测试。 |

### 2.3 非目标

1. 不在系分文档中展开业务经营策略、合规最终结论、会计制度或外部机构协议。
2. 不把清算网络、支付机构、银行、卡组织或跨境外汇规则写成本系统默认能力。
3. 不描述交付过程管理内容。
4. 不要求运营后台绕过交易层、路由层或账本层直接修正资金结果。
5. 不在本目录修改代码；本文档只定义最终设计和编码约束。

## 三、概要设计

### 3.1 术语与范围

| 术语 | 系分定义 |
| --- | --- |
| 资金指令 | 交易层接收的标准资金事实输入，对应 FundsInstructionSpec 或由交易请求转换而来。 |
| 资金交易 | 直接交易和授权交易的生命周期事实，包含交易聚合、交易明细、请求摘要和 route snapshot。 |
| 冻结单 | 余额控制事实，用于表达同主体 AVAILABLE <-> FROZEN，不等同于资金交易。 |
| 余额调整动作 | 余额控制事实，用于表达同主体资金账户余额调整和信用账户额度调整；支出控制范围和 Spend Rule 的额度、窗口或累计口径调整只更新预算控制视图和审计证据，不生成 ledger entry。对账差错可引用该动作修正同主体余额，但跨主体价值转移必须走资金交易调账事实。 |
| 钱包账户 | 资金账户、信用账户、支出控制范围、平台账户角色、支付工具、资金责任解析关系和主体余额查询的产品与契约层；它是上位能力域，不等同于 `FundingAccount` 单表。 |
| FundingAccount | wind-funds 内部可记账资金账户或平台责任资金账户，承载现金、待清算、待结算、在途、手续费、预收待付等内部资金或责任余额；它不等同于外部银行账户、托管户、备付金户、通道账户或卡组织账户。 |
| CreditAccount / SpendControlScope | 信用账户是可入账的额度控制账户，承载授信额度、可用额度和授权占用；支出控制范围是预算 scope、规则归属、展示和审计对象，不入账。二者都不能被归并为 `FundingAccount`，也不能表达现金沉淀。 |
| 资金路由 | 把资金指令解析成参与方、账户、账目、账本周期和 route leg 的模块。 |
| 账本 | 承载账本、账本交易、记账计划和不可变分录的事实层。 |
| 余额投影 | 由账本分录派生的当前余额或历史余额读模型。 |
| 交易投影 | 由资金事实、账本事实和运营事实派生的用户账单、商户账单、运营时间线、财务核对视图和指标项输入。资金底座不生成正式财务报表、监管报送或会计总账报表。 |
| 账本周期 | periodType + periodId，用于隔离同一可入账主体、同币种、同账目下不同生命周期、账期或额度周期的余额 bucket；预算规则窗口只进入 Spend Rule 控制视图。 |
| 对账清算模块 | 承载对账、清分、清算、结算、出款、差错、调账核销、追偿和操作审计的运营资金闭环。它只能通过交易层或账本层引用资金事实，不直接写分录、不直接改余额，也不替代持牌清算网络或外部机构规则。 |

### 3.1.1 多账本和三流系统边界

系统设计必须把内部账本、外部机构账本和真实资金证据拆开。wind-funds 只能写自己的交易事实、账本事实和运营处理事实；银行、通道、卡组织、ACH、清算网络、托管户或备付金户的账本只能通过引用、文件、回单和对账结果进入系统。

| 边界 | 系统承接对象 | 写入权限 | 校验要求 |
| --- | --- | --- | --- |
| 内部账本 | Ledger、LedgerTransaction、LedgerEntry、LedgerBalanceProjection。 | ledger 模块通过受控过账写入。 | posting plan 平衡、幂等、账本周期、余额投影可重建。 |
| 内部资金事实 | FundsTransaction、FundsTransactionDetail、FrozenOrder、BalanceAdjustAction、RouteSnapshot。 | transaction 和 balance control 受控写入。 | 请求摘要、生命周期、失败无副作用、原路径回放。 |
| 外部机构账本 | 银行账户、托管户、备付金户、PSP 账户、卡组织账户、清算网络账户。 | wind-funds 不写入。 | 只能保存 ExternalAccountRef、脱敏引用、回单、流水、文件和确认状态。 |
| 外部真实资金证据 | 银行流水、通道清算文件、出款回单、入金回单、外部批次、trace/reference。 | 对账清算模块记录证据引用和匹配结果。 | 与内部主体、账目、币种、金额、时间窗口和外部 reference 匹配。 |
| 使用者解释视图 | 余额查询、用户账单、商户账单、运营时间线、财务核对视图。 | 投影模块派生或重放。 | 不反写事实；必须标明状态含义、证据来源和不可操作原因。 |

三流的系统关系如下：

| 流 | 系统入口 | 可推进的对象 | 不得推进的对象 |
| --- | --- | --- | --- |
| 信息流 | 资金指令、业务流水、外部受理、回调、文件引用。 | 交易生命周期、路由、对账任务、人工复核。 | 在缺少账务校验或外部终局证据时直接推进 AVAILABLE、出款成功或生产完成。 |
| 账务流 | route snapshot、posting command、账本交易和分录。 | 余额投影、交易投影、清分准入、归档 Manifest。 | 外部机构账本、外部出款终态或持牌清算结论。 |
| 真实资金流 | 外部流水、回单、清算文件、银行或通道状态。 | 对账匹配、差错单、追偿、调账核销、出款回单状态。 | 直接覆盖历史分录、余额投影或交易事实。 |

### 3.3.3 P2 业务能力包系统承接准入卡

P2 业务能力包不是新的统一资金内核，也不是 transaction 模块的业务产品扩展。它的系统承接目标，是把 VCC、全球账户和收单的外部业务事实归一为资金底座已理解的 P1 资金动作，再复用 P0 钱包、账本、账目、清结算、对账和归档能力。

| 承接项 | VCC 发卡 | 全球账户收付款 | 收单业务 | 系统红线 |
| --- | --- | --- | --- | --- |
| 入口形态 | 授权、clearing、reversal、refund、chargeback 场景 pack。 | 入金匹配、出款提交、外部在途、成功回单、退汇场景 pack。 | payment attempt、capture、refund、dispute、settlement payout 场景 pack。 | 不新增平行交易内核，不让业务 pack 绕过 `transaction-face`、route、ledger 和 reconciliation。 |
| 主体边界 | 卡、token、holder 和 processor account 只做工具或外部引用。 | VA、银行账户、Nostro/Vostro 只做外部账户引用。 | PSP、收单行、卡组织和支付凭证只做外部引用。 | route participant 必须解析为内部资金账户、信用账户或平台账户角色解析后的平台资金账户；支出控制范围和 Spend Rule 只能作为控制上下文、规则快照和查询维度。 |
| 公共契约 | 默认复用授权交易、退款、清结算和对账契约；新增枚举或 DTO 必须专项授权。 | 默认复用直接交易、出款、对账和 FX 引用契约；新增在途或退汇字段必须专项授权。 | 默认复用收款、清分、清算、结算、出款、退款和争议引用契约；新增 capture/dispute 字段必须专项授权。 | 不得把业务外部协议字段全集倒灌到 core 或 face；公共契约只保留稳定资金语义和脱敏引用。 |
| 数据落点 | 只保存资金事实引用、脱敏工具快照、授权/清算/争议引用和审计摘要。 | 只保存外部账户引用、银行流水引用、回单引用、费用和 FX 决策快照。 | 只保存 capture、清结算、出款、refund、chargeback 的资金引用和商户账务摘要。 | 涉及表结构、H2 schema、Mapper/Entity 必须在专项工程任务中明确所有权和测试范围。 |
| 回归守卫 | 授权拒绝无 route/entry，clearing/chargeback 基于原授权或原 route。 | 外部受理不加 AVAILABLE，退汇不走普通退款，错币种无 quote 阻断。 | capture 不可提现，清分不释放可结算，refund/chargeback 防重复损失。 | 必须同时跑 P2 专项测试和受影响 P0/P1 回归；缺回归时只能做 contract-only 或设计验证。 |
| 未覆盖或阻断信号 | 完整 PAN/CVC 进入日志、投影、导出或测试夹具。 | 外部银行账户成为 ledger subject，或外部 accepted 被展示为到账成功。 | 支付成功直接展示可提现，或 chargeback 被普通退款吞掉。 | 任一红线触发时，不得声明业务能力包完成或带条件完成。 |

ACH 或银行转账不新增 `ach-*` 模块、不进入 `core` 成为统一 DSL 枚举全集，也不在 `transaction-impl`、`wallet-impl` 或 `ledger-impl` 中实现 Nacha、ODFI/RDFI、文件批次、Debit 授权、return code、NOC 或 reversal 规则。若业务专项需要使用 ACH 轨道，系统只接收上层业务或适配层已经归一的资金事实、外部引用、核验状态和对账证据，并回挂 `ACH-BOUNDARY-001` 至 `ACH-BOUNDARY-006`、`AC-RAIL-002A` 至 `AC-RAIL-007`、`TDD-RAIL-002` 至 `TDD-RAIL-007`、`TDD-RED-030` 和 `TDD-RED-034`；任何协议解析、敏感银行账户信息、规则解释或主数据更正逻辑必须留在业务系统、通道适配层或专业确认流程。

#### 3.3.3.1 外部适配证据最小契约

P2 业务能力包承接发卡处理商、银行、PSP、卡组织、ACH/银行转账适配层或上层业务系统事件时，必须先形成证据包，再进入资金交易、清结算或对账。证据包不等于原始协议全集；它是资金底座可去重、可验签、可回查、可审计和可对账的最小摘要。

| 证据对象 | 最小字段或摘要 | 资金底座用途 | 系统红线 |
| --- | --- | --- | --- |
| GatewayInstruction | sourceSystem、scenarioPack、businessSn、actionType、amount、currency、idempotencyKey、requestDigest、operatorRef。 | 证明外部动作由哪个业务事实发起，并作为重复请求、回放和审计入口。 | 不保存完整业务订单，不把指令受理当成交易成功。 |
| RouteDecisionSnapshot | providerCode、channelCode、ruleVersion、candidateRouteRefs、selectedRouteRef、excludedReasons、decisionTime。 | 解释为什么走某个外部通道，并支持后续争议、失败重试和对账定位。 | 不允许在缺原 route snapshot 时重新选路兜底。 |
| ChannelRequest | providerCode、externalMerchantRef、requestTime、requestDigest、credentialVersionRef、sensitiveDataPolicy、externalRequestRef。 | 证明实际发给外部机构的请求摘要、凭证版本和敏感数据处理口径。 | 不保存 PAN/CVC、完整银行账号、密钥、证书或原始敏感报文。 |
| ChannelResponse | externalResponseRef、rawStatusCode、mappedStatus、mappedReason、responseTime、retryAdvice、responseDigest。 | 把同步返回翻译成内部可运营状态，并区分成功、失败、处理中、可重试和不可重试。 | raw success/accepted 不能直接映射为 AVAILABLE 或到账成功。 |
| WebhookEvent | externalEventId、eventType、eventTime、receivedAt、signatureVerification、dedupeKey、orderingKey、payloadDigest。 | 承接异步通知，处理重复、乱序、补发和验签失败。 | 验签失败、去重冲突或乱序不可静默推进资金事实。 |
| ChannelReference | authorizationRef、clearingRef、refundRef、chargebackRef、traceRef、fileRef、batchRef、maskedInstrumentRef。 | 作为 route snapshot、对账批次、差错工单和运营查询的外部索引。 | 缺引用、重复引用或引用冲突必须进入差错或隔离。 |
| ExternalQueryResult | queryTime、queryReason、externalStatus、mappedStatus、evidenceRef、operatorRef、queryDigest。 | 处理未知状态、超时和回查，支持等待、放行、阻断或差错。 | 主动回查结果未终局时不得强行展示终局成功。 |
| ExternalFileDigest | fileType、fileDate、fileRef、checksum、lineCount、amountSummary、receivedAt、parserVersion。 | 支撑清算文件、银行流水、卡组织文件、对账文件和批量差错。 | 文件导入成功不等于账实对平；必须进入匹配和差错闭环。 |
| ExternalRuleVerification | ruleSource、ruleVersion、jurisdiction、effectiveDate、verifiedAt、verifiedBy、verificationStatus。 | 证明外部规则、通道能力、合规或资金模式已被专业方确认或标记待确认。 | verificationStatus 不是 confirmed 时，不得声明生产能力完成。 |

实现上可以把这些语义对象折叠到 scenario pack DTO、route snapshot、external evidence、reconciliation source record 或审计表中，但字段语义不得丢失。任何 P2 能力包缺少证据包时，只能做 contract-only 设计验证或隔离导入，不得进入生产资金流。

依赖红线：

2. core 不依赖 DAL、Web、消息、具体业务实现。

5. ledger 不反向持有业务交易生命周期状态。

### 3.5 架构决策记录

本节记录已接受的高层架构决策。若后续工程任务需要改变这些结论，必须列为人工确认点，并同步补充 ADR 或系分变更。

| ADR | 状态 | 决策 | 选择理由 | 复审触发 |
| --- | --- | --- | --- | --- |
| ADR-001 | 已接受 | 保持模块化单体，不拆微服务。 | 当前主要风险是资金语义和模块边界，拆服务会提前引入分布式一致性、部署和运维复杂度。 | 清结算、对账、归档或通道能力出现独立团队、独立数据归属、独立发布和明确故障隔离需求。 |
| ADR-002 | 已接受 | core 作为资金语义内核，只承载 DSL、枚举、值对象和端口契约。 | 保护资金语义稳定，避免核心规则依赖 DAL、Web、MQ 或具体实现。 | core 出现 Mapper、Entity、Spring Bean 实现、外部 SDK 或 tests 依赖。 |

| ADR-004 | 已接受 | 余额控制 adjust 和对账差错调账分层承接。 | 同主体余额、额度、预算控制与跨主体价值转移必须隔离，避免 adjust 被误用成万能调账。 | 需要跨主体补偿、外部差错核销或批次授权调账时。 |
| ADR-005 | 已接受 | 对账清算域独立建模，不混入交易主链路。 | 对账、清分、清算、结算、出款、差错和追偿具有独立状态和审计，混入交易会破坏闭环。 | 进入数据库级落地或外部出款接入。 |
| ADR-006 | 已接受 | governance 是逻辑治理面，物理模块落点由工程任务决定。 | 归档、重放、差异报告属于跨事实治理能力，不为未知未来强行拆分或固化物理形态。 | 进入归档 Manifest、余额快照、交易投影重放或指标边界落地。 |

ADR-006 的落地约束：工程任务必须明确选择复用既有 `governance-face` / `governance-impl`、扩展已有包，还是新增独立物理模块；同时写清依赖方向、是否新增公共契约、表结构和 H2 schema、Mapper/Entity 归属、边界测试范围和指标水位隔离测试。未确认前，governance 只作为逻辑能力边界和设计输入，不得创建空壳模块、跨模块依赖 impl 或宣称归档/余额快照/差异报告数据库级完成。

ADR-007 的落地约束：任何 P2 业务专项进入编码前，工程任务必须声明业务分册验收 ID、场景 pack 范围、允许新增或修改的公共契约、外部引用脱敏字段、DDL/H2 schema 是否涉及、P0/P1 回归范围、外部规则核验状态和未覆盖红线。外部规则核验状态至少包含规则来源、版本或发布日期、生效日期、适用法域或适用范围、核验日期、确认方和确认状态。未确认前，06、07、08 只能作为产品和系分补充，不得替代业务专项工程写入许可。

## 四、详细设计总则

本章是总览级详细设计索引，覆盖接口设计、数据设计、状态机、主流程、异常流程、补偿流程和人工介入的共用规则。对象级字段、表设计、服务类设计和状态流转细节下钻到 02、03、04、05 分册承接。

### 4.1 写入链路

```mermaid
sequenceDiagram
    participant Caller as 业务/运营调用方
    participant Cmd as 交易命令服务
    participant Conv as 指令转换器
    participant Orch as FundsInstructionOrchestrator
    participant Route as RouteResolver
    participant Life as FundsInstructionLifecycleRecorder
    participant Asm as LedgerPostingAssembler
    participant Ledger as LedgerTransactionPostingService
    participant Projection as LedgerBalanceProjectionService

    Caller->>Cmd: 提交交易/授权/余额控制请求
    Cmd->>Conv: 转换为 FundsInstructionSpec
    Conv-->>Cmd: 返回标准资金指令
    Cmd->>Orch: execute(instruction)
    Orch->>Route: resolve(instruction)
    Route-->>Orch: ResolvedRouteSpec
    Orch->>Life: beforePosting(instruction, route, snapshot)
    Life-->>Orch: 生命周期结果或幂等短路
    Orch->>Asm: assemble(instruction, transactionSn, route)
    Asm-->>Orch: LedgerTransactionSpec
    Orch->>Ledger: post(ledgerTransaction)
    Ledger->>Projection: project(entries)
    Orch->>Life: markSucceeded / markFailed
    Orch-->>Cmd: 返回资金交易或冻结单流水
```

写入链路约束：

1. 请求转换器只做入参到资金指令的结构化转换，不访问数据库。
2. RouteResolver 输出 ResolvedRouteSpec，不保存 route snapshot。
3. 生命周期记录器保存交易或冻结事实、请求摘要和 route snapshot，不生成分录。
4. LedgerPostingAssembler 基于 route 生成 LedgerTransactionSpec 和 PostingPlan，不重新路由。
5. LedgerTransactionPostingService 是账本写入口，必须校验独立平衡和幂等入账。
6. 余额投影由 LedgerEntry 派生，投影失败必须有差异报告或补偿策略。

### 4.3.0.1 外部实体账户到内部对象映射

外部实体账户是对账和资金证据来源，不是内部可记账主体。系统落地时必须把外部实体账户、内部资金账户和使用者展示对象分开建模。

| 外部或业务对象 | 系统承接方式 | 可否作为 LedgerEntry 主体 | 典型用途 |
| --- | --- | --- | --- |
| 外部银行账户 | ExternalAccountRef、PaymentInstrumentRef、回单引用、流水引用。 | 否 | 入金识别、提现出款、对账、退款回补。 |
| 托管户 / 备付金户 / 清算户 | ExternalAccountRef、平台账户角色配置引用、对账文件来源。 | 否 | 账实一致、客户资金或商户待结算资金专业确认、外部流水核对。 |

| 归档或重放任务 | Manifest、checkpoint、watermark、交易投影重放任务、差异报告。 | 资金交易、账本分录、余额事实、清结算对象。 | 范围摘要、任务号、操作者、审批、dry-run/apply 模式、差异报告。 |

## 五、一致性设计

### 5.1 本地事务边界

| 边界 | 必须在同一可靠边界内完成 | 不应放入同一事务 |
| --- | --- | --- |
| 交易生命周期写入 | 幂等记录、交易聚合、交易明细、route snapshot。 | 外部系统调用、报表计算、运营通知。 |
| 账本过账 | 账本交易、posting plan、ledger entry、余额投影基础更新。 | 外部出款、第三方回调、长耗时对账。 |
| 清算确认 | 清算批次状态、批次明细、清算确认资金事实或账务动作引用。 | 外部付款提交。 |
| 出款回单 | 出款单状态、外部回单、失败回退资金事实引用。 | 无界重试、人工审批、外部查询或通知回调。 |

### 5.2 幂等与重复处理

| 场景 | 幂等键 | 重复处理策略 |
| --- | --- | --- |
| 直接交易 | tenantId + businessScene + businessSn 和请求摘要 | 相同摘要返回原结果，不同摘要拒绝。 |
| 授权后续事件 | 原授权交易号、事件类型、业务流水 | 不超过剩余授权、剩余可结算或剩余可退金额。 |
| 冻结和解冻 | 冻结业务流水、冻结单号、释放流水 | 超额释放失败，重复释放返回原结果。 |
| 清算批次 | 主体、币种、账期、规则版本、候选明细集合摘要 | 已确认不重复触发清算账务动作。 |
| 出款回单 | 出款单号、外部 reference、回单类型、回单摘要 | 相同摘要幂等；摘要冲突、金额不一致、币种不一致或成功/失败双终态进入差错或人工复核，失败回退只执行一次。 |
| 重放任务 | 重放范围、视图域、模式、原因、发起人 | 同范围重复任务返回已有任务或产生可解释差异。 |
| 归档申请和 Manifest | 归档申请号、Manifest 号、范围摘要和请求摘要 | 申请幂等不代表 Manifest 完成；Manifest 摘要不一致必须失败。 |

### 5.3 失败路径

| 失败阶段 | 处理策略 |
| --- | --- |
| 入参校验失败 | 不生成 route、posting plan、ledger entry，返回明确错误码和失败原因。 |
| 路由失败 | 生命周期记录为失败或拒绝，保留失败原因，不写账本。 |
| 生命周期幂等冲突 | 同业务键不同摘要拒绝，不复用原交易。 |
| 账务计划不平衡 | 拒绝过账，记录失败阶段和问题摘要。 |
| 账本过账失败 | 生命周期标记失败，禁止展示交易成功。 |
| 余额投影事件发布失败 | 不回滚已完成分录和余额投影，进入事件补偿和告警。 |
| 投影重放失败 | 保留任务状态、失败样本、差异报告和续跑位置。 |

### 5.4 统一失败分类

| 失败类型 | 典型场景 | 系统行为 | 验收断言 |
| --- | --- | --- | --- |
| 入参和权限失败 | 参数缺失、错币种、主体越权、无操作权限、无审批或无凭证。 | 拒绝请求，不生成 route、posting plan、ledger entry 或余额控制动作。 | 返回明确原因；无资金副作用；记录必要审计或拒绝日志。 |
| 路由和账务计划失败 | 缺平台账户角色、缺账本周期、账户能力不匹配、posting plan 不平衡。 | 生命周期进入失败或拒绝，不写账本分录。 | 失败原因可查询；不得展示交易成功；重复请求按幂等策略处理。 |
| 余额控制失败 | 可用余额不足、冻结超额释放、余额调整跨主体、错周期、账本未开放负余额能力或缺少本次运行时策略事实。 | 拒绝余额控制动作，不改余额投影和历史分录。 | 余额桶无变化；失败动作或拒绝原因可审计。 |
| 对账清算阻断 | 基础对账未通过、重大差错、候选重复入批、出款回单冲突。 | 阻断后续清分、清算、结算、出款或核销，进入差错或人工复核。 | 阻断原因、责任方、账龄、审批和重新对账路径明确。 |
| 归档和重放失败 | 缺范围、缺 Manifest、checkpoint 不一致、重放差异超阈值。 | 任务失败或暂停，不改变事实身份，不推进水位。 | 保留失败样本、差异报告、续跑位置和审批记录。 |
| 派生和观测失败 | 交易投影、余额日志、报表输入、事件发布或告警失败。 | 不反写事实；进入补偿、重放或告警处理。 | 分录和余额事实不回滚；补偿任务和告警可追踪。 |

### 5.5 架构可用性门禁

| 可用性场景 | 架构策略 | 编码准入要求 |
| --- | --- | --- |
| 入参、权限、路由失败 | fail fast，不产生资金副作用。 | 测试必须证明不生成 route、posting plan、ledger entry、余额控制动作或错误投影。 |
| 账务计划不平衡 | 拒绝过账，保留失败阶段和问题摘要。 | LedgerPosting 入口必须有平衡校验、错误码和失败审计。 |
| 账本成功、派生失败 | 账本事实不回滚，投影、日志、事件进入补偿或告警。 | 必须有补偿任务、告警指标或重放入口，不能让派生失败伪造成交易失败。 |
| 对账差错和清算阻断 | 阻断后续清分、清算、结算、出款或核销，进入差错闭环。 | 必须有差错单、责任方、处理动作、审批、凭证和重新对账路径。 |
| 归档和重放失败 | 不推进水位，不改变事实身份，保留差异和续跑位置。 | 必须有 dry-run/apply 模式、范围摘要、差异报告和人工确认点。 |
| 敏感查询和导出失败 | 拒绝导出或查询，不返回敏感明细。 | 必须校验权限、审批、脱敏、水印、下载审计和过期控制。 |
| 外部依赖或回调失败 | 业务事实与外部结果分离，按幂等键回查、补偿或人工复核。 | 不把外部受理当最终成功；必须保留外部 reference、回单摘要和冲突处理策略。 |

## 六、非功能设计

### 6.1 安全

1. 所有查询、导出、调账、冻结、解冻、出款重试和敏感操作必须校验租户、主体、角色、数据范围和操作权限。
2. 服务间调用必须使用可信身份，不能依赖客户端传入的操作者文本作为权限来源。
3. 资金明细、外部账户、支付工具、卡号、手机号、邮箱、证件、密钥、token 和凭证不得明文输出到日志。
4. 高危操作必须有操作者、审批人、原因、前后值、凭证、来源 IP、traceId 和结果审计。

高危操作进入编码前必须补操作矩阵，不能只写“需要权限”。最小矩阵如下：

| 操作 | 角色和数据范围 | 是否四眼复核 | 必填审计字段 | 禁止动作 |
| --- | --- | --- | --- | --- |
| 出款提交、重试和回单修正 | 财务运营、出款管理员；限定租户、主体、币种和结算单范围。 | 是。 | 操作者、审批人、原因、凭证、外部 reference、traceId、前后状态。 | 把外部受理改成成功、绕过结算锁定或重复出款。 |
| 差错放行、调账、核销 | 对账运营、财务复核；限定差错单和责任主体。 | 是。 | 差错单、责任方、处理动作、审批、凭证、重新对账号。 | 直接修改历史分录、余额投影或外部流水。 |
| 敏感明细查询和导出 | 授权运营、安全或审计角色；限定查询目的、时间窗口和主体范围。 | 按敏感等级决定。 | 查询原因、审批单、脱敏策略、水印、下载人、过期时间。 | 导出明文 PAN、CVV、token secret、证件或银行账户敏感号。 |
| 归档、重放和 apply | 数据治理管理员、财务或技术负责人；限定 Manifest、范围和模式。 | 是。 | 范围摘要、dry-run/apply、checkpoint、差异报告、审批和回滚说明。 | 无范围重放、dry-run 推进水位、缺 Manifest 标记完成。 |
| 条件放行 | 风控、财务、业务负责人按阈值授权。 | 是。 | 放行原因、阈值、到期重查时间、责任人和风险接受记录。 | 金额不平、错主体、错币种或余额公式不成立时放行。 |

### 6.3 性能与容量

1. 写入链路优先保护账本事实一致性，不用异步补账换取表面成功。
2. 查询链路通过余额投影、交易投影、索引、分页和归档索引控制响应时间。
3. 归档和重放必须分批处理，有最大窗口、最大记录数和断点续跑。
4. 大批量导出使用异步任务和审计记录，不在接口同步返回全量敏感明细。

进入生产编码的工程任务必须补齐下列 NFR 参数，未知时不得写“默认”或留空，只能写待确认并说明是否阻断：

| --- | --- |
| 写入吞吐 | 峰值 TPS、平均 TPS、幂等键保留期、重复请求比例假设。 |
| 批处理容量 | 清分、清算、对账、归档、重放的最大窗口、最大记录数、单批超时时间和拆批策略。 |
| 并发和锁 | 锁粒度、状态版本、唯一键、冲突重试次数、失败方无副作用断言。 |
| 外部回调 | 回调乱序、重复、成功失败双终态、金额不一致和超时回查策略。 |
| 数据保留 | 热区保留期、冷区可查范围、审计留存期、敏感导出过期时间。 |
| 回滚和补偿 | 是否可回滚、只能补偿的事实、补偿入口、人工确认和差异报告要求。 |

| P0/P1 | 资金数据治理和账本余额快照 | governance、资金归档申请、资金归档 Manifest、Checkpoint 引用、Watermark 引用、DifferenceReport、治理读取或导出快照、账本余额快照。 | 逻辑边界、核心 API、Request/Query/DTO、范围、审批、水位、差异报告、只读边界、账本余额快照覆盖模式、物理落点、冷热查询和指标不反写测试齐备；工程任务必须明确治理物理落点、依赖方向、公共契约、DDL/H2 schema、Mapper/Entity 归属、边界测试和指标水位隔离后才能编码。 |
| P1 | 直接交易、授权交易、余额控制和交易投影 | 资金交易、授权交易、冻结单、余额调整动作、route snapshot、posting plan、交易投影。 | 服务入口、状态机、幂等键、失败无副作用、原路径回放、余额控制边界、只读交易投影和 P0 回归断言齐备；含权益部分退款还必须证明分摊规则版本、稳定排序、舍入、尾差归属、组件剩余额度、幂等和并发保护。 |
| P2 | VCC、全球账户和收单业务支持 | 业务 PRD 06、07、08，场景交易 capability pack，外部引用、规则版本、脱敏摘要和业务状态映射。 | 必须证明复用 P0/P1 能力，不新增平行钱包、账本、清结算、对账或归档；外部协议、敏感数据和专业规则只保留引用、摘要和待确认项。 |
| 横切 | 测试、观测、安全、金融红线。 | 每个模块都能映射到测试矩阵、指标告警、权限审计和上线前检查清单。 |

进入编码前统一检查：

1. 需求能映射到产品验收 ID、DSL 场景、系分模块和数据表。
2. 每个写入对象有状态机、唯一键、幂等键、非法流转和失败副作用说明。
3. 每个余额变化场景有 route、posting plan、ledger entry、余额投影和账本周期断言。
4. 每个生产高危任务有范围、审批、checkpoint、差异报告、告警和人工兜底。
5. 每个敏感查询和导出有权限、脱敏、水印、审计和过期控制。
6. 每个跨模块实现有架构边界测试或静态检查证据；缺少 LayerBoundaryTests 时，该批次不得宣称模块边界已自动防护。
7. 清结算与对账必须先落 `TDD-B7-RED-001` 至 `TDD-B7-RED-009`；资金数据治理必须先落 `TDD-B8-RED-001` 至 `TDD-B8-RED-005`。Red 未证明错误放行前，不得进入对应 Green 实现。
8. 采用任务化工程推进时，工程任务必须先完成计划评审，确认任务标识、owner、写入范围、只读范围、AC/TDD 映射、验证命令、停止条件、评审 owner、状态记录位置和恢复方式；缺任一项时，只能继续设计、TDD 分析或 contract-only。

### 7.1 编码前裁决口径

进入编码前，系分评审必须把目标态设计裁决成一种可执行结论。未裁决清楚时，不得以“设计已通过”为理由开始改公共契约、表结构或生产流程。

| 裁决结论 | 含义 | 允许动作 | 禁止动作 |
| --- | --- | --- | --- |
| 继续产品或系分澄清 | 场景、对象、资金事实、外部规则或验收 ID 不完整。 | 补 PRD、DSL、系分或验收矩阵。 | 写代码、DDL/H2、运行时配置或生产任务。 |
| TDD 分析 | 产品和系分边界清楚，但 Red、夹具、H2/DDL 范围或验证命令未确定。 | 输出测试矩阵、目标测试类、失败断言和数据准备方案。 | 写 Green 实现或扩大公共契约。 |
| contract-only | 只允许补契约、枚举、DTO、DSL fixture 或只读验证，不触碰资金写入。 | 做契约草案、JSON 契约、只读查询或 dry-run 验证。 | 写交易事实、账本事实、清结算事实或归档 apply。 |
| 单一最小交付编码 | 证据包明确写入范围、禁止范围、Red、H2/DDL、验证命令和停止条件。 | 按独立工程边界实现一个最小闭环。 | 顺手扩展清结算深水区、资金数据治理、P2 业务或外部协议。 |
| 生产准入评审 | 代码和测试已完成，需要评估上线启用。 | 核验 NFR、容量、告警、Runbook、权限审计、外部规则和回滚。 | 用设计文档替代生产证据。 |

```mermaid
flowchart LR
    PRD["产品验收用例"] --> Contract["契约测试\nRequest / DTO / Spec / JSON"]
    PRD --> Flow["流程测试\n交易 / 授权 / 冻结 / 清结算"]
    PRD --> Ledger["账务测试\nPostingPlan / LedgerEntry / Projection"]
    PRD --> Boundary["架构边界测试\n依赖方向 / Entity 不外露"]

```

| 测试类型 | 保护对象 |
| --- | --- |

| 契约测试 | face 接口、Request、Query、DTO、Spec、DSL JSON 样例。 |

| 投影测试 | 余额投影、余额变更事件、交易投影、重放和差异报告。 |

## 九、设计红线

1. 不得绕过交易层、路由层和账本层直接修改余额。
2. 不得在授权拒绝、路由失败、余额不足或账本失败时生成 ledger entry。
3. 不得把支付工具、外部账户、业务订单、报表或运营备注作为内部账本主体。
4. 不得把清算账期、结算周期、报表周期、归档水位或 spend-rule window 当作账本周期。
5. 不得用余额日志、交易投影或指标结果修复余额事实。
6. 不得直接修改历史分录；错账只能追加补记、冲正、调账和核销事实。
7. 不得在缺检查点、缺资金归档 Manifest、缺差异报告或无范围的情况下执行生产重放或归档。
