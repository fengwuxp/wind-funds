# 支付资金底座产品设计

## 目录定位

本目录定义 `wind-funds` 的产品目标、核心名相、能力边界、业务场景、规则和验收摘要。它回答“为什么做、给谁用、稳定提供什么能力、什么不属于资金底座”，不定义 Java 接口、表字段、实现状态或验证命令。

正式产品文档只保留当前有效结论。讨论过程、角色争论、历史方案、工程任务状态和测试执行结果不进入正文；工程事实分别回到系分、TDD、源码和 Git 历史。

## 行业校准

| 公开实践 | 可复用结论 | 本项目取舍 |
| --- | --- | --- |
| [Highnote 虚拟卡](https://docs.highnote.com/docs/issuing/cards/issue/issue-virtual-cards) 先创建承载资金的 financial account，再为其发卡。 | 支付工具与资金主体分层。 | `PaymentInstrument` 不持有余额；VCC 绑定到 `FundingAccount` 或 `CreditAccount` 子账户。 |
| [Highnote Spend Rules](https://docs.highnote.com/docs/issuing/spend-controls/spend-rules) 作用于授权金额，撤销影响累计授权金额，退款不影响；周期次数要与 velocity control 组合。 | 支出控制与资金退款是两个层次。 | 退款默认只改资金事实；只有上层策略明确要恢复控制额度时才写 `REFUND_COMPENSATED`。 |
| [Stripe Issuing 授权](https://docs.stripe.com/issuing/purchases/authorizations) 区分批准占用、capture 和 reversal；[Issuing 交易](https://docs.stripe.com/issuing/purchases/transactions) 还包含无原授权退款、强制完成和多次 capture。 | 授权不是最终资金事实，完成和逆向必须保留原事实引用。 | 保留 approve/complete/reversal/refund 分层、原路回放和业务确认的 no-auth 入口；超时本身不作为可信释放事实。 |
| [Modern Treasury Ledger Objects](https://docs.moderntreasury.com/ledgers/docs/guide-to-ledger-objects) 以 ledger transaction 组织平衡 entries；[Ledger Guarantees](https://docs.moderntreasury.com/ledgers/docs/ledgers-guarantees) 强调平衡、不可变、幂等和原子写。 | 原子账务事件与分录明细各有职责。 | 保留 `LedgerTransaction` 作为账务事件聚合，`LedgerEntry` 作为不可变分录，投影和对账不反写原事实。 |

行业产品可能对过期授权自动释放占用，但 `wind-funds` 已确认超时为不可信中间状态，必须等待上层提供可信撤销或完成事实。这是有意的资金安全差异，不随厂商状态机自动变更。

## 产品定性

`wind-funds` 是支付资金底座，不是发卡、订单、优惠券、收单、银行通道或全球账户业务系统。它稳定提供以下能力：

1. 接收上层已经确认的资金事实。
2. 把资金事实解析为明确的内部主体、金额、币种和资金路径。
3. 形成可平衡、可追溯、可重放的账本事实。
4. 派生余额和交易解释视图。
5. 为清结算、对账和治理提供事实证据。

所有场景先回答三问：谁的钱、多少钱、怎么变的。不能回答这三问的输入不得进入资金写链路。

## 核心边界

| 对象 | 产品职责 | 明确不是什么 |
| --- | --- | --- |
| `FundingAccount` | 承载真实资金余额或平台资金责任。 | 信用额度、预算 scope、支付工具或外部银行账户。 |
| `CreditAccount` | 承载授信额度、可用额度、授权占用和已用额度。 | 现金账户或父资金账户的镜像。 |
| `SpendControlScope` / Spend Rule | 表达预算归属、支出规则、控制窗口和控制证据。 | 资金池、账本主体或现金余额。 |
| `PaymentInstrument` | 表达卡、VA、外部钱包端点或通道 token 等支付入口。 | 内部资金账户或 LedgerEntry 主体。 |
| `PaymentInstrumentBinding` | 表达支付工具与 `FundingAccount` 或 `CreditAccount` 的当前绑定及历史变更证据。 | 控制范围、Spend Rule、账户父子层级或资金责任本身。 |
| `AccountHierarchyRelation` | 表达资金账户或信用账户到直接父账户的不可换绑结构关系。 | 自动出资规则、余额汇总规则或多级树解析服务。 |
| `SpendSubjectFundingRelation` | 表达某资金账户或信用账户在指定币种和关系类型下唯一的出资或结算责任目标。 | 账户层级、支付工具绑定、Spend Rule 或扣款事实。 |
| `RouteSnapshot` | 固化本次交易实际采用的主体、工具、关系和路径证据。 | 当前配置的动态视图。 |
| `LedgerTransaction` / `LedgerEntry` | 记录原子账务交易与不可变分录事实。 | 业务订单状态或外部通道状态。 |
| 投影视图 | 为余额、账单、运营、对账和审计提供只读解释。 | 资金事实源或改账入口。 |

三种关系不得混用：支付工具绑定回答“这个工具关联谁”；账户层级回答“这个账户的直接父账户是谁”；资金责任回答“这次支出最终由哪个内部主体承担”。账户层级本身不触发出资、扣款或余额变化。

## 场景准入

| 场景 | wind-funds 承接 | 上层业务承接 |
| --- | --- | --- |

| VCC | 支付工具快照、资金/信用子账户、直接父账户快照、授权资金事实和原路回放。 | 发卡、卡生命周期、issuer 事件、卡主状态和完整卡账单。 |
| 全球收付款 | 归一后的入金/出金事实、外部引用、FX 应用事实、退汇和对账。 | 银行协议、受理状态、合规决策和通道编排。 |
| 收单 | 已确认支付资金事实、商户资金账户、清结算、退款、拒付资金结果和对账。 | 支付尝试、通道路由、商户协议和卡组织案件。 |
| Spend Controls | 规则版本、挂载、决策证据、控制流水和只读投影。 | 产品策略、实时授权业务决策和外部规则适用性。 |

## 产品验收摘要

进入系分和 TDD 前，关键场景至少满足：

1. 正向、逆向、异常和人工处理路径有明确业务结果。
2. 资金主体、责任主体、控制主体和支付工具没有混用。
3. 退款、撤销、清算、对账和重放使用原事实与原快照，不按当前配置重算。
4. 授权超时或外部状态不明不自动形成可信资金终态。
5. 失败路径不产生半截 route、posting、LedgerEntry 或余额变化。
6. 外部规则未确认时明确阻断、降级或人工处理，不写成生产可用。
