## 阅读摘要

当前结论：`wind-funds` 是可嵌入宿主的资金领域公共能力库。它接收宿主已经确认的业务意图和外部资金事实，形成可幂等、可追溯的内部资金事实与查询证据。资金影响只能通过关联的新事实冲正或补正，已记录的交易、账本分录和对账结果不可原地改写。

产品视图：公共能力层负责解释“谁的钱、多少钱、因何变化、形成了什么内部事实、用什么证据核对”；宿主继续拥有订单、优惠券、VCC、支付通道和外部网络等产品生命周期，以及营销、履约、风控、合规和协议裁决。

公共语言约定：领域生命周期当前值统一称为 `state`；运行、准入和决策结论使用 `outcome`、`result` 或具体业务名。外部协议、展示和发布状态必须带来源或用途限定词，不能用无修饰 `status` 形成第二套生命周期语言。

主链路：宿主确认业务语义或外部事实 -> 公共能力层校验资金前提 -> 形成或拒绝资金影响 -> 保存内部资金事实和关联证据 -> 提供查询、清结算和对账所需证据。逆向和纠错必须引用原事实并追加新事实。

核心边界：本文不是 Java API、数据库或模块实现设计。`Q-002` 已确认资金责任方、交易角色、内部可记账账户、账目/余额维度、支付工具和四类事实引用必须分层；只有产生内部资金/账务影响的输入才必须经受控解析落到内部可记账账户，并冻结规则版本、账户关系和原 route。“内部可记账账户”仍是产品上位名，不批准最终 Java 类型、Funding/Credit 分类、账目拆轴或 posting matrix，也不把 Credit 解释为现金。

目标读者：业务与产品 Owner、资金域研发和测试、宿主接入团队、财务/运营/对账确认方。本文支持他们判断公共能力层应该拥有什么、不应该拥有什么，以及后续 DSL 和系统设计可从哪些产品事实出发。

## 1. 背景与问题

本章说明为什么需要重新定义公共能力层，以及哪些材料只能证明现状、不能决定目标态。

### 1.1 现状事实

- `wind-funds` 当前同时存在 `core`、`ledger`、`wallet`、`transaction`、`reconciliation` 等能力，以及大量 public 类型；这些源码只能证明当前实现形状，不能自动证明目标产品语义正确。
- `capte-domain` 有钱包授权/完成/撤销/退款和 Benefit 出资的真实源码调用；当前已有 Provider 制品与 Capte 集中测试宿主的 real Bean、联合 H2、事务和恢复证据。该仓是通用领域模块，无独立生产数据库和部署进程；Provider impl 仅在 `tests` 以 test scope 装配是预期边界，真实 Consumer 的 composition root、数据库和部署证据不属于本仓当前交付。
- Benefit Consumer 已出现请求字段和本地 Snapshot API 漂移，并且退款依赖重新查询和当前配置，说明“公共契约必须保留哪些原事实”不能只由现有接口数量决定。
- `fincone` 当前是 docs-first 设计仓，没有运行时代码；VCC、全球账户和收单材料只能提供场景与边界候选，不能证明已经接入。
- 旧产品、DSL、系分、TDD 和历史 OpenSpec 中存在可复用问题与案例，但本次重设计不把它们当作目标态权威。

### 1.2 真实问题

公共资金能力层当前缺少一份从产品责任出发、经过跨项目真实场景验证的统一定义。结果是当前类型、历史设计和场景需求容易反向决定公共边界：调用方难以判断应提交什么资金事实，Provider 难以判断哪些概念必须稳定，测试也容易把单仓行为误当成跨仓可用性。

如果不先统一产品定位和责任边界，后续会出现三类代价：为每个场景增加专用内核；把宿主业务对象塞入 `core`；或用宽扩展字段隐藏收付款主体、原交易、账目和证据等关键事实。三种做法都会降低可理解性、可追溯性和接入稳定性。

### 1.3 证据与可信度

当前产品定位由人类 Owner 在 `Q-001` 中确认。当前源码、测试与 Consumer 调用属于现状证据；`fincone` 文档和旧设计属于设计证据；尚未取得的跨仓 real Bean、联合 schema、事务和运行结果保持待验证。本文不把设计确认外推为实现、启用、发布或生产完成。

## 2. 目标与非目标

本章限定本产品要改变的结果、明确不承担的责任和停止下沉的条件。

### 2.1 产品目标

1. 为不同宿主提供同一套容易理解的资金公共语言和能力边界，避免按订单、Benefit、VCC、ACH 或收单分别建设资金内核。
2. 让每次资金影响都能解释主体、金额、业务原因、原事实、内部账务结果和核对证据。
3. 让公共能力对调用方简单，但不隐藏资金责任、幂等冲突、完成层级、失败副作用和逆向约束。
4. 让产品定义能够逐层交给 DSL、系分和 TDD，而不在产品文档中提前固化 Java 类、表结构或实现算法。

### 2.2 成功标准

- 订单钱包支付、Benefit 出资、VCC 授权、全球账户 confirmed credit、收单清结算和三方对账能用同一组产品名相说明，不需要复制场景专用资金内核。
- 任一候选公共能力都能说明服务对象、拥有的事实、输入前提、业务结果、失败和恢复边界。
- 订单、券、卡、支付工具、外部账户和协议状态不会因接入资金域而成为另一份产品生命周期事实源。
- 现有 public 类型可以依据产品职责和真实消费者审查，而不是依据历史稳定标签默认保留。
- 后续 DSL 可以只从已确认产品事实提炼稳定概念，不依赖宽 `Map<String, Object>` 承载关键资金事实。

### 2.3 非目标

- 不建设订单、优惠券、VCC、收单、ACH、全球账户或支付通道产品。
- 不替宿主决定营销、履约、风控、合规、税务、会计或外部协议语义。
- 不直接修改银行、通道、卡组织或清算网络的外部账本。
- 不在本文确定 Java API、DTO、枚举、数据库、事务、中间件或部署方式。
- 不因为当前没有消费者而预建佣金、提现、对账或其他场景专用框架。
- 不用 Recording/Fake、旧 Snapshot 或 Provider 单仓测试宣称 Consumer 已可用。

### 2.4 停止或拆期信号

主体、资金归属、原事实、完成层级或责任 Owner 不清时，停止向 DSL 下沉。Consumer 缺口若仍可能来自版本、映射、Bean、schema 或事务装配，则先形成宿主最小验证，不扩公共接口。涉及外部规则、法域、会计或监管结论时，交给对应专业 Owner 确认。

## 3. 定性与范围

本章回答这是什么产品、服务谁、与宿主如何分责，以及哪些名相仍待确认。

### 3.1 产品定性

这是一个嵌入式资金领域公共能力产品，不是面向终端用户的独立业务产品，也不是场景工作流平台、外部支付网络镜像或通用数据访问层。

其直接使用者是宿主业务系统和资金域内部协作能力；间接使用者包括需要查询资金结果、账单、清结算和对账证据的业务、运营、财务和测试角色。最终资金归属、法律责任和会计口径仍由相应业务、财务、法务与合规 Owner 确认。

### 3.2 能力提供者视角

公共能力层稳定提供四类产品结果：

1. 对宿主已确认的资金意图或外部资金事实作资金侧准入，明确接受、拒绝、待证据或冲突。
2. 形成账户、资金交易、路由、账本和余额等内部资金事实，或证明本次没有资金影响。
3. 为清分、清算、结算、对账、查询和审计提供可关联的事实与证据。
4. 通过引用原事实的新交易、新分录或新对账运行表达逆向和纠错，不修改历史事实。

本文不把这四类结果直接映射成四个模块或一组 API；模块归属和接口形状由 DSL 与系分阶段决定。

### 3.3 上下游责任边界

| 责任面 | 宿主或外部 Owner | 支付资金公共能力层 |
| --- | --- | --- |
| 业务意图 | 证明订单、Benefit、VCC、收单或其他业务为何需要资金动作，以及参与主体和业务规则 | 校验资金侧必要前提，不重做宿主业务决策 |
| 外部事实 | 适配并解释银行、通道、卡组织或外部网络的身份、认证、版本和业务语义 | 接收已经过边界校验的外部资金事实或证据引用，不拥有外部协议生命周期 |
| 内部资金事实 | 不直接改余额、拼分录或伪造结果 | 拥有资金交易、内部账务事实、余额结果及其可追溯关系 |
| 逆向和纠错 | 提供合法业务原因、原事实引用和授权 | 校验累计与责任边界，通过关联的新事实表达资金影响 |
| 清结算与对账 | 提供业务事实、外部证据、规则 Owner 和人工处置责任 | 形成内部候选、结果、差异、Gate 和资金动作证据；不覆盖历史事实 |
| 展示与履约 | 决定用户页面、订单履约、券状态、卡状态和运营动作 | 提供稳定查询证据，不反向拥有宿主展示或履约状态 |

### 3.4 稳定点与变化轴

跨场景稳定点是金额与币种、资金责任、业务原因、原事实、幂等与冲突、不可变事实、追加式逆向、内部账务平衡和外部证据关联。

变化轴包括业务单据类型、支付工具、外部轨道、通道状态、法域、规则版本、完成层级、结算周期和人工处置方式。变化轴必须留在宿主、适配或有明确 Owner 的规则边界，不因多个场景都出现就自动进入 `core`。

### 3.5 核心名相

| 名相 | 当前产品定义 | 不是什么 | 状态 |
| --- | --- | --- | --- |
| 宿主业务意图 | 宿主已经完成业务准入并希望产生或控制资金影响的业务事实 | 原始页面请求、未验证回调、完整订单或券生命周期 | 已确认 |
| 外部资金事实 | 已由责任边界解释和验证、可用于资金处理或核对的外部结果 | 单纯 `accepted/processing` 文案或未经验证的事件 | 已确认 |
| 内部资金事实 | 公共能力层记录的账户、交易、账务、余额、清结算或对账事实及其关联 | 宿主业务终态、外部到账承诺或可原地修改的记录 | 已确认 |

### 3.6 明确不采用的方向

- 不采用“一套万能资金指令 + 任意扩展字段”承载所有产品语义；关键事实必须有明确名相和责任。
- 不采用按订单、Benefit、VCC、全球账户或收单分别建设资金内核；场景差异由宿主和有证据的边界承担。
- 不采用让 Consumer 直接组装 posting 或修改余额的接入方式。
- 不因现有 API 已标记 stable 就保留旧契约或跳过产品职责审查。

## 4. 概要设计

本章给出不依赖模块和接口形状的产品主链路与能力布局。

### 4.1 方案概述

产品围绕“已确认输入 -> 内部资金事实 -> 查询与核对证据”建立公共能力。宿主先完成业务语义和外部协议解释；公共能力层只在资金事实充分时产生资金影响，并保留业务、原交易、路由、账务和外部证据之间的关联。

### 4.2 核心能力布局

| 能力组 | 对外提供的产品结果 | 当前边界 |
| --- | --- | --- |

### 4.3 产品主链路

1. 宿主识别真实业务场景，确认业务单据、参与责任、金额币种、业务幂等身份和所需资金结果。
2. 对外部轨道场景，宿主或适配边界先完成认证、版本和状态解释，只提交可识别的外部资金事实或证据。
3. 公共能力层校验资金主体、账户、金额、原事实、幂等和完成层级；材料不足时拒绝、挂起或进入人工/差错路径。
4. 需要资金影响时形成资金交易、内部账务和余额结果；不需要资金影响时保留可解释的拒绝、只读或证据结果。
5. 查询、清结算和对账沿同一事实链工作。退款、return、reversal、冲正和补正引用原事实追加记录。

### 5.3 产品接口抽象

这里的接口是产品能力，不是 Java 方法：

- 提交资金意图：宿主提供已确认业务原因、责任、金额、幂等身份和期望资金结果；公共能力返回接受、拒绝、冲突、待证据或已重放结果。
- 提交外部资金事实：适配边界提供已验证的外部事实和稳定引用；公共能力返回资金影响、只读证据、差异或停止结果。
- 发起逆向或纠错：调用方提供原事实、合法原因和授权；公共能力返回新的关联事实或明确拒绝，不修改原记录。
- 查询资金证据：调用方按稳定业务或资金引用查询内部事实链；公共能力返回可解释证据，不替调用方推导订单履约或外部到账。

### 5.4 场景合同共同读法

- 每个场景分别列出业务、外部、资金交易、账本、余额及场景特有事实 Owner；箭头只表达该场景的局部证据偏序，不代表全局状态机或跨 Owner 原子事务。
- “资金效果”只描述产品语义，不批准 `LedgerSubjectCode`、posting matrix、Java 类型或 API。需要资金影响时才解析内部可记账账户；拒绝、NOC 和只读证据保持零资金影响。
- `UNKNOWN` 沿原 Intent/原业务与资金身份和权威查询恢复；逆向引用原事实追加新 Intent/事实。只有满足 `Q-004` 的权威终结、资金效果闭合、不再可能迟到生效和重新授权证据，才允许同一 Intent 下的新 Attempt；部分效果不得完整重跑。
- 每个运行缺口均在 `5.12` 记录缺失事实、Owner、阻断行为、fail-closed 结果和恢复条件。`G1` 要求 P0/P1 具备已接受且可验收的正向产品语义；真实宿主尚不能供给该语义时阻断对应切片，不反向把运行缺证写成新的公共产品决策。

### 业务场景设计：`SIM-01` 商品钱包 900 支付与退款

- **业务问题与期望结果**：用户使用钱包完成 900 CNY 商品支付；业务履约、授权、扣划和退款分别可追溯，不处理外部轨道终态。
- **参与者与责任**：Order/Payment Owner 拥有订单、账单、履约和退款资格；Wallet/Transaction/Ledger Owner 拥有钱包准入、授权、完成、退款及账务/余额事实。
- **触发与前置事实**：租户、用户、订单/账单、900 CNY、付款钱包和收款责任已由宿主确认；宿主按已接受的 `P-SIM01-01-D` 在 A/B/C 中选择唯一模式，付款方和该模式要求的收款责任均须解析为准入的内部可记账账户并冻结责任关系与原 route。当前 `payeeId=capte` 不能替代选择结果或收款账户，见 `P-SIM01-01-HOST`。
- **主路径与状态变化**：业务受理 -> 授权资金事实 -> 授权账务 -> 钱包可用金额转为授权占用 -> 完成资金事实 -> 完成账务 -> 指定责任账户的目标余额效果可取证 -> Order Owner 的业务声明。各层独立取证；按已接受的 `P-SIM01-02-A`，纯内部钱包只有在业务目标、动作事实、平衡账务和指定责任账户余额效果均闭合后，才可最终声明 `PAID/REFUNDED`。
- **适用规则**：遵守 `Q-001` 的事实所有权与追加修复、`Q-002` 的账户解析和原 route、`Q-003` 的分层证据、`Q-004` 的稳定 Intent 与受控 Attempt；当前缺少 `P-SIM01-04` 的宿主权威查询证据，仍不得自动重做。
- **完成证据与验收种子**：`P-SIM01-03` 已接受“生命周期根 + 耐久独立动作事实”的稳定语义。授权、完成、退款各有不可变、可单独识别、可唯一定位且可被宿主耐久引用的动作事实；生命周期根和汇总只负责关联与累计，不单独证明动作成功。动作事实可由明细、事件或独立主事实承载，本层不预设“一动作一主交易流水”；交易、平衡账务、指定余额效果和幂等复用分别可验证，进程重启后仍可恢复。订单 `PAID/REFUNDED` 不冒充资金、账务、余额或对账证据；反之，任一单层资金流水、RouteSnapshot、LedgerEntry 或余额观测也不能单独推出订单 `PAID/REFUNDED`。
- **逆向、异常与停止**：完成前取消只释放未消费授权；完成后退款必须引用一个或多个已证明成功且仍可退的原完成动作事实，并按每个原完成事实的金额币种、责任、原 route 和可退总上限分别累计。拒绝需零 RouteLeg/posting/entry/余额；`UNKNOWN` 先查询。缺账户责任仍扣款、已完成后 reversal、当前绑定重算退款、换身份补单和缺少 Q-004 准入证据仍自动重做均为红线。`P-SIM01-01-HOST`、`P-SIM01-02-HOST`、`P-SIM01-03-E4` 与 `P-SIM01-04` 仍阻断现有宿主正向资金执行、最终展示、自动退款与集成闭合。

### 业务场景设计：`SIM-02` 券 100 + 钱包 900 组合支付

- **业务问题与期望结果**：一个 1000 CNY 账单由普通券 100 和钱包资金 900 共同满足；每一腿的结果、证据和逆向独立可恢复。
- **参与者与责任**：Order/Payment Owner 拥有组合计划和聚合结果；Coupon Owner 拥有券 lock/confirm/release/return；Wallet/Transaction/Ledger Owner 只拥有钱包 900 的资金事实。普通券不是资金账户或余额。
- **触发与前置事实**：券额度 100、钱包资金 900 与账单 1000 守恒；钱包双方责任满足 `SIM-01`，券只以业务资格和核销证据参与。完成顺序、部分成功政策和成功腿引用的耐久责任由宿主确认。
- **主路径与状态变化**：父计划受理 -> 券锁定与钱包授权分别成立 -> 各腿按宿主策略完成 -> 每腿局部证据汇总 -> Order Owner 的履约门槛。券腿只有业务效果；钱包腿独立形成资金、账务和余额影响。
- **适用规则**：父层不得覆盖局部事实；`UNKNOWN` 腿先查询；按 `Q-004` 冻结已完成组件、剩余上限和原决策后，才可只处理未完成组件；不得整组重跑。
- **完成证据与验收种子**：正常路径分别看到券确认 100、钱包完成 900 和父账单 1000；部分成功时成功腿引用、资金效果和补偿结果持续可见；补偿失败不覆盖原成功；重启后可从分腿事实恢复。
- **逆向、异常与停止**：两腿均未完成时分别释放；一腿已成功而另一腿未闭合时，按已接受的 `P-SIM02-01-A` 保留成功腿，在冻结的履约时限、业务授权和 Q-004 准入内优先恢复未完成腿；超出任一边界则放弃父支付并请求所有成功腿 Owner 追加逆向。任一腿 `UNKNOWN` 时父层未决，不执行新动作。总状态覆盖分腿、清空成功流水、券 ID 入账、`UNKNOWN` 补偿和整组盲重跑均为红线。父计划宿主证据缺口见 `P-SIM02-01-HOST`，Coupon 动作权威的宿主消费缺口见 `P-SIM02-02-HOST`。

### 业务场景设计：`SIM-03` Benefit 平台 60 / 商户 40 成本分配、资金 contribution 与退款

- **业务问题与期望结果**：以“100 CNY 券核销、平台承担 60、商户承担 40”作为验收模拟输入，检验成本责任、Benefit 承接责任和退款原事实能否分别解释；这不证明当前宿主已有一组运行中的 60/40 配置，也不预设 60/40 必然形成两笔内部资金转移。
- **参与者与责任**：Coupon/Benefit Owner 拥有核销和成本分摊决策；Order/Commercial 与 Finance/Accounting/Risk Owner 确认成本与承接责任；Transaction/Ledger Owner 只记录所选模式中适用的资金、账务和余额事实，不替业务 Owner 把经营折让资金化。
- **触发与前置事实**：核销金额、规则版本、分摊与舍入结果已确认；宿主按已接受的 `P-SIM03-01-D` 在 A/B/C 中产出唯一选择，并冻结成本与承接责任、是否形成内部资金转移及原事实。只有需要资金影响的责任项才解析内部可记账账户和必要账目语义；券、活动和核销日志只作业务引用。
- **主路径与状态变化**：核销计算出模拟 60/40 -> 按 `P-SIM03-01-D` 冻结的唯一模式分别形成平台资金 contribution、商户经营折让或商户资金 contribution -> 每项资金/非资金事实独立留存 -> Benefit Owner 的业务完成门槛。成本合计守恒为 100；资金事实数量可以是 0、1 或 2，取决于已签收模式，不得由 60/40 标签直接推导。影响价值的分摊、舍入和适用规则按 `Q-004` 固定为不可变业务决策类别。
- **适用规则**：Benefit `settle` 不表示 clearing/settlement batch 或对账完成；已形成的原 contribution 资金事实不可覆盖，退款沿原事实和原决策而非当前配置；原资金事实或业务决策快照缺失时停止。确定失败腿只有在 `Q-004` 准入证据和 Benefit 场景政策同时满足时才可新 Attempt。
- **完成证据与验收种子**：模式 A 应看到平台 60 的独立资金事实和商户 40 的经营折让事实；模式 B 应看到平台 60、商户 40 两组独立资金事实；模式 C 应看到两项成本业务事实且零 Benefit 资金影响。配置变为 70/30 后，历史退款/恢复仍引用核销时原 60/40 事实与决策；任何已形成的原交易与逆向均保留且累计不越界。
- **逆向、异常与停止**：资金项退款分别引用自身真实成功 contribution；非资金折让沿原订单/券业务决策恢复，不伪造资金退款。一项成功、另一项失败/未知时按已接受的 `P-SIM03-02-R-A` 保留逐项事实并优先恢复未完成项，越过冻结边界后逐项逆向已形成效果；不重做成功项。缺责任仍 settle、宽 context 承重、一条流水冒充多项、当前配置重算和把 FAILED/PROCESSING 记录存在当成功均为红线。宿主路由、父策略和逐项权威证据缺口分别见 `P-SIM03-01-HOST`、`P-SIM03-02-HOST`、`P-SIM03-03`。

### 业务场景设计：`SIM-04` VCC 授权、部分完成、释放与退款

- **业务问题与期望结果**：VCC 授权 100、两个完成输入 30/50、释放 20 和退款 20 沿同一事实链解释；已接受的 `P-SIM04-01-A` 要求资金公共层只消费权威归一的不可变增量，重复、乱序和迟到均不得重复影响资金。
- **参与者与责任**：VCC Owner 拥有 Card/VCC Transaction/Event 和展示；issuer/processor Owner 拥有外部权威事实；wind-funds 拥有 Credit/Funding 责任账户及资金、账务、余额。Card、PAN、token 和工具不入账。
- **触发与前置事实**：可信工具绑定、金额币种、责任解析和内部账户已确认；SHARED 可由 Credit 承担额度责任、父 Funding 承担真实资金责任，二者不是永久一对一。后继动作须定位原事实、原 route 与累计剩余范围。
- **主路径与状态变化**：来源证据 -> VCC/issuer 边界按已签收 authority/sequence 归一 -> 不可变增量 Event -> FundsTransaction -> Ledger -> 余额维度 -> Event applied -> VCC 聚合；Network Settlement 是独立链。显式增量模拟 `Δ30 + Δ50` 的完成累计为 80、剩余 20 可释放；issuer 累计快照 `30 -> 50` 须先按 `P-SIM04-02-D` 在 adapter 侧选择的已签收规则归一为 `Δ30 + Δ20`，具体规则仍受 `P-SIM04-02-HOST` 阻断，不得直接把快照 50 当公共层 `Δ50`。退款 20 必须引用可退的原成功 complete 事实。
- **适用规则**：拒绝事件可以业务 applied 但零资金；完成前 reversal 只释放剩余授权，完成后 refund 受本金上限约束；权威失败后的新 Attempt 必须满足 `Q-004` 准入和 VCC Owner 的场景授权。
- **完成证据与验收种子**：拒绝无 legs/posting/entry/balance；PREPAID/SHARED 责任可区分；显式增量与累计快照归一后的增量关系分别可复算；每次完成后剩余授权可观测；完成、释放、退款累计不越界；Event applied、入账、余额与 Network Settlement 不互推。
- **逆向、异常与停止**：未关联 refund、overcapture、迟到矛盾和 chargeback/dispute 保留差异并人工处理。Credit 当现金、issuer accepted 推导入账、当前 binding 重算、notice 自动退款和覆盖旧事实均为红线。未闭合运行能力见 `P-SIM04-01-HOST`，具体外部权威、finality 与 adapter 证据见 `P-SIM04-02-HOST`。

### 业务场景设计：`SIM-05` GlobalAccount / ACH confirmed credit、NOC 与 return

- **业务问题与期望结果**：区分 ACH 指令、外部处理、confirmed 事实、内部入账和可用余额；重复回执不重复入账，NOC/return 不冒充普通退款。
- **参与者与责任**：GlobalAccount Owner 拥有能力视图、Instruction、Receipt、Difference 和展示；bank/ACH/channel Owner 拥有外部状态语义；wind-funds 只拥有受控内部资金事实。外部账户不是内部余额主体。
- **触发与前置事实**：外部账户资格、tenant、direction、金额币种和引用可定位；上游业务/rail adapter 按已签收规则完成真实性、authority、scope、稳定身份、方向、原事实关系、规则版本和 confirmed 归一后，才可提交一次规范化资金指令。accepted/processing/NOC/只读证据不解析内部账户、不进入资金入口。
- **主路径与状态变化**：Instruction -> submitted -> accepted/processing（零资金）-> 上游权威 confirmed fact -> adapter 提交规范化 primary effect -> `wind-funds` 校验 tenant、金额币种、内部责任/账户、稳定身份、幂等冲突、原事实、累计上限和 route/账务守恒 -> FundsTransaction -> Ledger -> 指定余额。authority、内部闭合、可用性与 rail finality 分别声明；return/NOC/reversal 与后继对账是独立链。
- **适用规则**：confirmed fact 与最终入账均最多贡献一次；return/reversal 引用其实际作用的原外部事实和原内部资金事实并等待已签收矩阵；NOC 只形成未来主数据建议；`UNKNOWN` 沿原引用恢复。
- **完成证据与验收种子**：accepted/processing/NOC 的交易、账务、余额增量均为零；权威 confirmed 首次成立后只提交一次规范化 primary effect；同身份同语义重放原结果，同身份异金额/币种/方向/责任/原事实冲突并拒绝；外部账户只作证据，内部未知不得展示到账，差异需责任动作和后继对平关闭。
- **逆向、异常与停止**：重复 receipt 归并，迟到/冲突进入 Difference；真实性、原引用或状态映射不明时由上游人工停止，资金准入、账务或余额未知时由 `wind-funds` fail closed。到达顺序当权威、NOC 改余额、仅凭 `CONFIRMED` 字符串入账、换身份重发和外部账户入账均为红线。未闭合运行能力见 `P-SIM05-01-HOST`。

### 业务场景设计：`SIM-06` 收单 capture -> clearing -> settlement -> payout

- **业务问题与期望结果**：capture、清分、清算、结算锁定、payout 提交/外部结果和后继对账分别可解释，资金所在阶段与责任清楚。
- **参与者与责任**：Acquiring/PSP Owner 拥有 capture/refund/dispute；Merchant Settlement Owner 拥有清分、清算、结算和 payout；rail/bank Owner 拥有外部结果；wind-funds 拥有内部资金、账务、余额和 Gate 证据。
- **触发与前置事实**：Acquiring/PSP adapter 已按 `P-SIM06-01` 所选门槛验真并归一 capture；payer/收款责任、金额币种、原授权或已签收的无内部授权原事实、累计上限和责任规则版本均可冻结。`wind-funds` 仍独立执行资金准入与守恒校验。只有适用且已由 Owner 签收 Gate 的 clearing、settlement、payout 等写入动作，才在自己的最终写入边界复核 exact object 的 current evidence；capture 是否需要 fresh Gate 不在本合同批准。
- **主路径与状态变化**：达到所选门槛的 normalized capture -> 冻结责任模式指定的待清算资金责任；split confirmation 零资金；clearing Gate -> 可结算资金；settlement Gate/审批 -> 已锁定资金；payout Gate/authority -> submitted -> accepted/processing（零新资金）-> authoritative result -> payout 资金/账务；post-action reconciliation 独立发生。测试中的商户 `CLEARING` 只是一种 E2 组合证据，不批准公共账户类型、账目或 posting。
- **适用规则**：各 Gate 是前置准入，不是动作完成；split 前 refund 沿原 capture，清算后由有权 Owner 追加 adjustment，payout 后另记 recovery/追偿责任；失败后再次出款同时受 `Q-004` 准入和 payout Owner 场景政策约束。
- **完成证据与验收种子**：capture 后商户资金不冒充可用；split 零资金；清算、锁定、提交和 payout 结果各有事实；Gate blocked 零后续资金；accepted/processing 零新资金；旧 Gate 不跨对象/时点复用。
- **逆向、异常与停止**：normalized capture、内部资金动作、账务或余额任一必要维度 UNKNOWN 时沿原 identity 查询，零新 capture 资金效果；相反终态和引用冲突进入 mismatched/manual。RETURNED 未签收前不返还或重发。raw status/`CAPTURED` 字符串直接入账、capture 等于可用/可出款、BALANCED 自动执行、缓存 Gate 授权、外部成功内部未闭合时换 identity 重发、RETURNED 猜责任和 Recovery 创建等于已追回均为红线。相关产品政策已分别接受 `P-SIM06-01-A / P-SIM06-02-B / P-SIM06-03-B`，真实规则与运行证据仍由对应 HOST 门禁阻断。

### 业务场景设计：`SIM-07` 业务、内部资金与外部事实三方对账

- **业务问题与期望结果**：在冻结范围内回答业务、内部资金和外部事实是否完整、同额、同币、同状态，并让差异有 Owner、处置引用和后继对平。
- **参与者与责任**：宿主、Transaction/Ledger/Balance、adapter/rail 分别拥有三方源事实；Reconciliation Owner 只拥有 scope、快照、匹配结果、差异、lineage 和 Gate，不改写源事实。
- **触发与前置事实**：tenant、对象范围、currency、时间窗口/时区/日期语义、规则版本、coverage/watermark 和来源 Owner 可证明；每侧先冻结不可变 normalized facts。Provider 只支持严格 `1:1` 比较，不冒充 native 三方或 `1:N/N:1` matcher；复杂关系必须由来源 Owner 先聚合。
- **主路径与状态变化**：三方事实确认 -> 规范化/快照 -> coverage -> run/result -> balanced 或 difference；差异 -> Owner/处置引用 -> 新快照/后继 rerun -> current balanced -> closed。对账与 Gate 全程零自动资金影响。
- **适用规则**：全覆盖且逐项满足规则才 balanced；来源、规则或 evidence 变化创建 replacement lineage；资金修复由有权资金用例追加新事实，对账只关联。
- **完成证据与验收种子**：Batch completed 与 balanced 分开；旧/错对象/非 current lineage 不能 Gate passed；同一冻结输入重放原结果，变化输入创建新 run；差异关闭同时要求受控处置引用和后继 current balanced。
- **逆向、异常与停止**：缺侧、coverage 不足、漂移、重复映射和金额/币种/状态冲突拒绝封版或形成差异；无法定责时 blocked/manual。行数相等判平、反写交易/分录、旧 balanced 复用、difference 自动调账和人工关闭冒充对平均为红线。产品政策已接受 `P-SIM07-01-A`，Provider strict-exact 已具备；未闭合的真实来源、Consumer、恢复与 E4 见 `P-SIM07-01-HOST`；对账 run/rerun 的证据血缘不等同于资金 Intent/Attempt。

- **当前宿主证据门禁**：当前 Capte 不能耐久保留策略版本、成功腿和每次逆向/补偿事实，且父级 failure 会覆盖局部结果；该缺口转为 `P-SIM02-01-HOST`。在其关闭前不自动继续、逆向或声明完整/已取消。
- **资金与恢复红线**：不得丢弃成功腿引用；不得在 `UNKNOWN` 时 cancel/refund 另一腿；不得整组重跑；不得把确定失败简化为自动重试；补偿失败必须与原成功同时可见；普通券不因此成为资金账户或 FundsTransaction。
- **非裁决项**：Coupon confirm、release/cancel、return 权威查询的具体实现、Provider API、事务/Saga、重试次数、具体执行器技术顺序和补偿实现。

### 5.16 `P-SIM02-02-A` Coupon 动作权威裁决

- **状态**：`accepted / P-SIM02-02-A`；本题只裁决 Coupon 动作事实由谁权威回答、父计划可以消费什么，不把普通券资金化，也不批准 API、存储或事务实现。
- **决策命题**：对一笔已锁定券，`confirm`、`release/cancel`、`return` 发生超时、异常、重启或迟到冲突时，Order 应以哪类 Coupon 事实判断动作是否闭合，并安全推进 `P-SIM02-01-A`。
- **当前事实**：Coupon 域源码已形成 lock、redeem、release、return/not-return/compensate 等不可变动作流水及按原事实查询的能力；同步结果也携带动作引用。Order 的 Coupon 参与方却只看 `success`，confirm 不保存核销引用，cancel 返回原 lock 引用，return 不保存退券引用；confirm 异常还会立即 release。因此当前实现证据支持“动作事实应成为权威”，但不证明宿主已经正确消费或运行闭合。
- **共同底线**：每个动作至少具备稳定动作身份、动作类型、券价值/范围、局部领域结果、业务效果、证据确定性和可查询引用。lock 是本次用券链的原事实；confirm 与 release/cancel 是引用该 lock 的互斥支付阶段决策；release/cancel 只能释放尚未被 confirm 消费的 lock 范围；return、not-return 或 Coupon 补偿必须引用真实成功的 confirm 事实。同步响应、父计划状态和 Coupon 当前聚合状态都不能单独覆盖不可变动作事实。

| 方案 | 事实权威与动作身份 | 原事实与可逆范围 | UNKNOWN / 重启恢复 | 父计划可消费的声明 | 自动化边界与代价 |
| --- | --- | --- | --- | --- | --- |
| A 全动作权威（已接受） | Coupon Owner 为 lock、confirm、release/cancel、return 分别维护不可变、可唯一定位的动作事实；聚合状态只是投影 | confirm/release 引用原 lock；return 引用成功 confirm，并受原券价值与已逆向范围约束 | 调用异常或响应丢失时沿原动作身份查询；查不到、冲突或证据未闭合均保持 `UNKNOWN`，不新发相反动作 | 父计划只消费 Coupon Owner 对具体动作事实给出的本层已知/终局、领域结果、事实引用和不可外推范围 | 四动作均可在证据闭合后自动推进；要求宿主耐久保存引用，但不要求特定物理载体 |
| B 受限动作权威 | 只对 Owner 明确签收的动作提供与 A 相同的耐久事实；未覆盖动作保持 `NOT_SUPPORTED/PENDING` | 已覆盖动作沿原事实约束；未覆盖的 release/return 不得由当前状态或其他动作代替 | 已覆盖动作可沿原身份恢复；未覆盖动作永久 fail closed/manual，不能承诺稍后自动补齐 | 父计划只消费已签收动作的局部声明；一旦流程需要未覆盖动作即保持未决并转人工 | 可窄化自动能力，但不是 A 的分期实现；缺任一必需动作就不能自动完成对应正向或退出路径 |
| C 当前状态、同步响应或 Order 影子状态为权威 | 没有稳定动作身份，以用户券当前态、调用布尔值、异常映射或父计划本地状态判断动作 | 无法可靠证明原 lock/confirm、可逆范围或互斥动作因果 | 超时只能猜成功/失败，重启后由宿主自证 | 父计划可快速推进，但无法证明 Coupon 实际效果 | 拒绝候选；正是当前异常后 cancel、局部事实丢失和错误退出风险的来源 |

- **Owner 回答与最终结论**：用户明确接受 `P-SIM02-02-A`。Coupon Owner 的耐久动作事实是唯一业务权威；Order 只保存引用和本地消费结果，不复制或改写 Coupon 事实。A 是产品语义，不要求动作事实落为某种 Java 类型、表或状态枚举；B/C 不采用。
- **动作与逆向门槛**：confirm 只有在其动作事实被 Coupon Owner 权威证明闭合后才算券腿成功；release/cancel 只解除仍有效且未 confirm 的 lock；return 只作用于已成功 confirm 的券效果，并沿原 confirm 事实形成新的关联事实。`FAILED/REJECTED` 标签、查询未命中或“当前不存在日志”本身既不证明券效果为零，也不自动授权相反动作。任何动作 `UNKNOWN`、查询不可用或发生互斥事实冲突时，只能沿原身份查询/补证，父计划保持未决并转人工，零新 confirm/release/return、零钱包逆向或补偿。
- **可观察 AC**：重启后可由原 lock 与父计划引用恢复 confirm 或 release/cancel 的唯一权威事实；退款阶段可由原 confirm 恢复 return/not-return/compensate 决策事实；重复查询不产生新券效果；同步超时不触发相反动作；父层展示始终保留 Coupon 原动作与钱包腿各自事实。
- **当前能力与后续门禁**：现有 Coupon 动作流水和查询只是源码 `E2` 候选证据；Order 尚未保存/查询动作引用，真实 Bean、schema、事务及宿主恢复未验证。接受 A 只关闭产品权威选择，宿主缺口继续由 `P-SIM02-01-HOST`、`P-SIM02-02-HOST` 和后续集成证据阻断。
- **red lines**：不得把普通券映射为 FundsTransaction；不得把 `success=true`、异常、本地父状态、当前用户券状态或“存在一条日志”单独当作动作闭合；不得在 confirm `UNKNOWN` 时 release，也不得在 release/return `UNKNOWN` 时逆向钱包或声明已取消；不得用当前规则重算或覆盖原动作事实。
- **非裁决项**：具体查询接口、DTO、表/字段、状态枚举、锁和事务、消息、重试次数、P-SIM02-01-HOST 的父计划持久化，以及 G1/DSL/系分/TDD/实现授权。

### 5.17 `P-SIM03-01-D` Benefit 成本与承接责任路由裁决

- **状态**：`accepted / P-SIM03-01-D`；接受范围是“按 Benefit 产品/订单责任范围显式选择并冻结 A/B/C”，不是新增第四种经济模式，也不裁决账户类型、账目代码、posting、会计分录、API 或实现。
- **决策命题**：在 100 CNY 券核销模拟中，平台承担 60、商户承担 40 时，这两项分别是什么经济责任，订单价值由谁承接，哪些项应形成独立资金事实及如何沿原事实逆向。
- **当前事实**：60/40 只来自当前验收模拟和活动分摊配置，不能证明真实合同或固定比例。Capte 把出资角色、资金性质和 Benefit receiver 分开配置，但生产 settle 请求尚未提供完整成本/承接责任；Fincone 已签收的窄化设计子契约只支持商品订单 `SPECIFIED` 补足该订单冻结经济受益责任的待清分应收。当前测试宿主 L3/E4 已通过，启用、发布和生产仍阻断。
- **共同责任快照**：无论选择 A/B/C，都必须冻结 tenant、商品订单/核销原事实、业务场景、币种、责任规则版本、平台/商户成本金额、分摊与舍入决策、经济价值承接责任，以及每项是否产生内部资金影响。成本承担方不自动等于卖方、收款方或 Benefit 承接方。
- **接受答案 D**：公共能力不固定某一成本/资金模式；宿主按 `tenant + 产品类别/商品订单 + business scene + merchant（或无 merchant）+ currency + Benefit 责任规则版本` 在 A/B/C 中显式选择，每次核销只能冻结一种模式。D 只是责任路由规则，不产生第四种资金影响；当前只有 Fincone 已接受的商品订单 `SPECIFIED` child scope 可使用 order payee 作为冻结经济价值承接来源，其他产品类别未签收时保持 fail closed。无法唯一命中、多模式同时命中、责任规则版本不明或快照冲突时，必须 fail closed，不设默认优先级或降级模式。

| 方案 | 适用产品类别 | 平台 60 / 商户 40 成本责任 | Benefit 承接责任与正向效果 | 每项事实与 partial | 退款 / 恢复原事实 | 代价与边界 |
| --- | --- | --- | --- | --- | --- | --- |
| A 平台资金补足 + 商户经营折让（推荐） | 商品订单由平台补贴与收款商户共同让利；商户 40 表示少收而非另行注资 | 平台 60 是独立资金成本；商户 40 是订单/券经营折让责任，不产生第二笔内部价值转移 | 平台 60 补足订单已冻结经济受益责任；商户 40 直接减少该订单原应收，不能再次增加同一应收 | 一笔平台 contribution + 一笔商户经营折让事实；任一未知不覆盖另一项，父 Benefit 保持 partial | 平台份额引用原成功 contribution 逆向；商户份额沿原订单/券折让事实恢复，不伪造资金退款 | 资金事实最少，避免同一商户自转和重复确认应收；要求订单原价、折让后应收和平台补足三者守恒 |
| B 平台与商户分别资金出资 | 平台和商户均存在经 Finance/Accounting/Risk 签收的独立营销资金责任 | 平台 60、商户 40 各自由自身已冻结成本责任承担，不能仅由角色或活动字段推导 | 两项分别补足订单已冻结经济受益责任；若商户成本方与承接方属于同一商户，必须证明是两个真实且不同的经济责任，不能无意义自转 | 两笔独立 contribution；每笔各有成本、承接、金额币种和结果，单项未知/失败不覆盖成功项 | 每笔退款只引用自身真实成功 contribution，并分别遵守原责任、原 route 与累计上限 | 自动资金与证据成本更高；未证明两项独立经济实质或非重复价值影响时不得选择 |
| C 仅成本分配、零 Benefit 资金动作 | 60/40 只用于营销归因、经营分析或后续人工结算，本场景不承诺内部实时价值转移 | 平台和商户仅形成业务成本归属，不创建 Benefit 资金 contribution | 订单价格/应收如何体现必须由订单商业合同另行闭合；Benefit 本层零资金影响 | 两项业务责任事实，零 Funds/Ledger/Balance 影响；不得一边选择 C 一边调用 settle | 退款只恢复原业务折让/成本决策，不创建 Benefit 资金退款 | 自动化最低；SIM-03 的资金正向能力标为 `NOT_APPLICABLE`，不能冒充两笔资金能力 |

- **推荐 A 的理由**：当前商品订单 `SPECIFIED` 的目标是解释同一销售优惠如何由平台补贴与商户少收共同承担。A 只为真实外部补足部分形成资金 contribution，同时保留商户 40 的经营折让事实，最少产生资金动作，也避免同一商户既作为成本方又作为承接方时重复确认价值。若 Finance/Accounting/Risk 能证明商户存在独立营销资金责任且该转移不是自转或重复应收，再选择 B。
- **共同完成与退款门槛**：只有权威闭合的资金/非资金责任事实才计入已完成成本；`FAILED/PROCESSING/UNKNOWN`、记录存在、当前余额或聚合状态均不能单独证明成功。配置变为 70/30 后，历史退款/恢复仍沿原 60/40 责任快照；每笔资金退款只引用自身真实成功 contribution，非资金折让不伪造资金原事实。
- **不可外推范围**：Benefit settle 只证明本场景已签收的资金责任动作，不证明 clearing batch、settlement、payout、商户可用余额、银行到账或 reconciliation。待清分应收也不等于可用、已结算或外部到账。
- **Owner 回答与最终结论**：用户明确接受 `P-SIM03-01-D`。D 要求每次核销在 A/B/C 中唯一选择并冻结完整责任快照；真实合同、会计、风险和账户准入仍由对应专业 Owner 终审。
- **red lines**：不得从 `PLATFORM/MERCHANT`、资金性质、活动 receiver 字段、当前配置、测试账户、order payee 或既有待清分设计反推成本责任；不得把成本方自动等同收款方；不得用一条聚合事实冒充多个责任项；不得按当前配置退款；不得只引用核销/活动而不引用原成功 contribution；不得把平台中间责任、用户/订单价值池或活动静态 receiver 偷渡进当前窄化场景。
- **未关闭项**：`P-SIM03-01-HOST`、`P-SIM03-02-HOST`、`P-SIM03-03` 仍分别约束真实宿主的 A/B/C 路由与责任快照、父策略与 partial 恢复、多责任项动作与权威证据；在首个真实可部署 Consumer 出现前保持 `DEFERRED`，不要求 `capte-domain` 通用模块提供生产数据库、composition root 或 L4。当前公共制品与 Capte 集中测试切片已证明 artifact lineage、Bean/schema/事务、单项 `SPECIFIED` E4 与版本解析；`VC-002`、真实 Consumer enablement、发布和生产仍由 OpenSpec 单独准入。

### 5.18 `P-SIM03-02` Benefit 部分成功与恢复政策

- **状态**：`accepted / P-SIM03-02-R-A`。用户已明确选择 `R-A`；本题只裁决 D 已冻结责任模式后的父 Benefit 策略，不重开责任模式、金额、承接方或规则版本。
- **命名**：`M-A/M-B/M-C` 表示 `P-SIM03-01-D` 已接受的三种责任模式；`R-A/R-B/R-C` 表示本题的三种恢复策略，两组字母彼此正交。
- **共同输入**：冻结 tenant、产品/订单/核销原事实、business scene、merchant（或无 merchant）、currency、D 选择结果、责任规则版本，以及每个必需责任项的身份、Owner、资金/非资金类型、金额、舍入、承接责任、原事实关系、局部领域结果、价值效果和证据引用。历史处理不得读取当前配置重算。
- **共同停止线**：任一项 `UNKNOWN/PROCESSING`、证据冲突或查询不可用时，整组零新执行、零新 Attempt、零逆向，只沿原项身份查询或补证；已闭合项不得覆盖、清零或重做。`FAILED/REJECTED` 标签只有在本项权威证明局部终结、目标效果为零或责任已闭合且不再可能迟到生效后，才进入策略选择。

| 策略 | 适用前提 | 已闭合项 | 未完成项与确定失败 | UNKNOWN | 逆向 / manual | 父层声明与闭合门槛 | 代价与风险 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `R-A` 恢复优先，越界后逐项逆向（推荐） | 冻结责任项、履约时限、业务授权和恢复边界均可证明 | 保留原事实，不重做 | 尚未执行项可按冻结策略继续；确定零效果失败项仅在 Q-004 准入和重新授权成立时继续。超出任一冻结边界即停止正向 | 只查原项，整组不扩张效果 | 不能继续时，资金项引用各自原 contribution 逆向，非资金项沿原折让/成本事实恢复；任一逆向未闭合即 manual | 所有必需项正向闭合才完整完成；所有要求逆向的已成功项分别闭合且未知终结后才完整恢复 | 完成率较高，但需要最完整的逐项权威查询、时限和授权证据 |

- **责任模式适配**：`M-A` 分别处理平台资金 contribution 与商户非资金折让；`M-B` 两笔资金 contribution 各自保留原引用、累计和退款上限；`M-C` 两项均为非资金责任，任何策略都不得创建 FundsTransaction、Ledger 或 Balance 影响。三种策略不得改变已冻结的 M 模式，也不得将失败项金额转嫁给成功项。

### 5.19 `P-SIM04-01` VCC 责任与授权累计决策包

- **状态**：`accepted / P-SIM04-01-A`。接受范围只包括 PREPAID/SHARED 的内部责任配置，以及资金公共层消费规范化增量动作并约束 authorize/complete/release/refund 累计的产品合同；不裁 issuer/processor 权威来源、事件优先级、finality、overcapture、late clearing、Network Settlement、账户分类或 posting。
- **事实基线**：Provider 当前源码/测试 `E2` 支持“授权根 + 后继动作事实 + 授权根级 complete/release/refund 累计”，也存在 SHARED Credit 子责任与 Funding 父责任的测试意图，但没有真实 VCC runtime Consumer。当前 refund 只引用 authorization root，并按根聚合的 `completed-refunded-declined` 校验上限；不能证明目标合同要求的逐 complete 分配与逐笔可退上限。Fincone VCC 文档仍为 `REVIEW_READY / OwnerDecision=PENDING / E1 / NOT_STARTED`；它支持通用增量 Event 模型，但具体 30/50 样例是 issuer 累计快照，最终 completed=50。候选 A 的具体 `Δ30 + Δ50 = 80` 来自 Provider/SIM 产品候选，不是 Fincone 已确认数字事实，不能由现有材料替 Owner 选择。
- **共同责任输入**：冻结 tenant、VCC/program/card、business scene、currency、授权金额、责任模式与规则版本、Credit/Funding 关系、原 authorization、原 route 和各动作适用范围。Card、holder、PaymentInstrument、Credit、Funding 分层；卡、PAN、token、工具和外部 IssuerAccount 均不是内部余额主体。Fincone adapter 还必须证明 PREPAID 的逐卡 Funding 子责任、SHARED 的逐卡 Credit 子责任和父 Funding 关系均已准入，且多张 SHARED 卡不共享同一 Credit 子责任；该宿主前置不批准公共账户类型或 posting。
- **共同责任合同**：PREPAID 的真实资金责任由本次已准入 Funding 承担；SHARED 的 Credit 承担额度/应还责任，父 Funding 承担真实资金或结算责任。Credit 不是现金，Funding 不是额度，二者不是永久一对一；后继动作只能重放原授权冻结关系，不按当前 binding 重算。
- **共同累计合同**：只按权威闭合的动作事实更新累计。`confirmedCompleted + confirmedReleased <= authorizedDisposition`；剩余可完成/可释放范围等于授权可处置总额减已确认完成和已确认释放。refund 必须分配并引用一个或多个真实成功 complete，按每个原 complete 的金额、币种、责任、原 route 和可退总上限分别满足 `confirmedRefunded + currentRefund <= originalCompletedRefundableCap`。release 不得作用于已完成部分，refund 不恢复授权可完成额度。

| --- | --- | --- | --- | --- | --- |
| A 规范化增量动作事实（推荐） | 公共合同只消费已由 VCC/issuer Owner 确认的动作增量；模拟明确为 `authorize Δ100 -> complete Δ30 -> complete Δ50 -> release Δ20 -> refund Δ20`。issuer 原报文如何归一仍受 `P-SIM04-02-HOST` 阻断 | 两种模式均按共同责任合同冻结；SHARED 同时保留 Credit 与父 Funding 责任证据 | 每个增量最多贡献一次；30 与 50 是两个成功 complete，累计完成 80，释放 20 后授权余量 0，退款 20 后剩余可退 60 | 未知动作不计入也不证明零效果；保留已确认增量及其上限，零新同类/相反动作，只查原动作 | 与当前 Provider 累计模型同向，金额守恒最直观；要求 VCC 边界先把外部金额归一为权威增量 |

- **Owner 结论**：接受 A，不选择 B。资金公共层只消费已经由 VCC/issuer 边界权威归一的不可变增量动作；issuer 原报文为累计快照时，必须先按 `P-SIM04-02-D` 在 adapter 侧选择、并由 `P-SIM04-02-HOST` 取得证据的 authority/sequence 规则归一，例如 `30 -> 50` 形成 `Δ30 + Δ20`，不得把快照 `50` 直接当成公共层 `Δ50`。A 的验收模拟 `Δ30 + Δ50 = 80` 仍只是显式增量输入样例，不反向改写 Fincone 的累计快照事实。B 作为未选择候选保留在决策证据中。
- **授权拒绝与异常**：authorize `REJECTED` 不产生可执行 legs、posting、LedgerEntry、余额变化或 declinedAmount；可保留无 legs 的解释性 route snapshot，且不进入后继累计。任一动作 `UNKNOWN/PROCESSING`、冲突或查询不可用时，零新同类或相反动作，只沿原动作身份查证。`FAILED/REJECTED` 标签本身不证明零效果；已证明的局部完成、释放或退款必须保留并占用对应上限，不整组重做。
- **证据分层**：authorization accepted、动作事实、账务、余额、issuer Event、Network clearing/settlement 和争议分别独立；聚合状态、返回引用、单个 Event、单条账务或余额变化均不得单独证明其他维度。卡关闭/过期也不覆盖迟到动作或原事实。

### 5.21 `P-SIM05-01` ACH 外部事实、return/reversal 与 NOC 决策包

#### 共同不变量

1. 同一 run 只消费一组冻结来源；同摘要重放原结果，scope/window/rule/source/evidence 变化必须创建新 run 并保留 previous/superseded lineage。旧 batch/run/match/difference/action 不覆盖、不删除。
2. 同一来源成员在一个结果中最多贡献一次。禁止用重复引用把 `1:N/N:1` 伪装成多个 `1:1`；未证明 coverage 的空侧、缺侧或总额相等不得自动对平。
3. 跨币比较必须先由来源 Owner 提供已签收的 FX 时点、来源、舍入和规范化 Money；否则进入 Difference/manual。金额为零、总额相等、Ledger 平衡或 Balance 相等均不替代逐项 provenance。

5. Gate 只消费 exact object 的 current completed/balanced lineage 和未关闭 Difference；`inspect` 是解释快照，最终资金命令必须在自身事务内重新 `check`。Gate/Balanced 不是可缓存授权、close evidence、调账指令或外部 finality。

## 6. 关键流程

本章只归纳跨场景复用的主流程、逆向和停止路径，不重复场景细节。

### 6.1 主流程

宿主确认业务事实和责任 -> 公共能力校验资金前提 -> 创建内部资金事实 -> 形成账务与余额结果 -> 返回稳定引用和查询证据。每一步的业务完成、内部记账和外部到账必须分别表达。

### 6.2 逆向流程

宿主引用原资金事实并说明逆向原因 -> 公共能力校验原责任、累计金额和可逆范围 -> 追加逆向交易与账务事实 -> 保留原事实和新事实的关系。当前配置变化不得改变原路径。

### 6.3 异常与人工处理

材料不足、同一幂等身份语义冲突、外部事实未知、账务不平衡或对账差异未关闭时停止资金影响。系统应返回可定位的失败或待处理结果；需要人工裁决时必须明确处理 Owner、所需证据和禁止绕过的 Gate。

### 7.1 已确认跨场景规则

1. 宿主业务生命周期与内部资金事实分属不同 Owner，任何一方都不能用自己的状态覆盖另一方事实。
2. 已记录的交易、账本分录和对账结果不可原地修改；逆向和修复只能追加关联的新事实。
3. 资金责任方、交易角色、内部可记账账户、账目/余额维度、支付工具，以及业务事实、原资金事实、账本事实和外部证据引用是不同产品对象，不得互换。
4. 当业务对象、交易角色、支付工具或外部端点将产生内部资金/账务影响时，必须按 tenant、currency、业务场景/账户模式与责任规则解析到一个或多个内部可记账账户，并把规则版本、账户关系和原 route 冻结在资金事实中；逆向沿原事实，不按当前配置重算。
5. NOC、拒绝和纯只读证据不产生内部资金影响时，不得为满足模型而解析或创建账户；Card、Payment Instrument、控制范围、GlobalAccount 产品对象和外部账户/轨道不得直接持有内部余额或成为账本主体。
6. 每个事实 Owner 所回答的独立问题构成正交证据维度，不存在跨 Owner 总 `SUCCESS` 或全局单调完成度枚举；业务、外部、资金交易、账本、余额、对账/Gate 只是基础示例，清分、清算、结算和出款等场景问题保持独立。
7. 每个场景声明所需证据维度、局部偏序和最终展示门槛；每个维度分别表达适用性、证据确定性/终局性、领域结果、资金效果、证据引用和不可外推范围。RouteSnapshot、transaction、ledger、余额、payout 和 reconciliation 任一维度都不得替代其他维度。
8. 提交后证据未知不等于领域失败或成功，必须沿原幂等身份和权威查询恢复；不得改换业务身份制造第二次资金请求。
9. 相同幂等身份且已承诺的经济语义一致时只能引用或复用原权威事实，不产生第二次资金影响；同一身份下金额、币种、责任账户、原事实或预期资金效果发生差异时必须停止并保持零新增资金影响。
10. 授权生命周期采用“可解释的生命周期根 + 耐久独立动作事实”的稳定语义：每次 complete、reversal、refund 均须有不可变、可单独识别、可唯一定位且可被宿主耐久引用的动作事实；生命周期根、返回引用或聚合摘要不单独证明动作成功。refund 引用真实成功且仍可退的原 complete 动作事实，并按每个原事实的金额币种、责任、原 route 和可退总上限分别累计。动作事实可落在明细、事件或独立主事实，本规则不批准具体物理结构。

11. 经济意图 `Intent` 与执行 `Attempt` 分层；Delivery、Event 和 Evidence 不得冒充 Intent 或 Attempt。同一 Intent 任一时刻最多一个 Attempt 仍可能产生目标经济效果。
12. 只有权威分别证明旧 Attempt 的局部结果为确定性失败/拒绝、目标资金效果为零或相关责任已经济闭合、旧 Attempt 不再可能迟到生效，并经重新授权后，才允许同一 Intent 下的新 Attempt。`UNKNOWN`、在途、冲突或外部成功但内部未闭合时禁止新 Attempt；领域结果和资金效果不得合成一个状态。
13. 同一 Intent 内，作用域/责任、经济动作与业务目的、价值、因果关系、预期资金效果和承重业务决策类别不可漂移。会改变责任、金额、准入或结果的分摊、舍入、规则版本和经济生效时点属于不可变经济语义；具体字段后置。
14. 退款、reversal、return、adjustment 和经济补偿是引用原事实的独立追加 Intent/事实；查询、证据补全、同语义重放和继续已冻结的未完成组件属于原 Intent/Attempt 的恢复。存在部分效果时禁止重跑完整 Intent，只有冻结完成部分、未完成部分、剩余上限和原决策快照后才可只处理未完成组件。

### 9.4 `MIG-02B` authorization release 产品合同

本卡只定义普通授权生命周期内“释放尚未完成授权余量”的公共资金语义。它复用已接受的 `release` action kind，不新建撤销状态机、通用逆向引擎或场景策略。

| 维度 | 产品合同 |
| --- | --- |
| 前置事实 | release 使用独立 reverse Intent；该 Intent 必须唯一引用同 tenant、同币种、真实成功且可证明的 authorization ActionFact。拒绝、缺失、冲突或 UNKNOWN 的授权不得进入 release。 |
| 动作与金额 | release Attempt 属于该 reverse Intent；每次 release 是独立、耐久、可唯一定位的新动作事实，Money 为正且只占用尚未 complete/release 的授权余量。 |
| 累计 | `confirmed complete + confirmed release <= authorized disposition`；release 不撤销已完成金额，refund 不恢复授权可完成额度，已证明 partial 立即占用上限。 |
| 责任与 route | 沿原 authorization 冻结的责任、账户关系和 route provenance 释放；不得按当前 binding、余额、卡状态或调用方指定 route 重算。 |
| 重放与冲突 | 同 identity 同语义复用原结果；同 identity 异 Money、币种、原授权、责任或 route 视为冲突，零新增动作/账务/余额。 |
| UNKNOWN | 只按原 release identity 查询和恢复；任一可能效果未闭合时不得换 identity 新建 Attempt，也不得自动 complete、release 或逆向。 |
| 完成证据 | release 领域结果、ActionFact、FundsTransaction、Ledger、Balance 与外部 authority/finality 正交；任何单层成功不得替代其他层。 |

最小金额种子：`authorize100 -> complete30 -> release20`，结果为 `completed=30`、`released=20`、`authorizationRemaining=50`；原 authorize 与 complete ActionFact 不变。`authorize100 -> complete80 -> release30` 必须因只剩 20 而拒绝，既有事实保持不变。

本卡明确排除 balance unfreeze、settlement lock release、payout failure release、refund、force/no-auth complete，以及仅凭 expired、timeout、卡关闭或外部事件名自动释放。它们只有在各自原事实、责任和真实复用需求独立闭合后才能另开文档卡。

### 9.5 `MIG-02C` authorization refund 产品合同

本卡只定义普通授权链上对真实成功 complete 的退款。refund 建立独立 reverse Intent，不覆盖 authorization 或 complete，不把 authorization root 的聚合额度当作逐 complete 原事实。

| 维度 | 产品合同 |
| --- | --- |
| 原事实 | reverse Intent 必须显式引用 `1..n` 条同 tenant、同币种、真实成功且可证明的 complete ActionFact；只引用 authorization root 不合法。 |
| 逐笔分配 | 每个原 complete 都有明确的正 `allocated Money`，分配合计必须等于 refund Money。`wind-funds` 不按 FIFO、LIFO、比例、到达时间或当前余额猜分配。 |
| 逐原上限 | 每条 complete 的已证明 refund 累计不得超过其同币种可退上限；已证明 partial 立即占用该上限，多笔 complete 不得相互挪用。 |
| 责任与 route | 每笔分配沿对应 complete 的冻结责任、原账户关系和 route provenance 执行；不得按当前 binding、账户状态或调用方自报 route 重算。 |
| 生命周期 | refund 不恢复 authorization 可 complete 额度，不改写原 complete 的 identity、Money、effect、digest 或 route provenance。 |
| 重放与 UNKNOWN | 同 identity 同语义复用；异 Money、分配、原 complete、币种、责任或 route 冲突。UNKNOWN 只查原 refund identity，不换号补单、自动逆向或重新分配。 |

最小金额种子：`authorize100 -> complete30 -> complete50 -> refund20`，refund20 明确分配给首笔 complete30；退款后两笔 complete 分别剩余可退 `10/50`，总剩余可退 `60`，authorization 可 complete 额度不因 refund 恢复。若一笔 refund40 覆盖两条 complete，必须显式给出例如 `10 + 30` 的逐原分配，不得只给根级总额。

当前 Provider E2 仅接收 `authorizationTransactionSn`，按 authorization root 执行 `AUTH_REFUND` 并校验根级 `completed - refunded - declined`；现有 request、instruction reference 和 durable action group 都没有不可变的逐 complete 分配证据。因此现有 root-level refund 只是执行/迁移证据，不得投影成本卡的 canonical refund ActionFact。该缺口命中 `D-MIG-001-A` 的“不可机械证明即停止”条件：只有新的项目级分配耐久性决策才能恢复 canonical refund 设计，不得直接进入实现。

本卡明确排除 no-auth refund、dispute/chargeback、direct refund、fee refund、payout RETURNED/recovery 以及外部 rail authority/finality。这些路径不得因为复用 `AUTH_REFUND` 名称或根级金额而自动进入本卡。

### 9.6 `D-MIG-001-R` refund allocation durability 决策摘要

决策题只有一个：当前根级 `AUTH_REFUND` 没有逐 complete 分配证据时，项目是继续保持 canonical refund 不支持，还是引入可证明分配的耐久承接。三个候选都不改变 9.5 的产品合同：

| 候选 | 产品结果 | 边界与代价 |
| --- | --- | --- |
| `A / DEFER_CANONICAL_REFUND_PROJECTION`（ACCEPTED） | 保留现有 root-level refund 执行，但不对外声明逐 complete canonical ActionFact；需要该事实的 Consumer 保持 unsupported/manual。 | 零新持久化和迁移成本；等首个真实 Consumer 提供分配、恢复和历史需求再重开。 |
| `B / VERSIONED_EXISTING_GROUP_ENRICHMENT` | 保持 `D-MIG-001-A` 的唯一 durable group，但对新版 ordinary authorization refund 持久显式 complete refs、allocated Money 和逐原 route provenance。 | 需要真实 Consumer、上游分配契约、版本化格式和一次切换；历史 root-only refund 不猜回填，继续 unsupported/manual。 |
| `C / FULL_PROJECT_ACTIONFACT_SOURCE_SWITCH` | 重开原 `D-MIG-001-B`，将既有与后续全部 action kind 一次性迁移到独立耐久 ActionFact 事实源。 | 范围最大，需全量 schema、回填、校验、切流与整版回滚；不能只为 refund 单独开启。 |

Human Owner 已接受 A。接受理由是：发卡行或上层业务并不保证提供可证明的逐 complete 退款来源，`wind-funds` 只能消费上游明确、权威、稳定的关联，不能按金额、时间、顺序或根累计强行匹配。A 不删除现有 root-level refund 执行，也不把它升级为 canonical 事实；来源缺失不是构造伪关联的理由。

接受 A 不否定未来真实关联：只有真实 Consumer 能稳定提供 complete refs、allocated Money、原 route、恢复和历史处置证据时，才项目级重开。B/C 未选择且不是运行时 fallback；按 action 采用“旧动作投影、refund 独立写入”的混合方案仍是已拒绝的双真相，不是第四候选。

### 9.7 `MIG-04` Transaction / Wallet ownership 产品边界

本卡只冻结公共能力 Owner 和一次性迁移边界，不设计 Java 签名或兼容方案。目标不是把 Wallet 能力搬空，而是让每个模块只回答自己的稳定资金问题。

| 能力 | 目标 Owner | 产品边界与处置 |
| --- | --- | --- |
| 账户、责任关系、PaymentInstrument/binding、能力与状态、Spend Rule/decision/control movement | Wallet | 保留为 Wallet 资金准入与控制事实；Wallet 不创建 FundsTransaction，不拥有交易生命周期。 |
| Intent/Attempt、资金动作指令、ActionFact、交易 root/detail、原事实、累计、route 与动作编排 | Transaction | 统一承接资金动作与生命周期；可消费 Wallet 的冻结准入/控制事实，但不得依赖 Wallet 实现、DAL 或 Mapper。 |
| Ledger profile、posting、LedgerTransaction/Entry、Balance projection 与窄只读事实 | Ledger | Ledger 事实不再经 Wallet 包装后供 Transaction 使用；具体 contract 和迁移由 MIG-05 冻结。 |
| Benefit、VCC、ACH、收单等场景对象、流程与外部 authority/finality | Host / Consumer / Adapter | 先归一为稳定资金指令或事实引用；不得以场景 facade、rail code 或状态机进入 Funds 公共契约。 |

对象级处置如下：

1. `PaymentInstrumentTransactionApplicationService` 的实现本来就在 Transaction，但接口和请求位于 `wallet-face`，仓内没有生产 Consumer。未来只有真实 Consumer 证明需要时，才一次性迁到 Transaction 契约；没有 Consumer 时收窄为内部编排或删除公开面，不保留 Wallet alias、bridge 或双 Bean。
2. `PaymentInstrumentCapabilityApplicationService`、预交易冻结 snapshot、责任解析与账户能力继续由 Wallet 持有；Transaction 只能消费其稳定准入结果，不能复制 Wallet 规则。
3. `SpendControlTransactionConsumptionApplicationService` 是 Transaction 对既有交易结果的协调逻辑，不是 Wallet 公共业务入口。未来在 Transaction 内聚编排，Wallet 只保留窄的 control movement 写入/查询；退款控制补偿仍需上游明确业务授权，不能由 Transaction 结果自动推断。
4. `LedgerQueryService` 及 Wallet 自有的 Ledger fact DTO 是重复 read adapter；`LedgerProfileService` 也是 Ledger 语义。二者目标 Owner 都是 Ledger，但当前 Transaction 不能直接依赖 `ledger-face`。物理引用解析遵循 9.8.5 已冻结的产品边界，不能预设必须新增窄读端口。
5. `FundsTransactionQueryService` 保持 Transaction 所有；公共 ActionFact 查询与内部聚合查询继续按既有边界分离，不迁给 Wallet。
6. Provider Benefit 场景 facade 在 MIG-04 阶段曾因 Consumer E4 未闭合而保留；`D-R8B-001` 已确认 `capte-domain` 作为无独立部署/数据库的通用模块，以唯一制品、真实 Bean、联合 schema/事务和跨进程恢复的 library test host E4 关闭本 Consumer 门槛。目标仍是 Capte adapter -> generic direct pay/refund + ActionFact，不泛化为新的场景引擎；未来部署宿主 L4 独立等待。

各原子组必须一次性无兼容迁移：支付工具交易 facade 与请求归属一起切；Spend control 协调入口与全部调用点一起切；Ledger wrapper/profile 连同全部调用点一起切；Benefit facade 按 `D-R8B-001` 迁到 Capte adapter 并删除 Provider 场景面。任何组都不设兼容桥、alias、双读、双写或过渡 Public API。

验收必须证明：旧 Wallet 交易 facade/read adapter 零生产引用；模块依赖守卫通过；支付工具 `authorize/complete/reversal（投影为 canonical release）/receive` 行为、责任 snapshot、原 route、Ledger/Balance 与幂等不变；Spend control movement 不重复且不制造额外资金/账务效果；原 LedgerTransaction 引用解析前后事实等价；timeout/restart 只按原 identity 恢复。PaymentInstrument 与其他未关闭 Consumer 仍按各自门禁阻断；Benefit 已进入独立 facade retirement，不再作为保留错误 Provider 归属的理由，也不外推全局 MIG-09。

### 9.8 `MIG-05` Ledger internalization 与交易投影产品边界

本卡此前冻结的稳定方向是：Ledger 事实仍由 Ledger 唯一写入和解释，Transaction 不直依赖 `ledger-face`，也不经 Wallet bridge。该方向不等于必须新增 `core` read port；9.8.5 基于当前源码重新比较最小物理承接。不新增投影表、异步读库、通用 CQRS 平台或第二事实源。

#### 9.8.0 最小能力地图

| 能力域 | 能力 Owner | 对外业务结果 | 能力边界 |
| --- | --- | --- | --- |
| 资金动作事实查询 | Transaction | 按稳定 identity 返回可机械证明的 ActionFact 或空/UNKNOWN。 | 不证明 Ledger、Balance、外部 finality 或 reconciliation。 |
| 账本写入与证据读取 | Ledger | 原子形成 posting/LedgerTransaction/Entry/Balance，并按 action 返回稳定 evidence。 | 不判断宿主业务结果，不让 Consumer 拼 posting。 |
| 账户与控制准入 | Wallet | 提供已冻结的账户、责任、PaymentInstrument 与 Spend control 准入事实。 | 不包装 Ledger，不创建 FundsTransaction。 |
| 场景与外部事实归一 | Host/Adapter | 将业务/rail 输入归一为稳定资金指令或事实引用。 | 不把场景状态、协议码或 finality 交给 Funds 推断。 |

#### 9.8.1 两类“投影”必须分开

1. `FundsActionFact` 是 Transaction 对自身唯一 durable action group 的版本化、机械可证、只读投影。它统一回答动作 identity、Money、领域结果、已证明资金效果、原事实与冻结 route provenance；可用于 timeout/restart 恢复、Consumer 解耦、审计和跨版本查询。它不证明 Ledger、Balance、外部 finality 或 reconciliation 已闭合。
2. Wallet `LedgerQueryService` 只是把 Ledger 查询和 DTO 再包装一层，既没有形成新的稳定事实，也没有新增权限、验真或聚合语义。它属于错误 Owner 的浅 read adapter，应在 MIG-05 原子切换后删除，不能升级为“交易投影平台”。
3. `FundsBalanceAdjustmentAuditApplicationService` 是一个 Transaction 侧组合审计读模型，当前没有生产 Consumer 证据。它可以在未来真实审计 Consumer 出现时组合 Transaction 与 Ledger 的只读证据，但不能反向要求保留通用 Wallet-Ledger wrapper；没有 Consumer 时应内部化或删除 Public 可见性。

#### 9.8.2 实际业务价值与使用场景

| 场景 | `FundsActionFact` 提供的价值 | 仍需独立证据 |
| --- | --- | --- |
| 授权调用 timeout、宿主重启 | 以同一 action identity 查询已成立/已证明零/UNKNOWN，避免换号补单和重复资金动作。 | Ledger 与 Balance 是否闭合分别查询，外部 issuer 结果由 adapter 持有。 |
| partial complete `30 + 50`、release `20` | 保留每个动作的 Money、原 authorization、逐原 route 与累计，不把父 root 状态冒充动作事实。 | 账务分录、余额桶和外部 clearing/finality。 |
| direct pay 后 recovery/refund | 明确引用哪个原资金事实、分配多少、沿哪条冻结 route 逆向，避免按当前账户或金额猜原交易。 | 退款资格、rail return、责任和损失由上游专业 Owner 决定。 |
| Consumer 展示与客服追查 | 用稳定公共事实解释“本次资金动作发生了什么”，不暴露 root/detail/Entity/Mapper。 | 订单状态、到账声明、对账关闭仍由各自 Owner 提供。 |
| 审计与对账取证 | 以 action identity 关联独立 LedgerFactRef，支持逐层核对和差异定位。 | ActionFact 不能代替 LedgerEntry、Balance projection 或 reconciliation result。 |

结论是“有价值，但必须克制”：只要投影仍是同一事实源上的确定性只读解释，并在证据不完整时返回空/UNKNOWN，它能显著降低 Consumer 对内部表和生命周期 root 的耦合；一旦让 projector 猜业务归属、退款分配、外部 finality，或让它成为第二写入事实源，价值就会反转为双真相和升级风险。

#### 9.8.3 行业校准与本项目取舍

- Stripe 将每笔余额变动记录为 `BalanceTransaction`，并通过 `source` 关联 Charge/Refund 等原对象；Payout 对账也要求从 payout 关联的 Balance Transactions 追到原对象。这支持“业务动作事实、余额运动事实、出款聚合分层并以稳定引用关联”，不支持把所有完成维度合成一个状态。来源：[Stripe Balance Transactions](https://docs.stripe.com/api/balance_transactions)、[Stripe payout reconciliation](https://docs.stripe.com/payouts/reconciliation)，核验日期 `2026-08-17`。
- Modern Treasury 的 Ledger Transaction 将 entries 作为原子、借贷平衡的不可变账本事实，posted 后不原地修改。这支持 Ledger 自己拥有 LedgerTransaction/Entry，Transaction 只消费稳定引用。来源：[Modern Treasury Ledger Transactions](https://docs.moderntreasury.com/ledgers/docs/ledger-transactions-overview)，核验日期 `2026-08-17`。
- Microsoft 的 CQRS 指南明确允许读写模型先共用同一数据存储；只有吞吐、查询复杂度或独立扩缩容确有需要时才拆读库，而分离存储会引入同步和最终一致性成本。Materialized View 也不适合源数据本就容易查询或强一致优先的场景。来源：[CQRS pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/cqrs)、[Materialized View pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/materialized-view)，核验日期 `2026-08-17`。

据此，本项目当前采用“同库、按需、source-owned read projection”：这里的“同库”指与宿主现有资金事实共用同一持久化/事务边界，不要求 `wind-funds` 拥有独立部署数据库。`FundsActionFact` 保持 Transaction-owned 公共只读投影；原 LedgerTransaction 引用优先从已经拥有它的事实 Owner 解析，Ledger 再验证自身事实，不建立异步物化视图。只有未来出现可量化的查询延迟、吞吐或隔离需求，并能证明重建、版本和一致性策略时，才重开独立读模型决策。

#### 9.8.4 产品停止线

- Transaction 不直接依赖 `ledger-face`，不经 Wallet bridge，也不接收 Ledger Entity/Mapper/分页查询对象。
- Ledger profile、posting plan、LedgerTransaction/Entry 与 Balance projection 继续由 Ledger 唯一拥有；Transaction 不选择 profile item 或 posting subject。
- 面向 Transaction 的原账本引用解析只回答自有 durable action group 是否持有唯一、完整的 `ledgerTransactionSn`；不提供自由分页、event string 搜索或通用报表查询。
- 当前不存在可直接复用的 `core` action-scoped Ledger read port，也没有证据证明必须新增；物理承接遵循 9.8.5 的已接受决策。
- Reconciliation 当前已有真实 Ledger face 读取并保留；Governance 当前没有 Java Consumer，只有无用途的 `ledger-face` POM 依赖。后者纳入未来原子迁移删除与依赖守卫，不作为保留或新增读契约的理由。
- 当前不新建表、缓存、事件流、读库、registry/factory 或第二 ActionFact 写链；性能问题在真实指标出现前不预解。

#### 9.8.5 `CI-MIG05-TRANSACTION-LEDGER-REFERENCE-001` 决策包

当前要解决的不是“如何搜索 Ledger”，而是 Transaction 在构造逆向指令时，如何取得原动作已经持久化的 `ledgerTransactionSn`。一手源码已证明 `FundsTransactionDetail` 保存该引用，Ledger posting 也会再次校验它与原资金交易、原 route leg 的一致性。因此不应先假定必须新增 action-scoped Ledger 搜索端口。

| 候选 | 实际做法 | 价值与代价 | 当前结论 |
| --- | --- | --- | --- |
| `A / TRANSACTION-FACT-RESOLVED-LEDGER-REF` | Transaction 从自己的 durable root/detail 中按 tenant、动作 event、成功结果与非空账本引用解析唯一 `ledgerTransactionSn`；Ledger 在逆向 posting 边界校验该引用。 | 不新增 core/face 端口、DTO 或搜索能力，Owner 边界最清晰；代价是 Transaction 必须对自己的事实组完整性 fail-closed。 | `ACCEPTED` |
| `B / CORE-ACTION-LEDGER-EVIDENCE-READER` | 新增 core internal read port，由 Ledger 按 funds action 搜索并返回稳定账本证据。 | 对未来多 Consumer 可复用，但当前只有两个承重逆向用例，且引用已存在 Transaction detail；会新增单实现端口和重复搜索语义。 | `NOT_SELECTED / NOT_FALLBACK` |
| `C / LEDGER-FACE-OR-WALLET-BRIDGE` | Transaction 直依赖 `ledger-face`，或继续通过 Wallet wrapper 查询。 | 改动看似小，但保留错误 Owner、宽查询和重复 DTO，违反当前模块依赖红线。 | `REJECTED / NOT_SELECTED / NOT_FALLBACK` |

三候选共同不变的产品合同是：先由原 root 的动作 event、冻结 route leg 和 participant 覆盖选出目标事实组，再要求组内全部 detail 同 tenant、结果已证明且 distinct 非空 `ledgerTransactionSn` 恰为 1；缺失、多命中、异租户或事实与冻结 route 不一致时停止，不取第一条、不换 identity 重做、不创建新资金或账务效果。普通 referenced refund 只选择 `PAY` 的非 `FEE` 回放 leg；独立费用退回选择 `FEE_CHARGE` 的唯一 `FEE` leg；带费 `PAY` 的费用退回选择同一 `PAY` route 中的唯一 `FEE` leg，并要求其目标存在 `FEE_RECEIVER`。合法 payer、payee、fee siblings 本来可以主体不同、金额不同，这不构成冲突；只有 detail 无法与对应 route participant/leg 对齐，或同一完整动作组出现空白/不同账本引用，才 fail-closed。`FundsBalanceAdjustmentAuditApplicationService` 当前只有测试 Consumer，不得用它证成新的通用账本读能力；无真实 Consumer 时优先删除或内部化。Ledger profile 归属另拆 `MIG-05B` 文档卡，本题不同时决定建账/profile/posting admission。

Human Owner 已选择 A。该选择直接复用 Transaction 已持有的原动作引用，消除 Wallet bridge 与跨模块宽查询的长期依赖，同时保持 Ledger 对 transaction/plan/entry/route 的独立复验；它能支撑 ordinary refund、standalone fee refund、embedded fee refund 和 authorization 后继动作的原引用解析。它不是新的查询平台，不证明 Ledger/Balance 完成，也不替上游补造缺失的业务原事实。解析与校验属于 Transaction Application/Service 用例边界，converter 只做映射。

#### 9.8.6 `CI-MIG05B-LEDGER-PROFILE-OWNERSHIP-001` 决策包

本题只解决“谁拥有 Ledger profile 定义、谁在账户创建时确保必需账本、Transaction 如何停止读取 profile 配置”，不重裁账户身份、route、posting、Ledger/Balance 完成或 MIG-09。

稳定产品合同如下：

1. `LedgerProfileCode` 是账户创建时冻结的稳定账务模板引用，也是唯一保留的 Public profile 概念；现有 `LedgerProfileSpec`、`LedgerProfileItemSpec` 及其 API baseline 是错误公开面，必须在无兼容迁移中删除。profile catalog/item、账目、normal side、period、allowNegative、settlement policy 和版本定义只归 `ledger-impl` 内部 Ledger Owner。
2. Wallet 只在 Funding/Credit 账户创建事务中提交已经准入的 tenant、subject identity/type、currency、profile code 和 period；它不读取或解释 profile items，也不决定账目和 posting。
3. Transaction settlement 不依赖 `ledger-face`，不读取 profile DTO，也不在交易路径自动建账；Ledger 初始化与 posting/admission 必须共用同一个按 `profileCode + version` 选择的内部 catalog integrity guard，逐 bucket 复验 subject、currency、category、normal side、allowNegative、effective period、settlement policy 和 cutoff。缺失、多命中或任一漂移均 fail-closed。
4. `capte-domain` 生产代码只把 `LedgerProfileCode` 当账户事实使用；当前两个测试宿主显式装配 Wallet profile/initializer 实现，只构成未来测试装配迁移，不证明宿主需要 profile 查询 Public API。
5. 受控初始化是一个原子命令：同一物理 bucket key 下的同 profile/version/catalog 语义并发只能创建一次并回读同一组 ledger identities；同一 key 下 profile/version 或 catalog bucket 语义不一致时只能一方成为 winner，另一方稳定冲突。不同 subject、currency 或 effective period 属于不同物理 bucket，应各自成功；任一 required bucket 失败时，本次新建账户和本次创建的全部 ledgers 一起回滚，不留下半套账本。

同构候选只改变最小物理 surface：

- **A `LEDGER-SERVICE-CONTROLLED-INITIALIZATION`（已接受）**：复用现有 `ledger-face.LedgerService` 承接“按 profile 确保必需账本”的受控命令；profile catalog 留在 `ledger-impl` 内部。Wallet 账户创建只提交命令，Transaction 删除 profile 预检查。该方案不新增单实现 Service，不公开 profile DTO。
- **B `DEDICATED-LEDGER-SUBJECT-ADMISSION-SERVICE`（未选择，非 fallback）**：在 `ledger-face` 新增独立 subject admission service。边界正确，但当前只有 Wallet 两个账户创建调用，现有 `LedgerService` 已拥有 create/query ledger 能力，暂无不可替代的独立 Public surface 证据。
- **C `MOVE-PROFILE-READ-SURFACE-AS-IS`（拒绝，非 fallback）**：把 `LedgerProfileService` 和 profile DTO 原样搬到 `ledger-face`。它会把内部账目配置暴露给调用方，并诱导 Transaction 直接依赖 Ledger face，保留错误的预检查与重复决策。

实际价值是让“账户是什么”与“该账户必须有哪些账本”分开：Wallet 写账户主数据，Ledger 以版本化 profile 创建并复验账本，Transaction 只提交资金动作。这样可删除 Wallet 错 Owner 的五个 profile/initializer Public 类型、两个 core profile spec 及两个实现，避免 profile 配置成为跨模块策略 API，同时保留 Funding/Credit 开户和 capte-domain 账户使用能力。

Human Owner 已选择 A，接受范围仅为 `LEDGER-SERVICE-CONTROLLED-INITIALIZATION` 及本节五项共同合同；B/C 未选择且不是 fallback。

#### 9.8.7 外部资金腿记账方向

历史实现曾把所有 route leg 都按“source 减少、target 增加”解释，导致 `EXTERNAL_IN` 的平台现金资产与用户负债同时增加时 posting plan 不平衡。根因不是 profile 或测试环境，而是把经济路径端点误当成统一余额方向。Route 的 source/target 只描述价值从哪里进入、到哪里离开；余额如何变化由稳定 leg kind、Ledger normal side 和原 posting 证据共同决定。

| 资金腿 | source 余额效果 | target 余额效果 | 业务例子 |
| --- | --- | --- | --- |
| `EXTERNAL_IN` | `INCREASE` | `INCREASE` | 外部入金 100：平台 `CASH +100`、客户 `PREPAYMENT +100` |
| `EXTERNAL_OUT` | `DECREASE` | `DECREASE` | 对外出款 100：客户结算负债减少、平台 `CASH -100` |
| 内部 `INTERNAL_TRANSFER/HOLD/RELEASE/CONSUME` | `DECREASE` | `INCREASE` | 同一资金体系内从一个 bucket 转入另一个 bucket |
| ordinary `RESTORE/RELEASE`，无 `replayRefLegId` | `DECREASE` | `INCREASE` | standalone refund、`PAYOUT_FAILED` 等按当前稳定路径回退 |
| reverse-class refund/reversal/release replay，具有非空且唯一 `replayRefLegId` | 原 posting 的逐 entry 精确反向 | 原 posting 的逐 entry 精确反向 | 不按当前事件名或 `RESTORE` 猜方向；authorization completion 不属于反向 |
| `ADJUST/LIMIT_ADJUST` | 使用指令已冻结的显式 effect | 使用指令已冻结的显式 effect | 不并入外部资金腿通用规则 |

组合后仍只表达真实净额：充值 100 先形成 `CASH +100 / PREPAYMENT +100`，再形成 `PREPAYMENT -100 / AVAILABLE +100`，最终净额为 `CASH +100 / AVAILABLE +100`；出款则先把客户责任移入待出款责任，再以 `EXTERNAL_OUT` 同时减少该责任和 `CASH` 资产。中间 `PREPAYMENT` 只承接边界，不凭空创造资金。

这是跨 topup、ACH/card/VCC 入金、payout 与退款/冲正稳定复用的公共资金不变量。上游或 rail adapter 仍负责外部事件验真、authority、finality 和业务策略；`wind-funds` 只消费已归一的 route leg，并由 Ledger 生成平衡、可追溯的 posting。该能力不新增 Public API、DTO、schema、策略引擎、兼容层、V2、双写或 fallback。

#### 9.8.8 `FUNDING_BALANCE_ADJUST` 有符号暂挂余额

Human Owner 接受方案 A：平台 `ADJUSTMENT` 是 debit-normal、允许负余额的有符号暂挂余额，不是“本期调账金额”或永远为正的审计指标。资金账户余额调增时，目标 `AVAILABLE` 与平台 `ADJUSTMENT` 都增加；调减时两者都减少。Ledger 再按各账目的 normal side 把同一显式 effect 转为一借一贷：调增为平台 `ADJUSTMENT DEBIT`、目标 `AVAILABLE CREDIT`，调减为目标 `AVAILABLE DEBIT`、平台 `ADJUSTMENT CREDIT`。若业务需要展示正数形式的调增/扣回金额，应从不可变调账事实生成只读指标，不得改变账本余额符号。

| 实际场景 | 公共能力结果 | 不由本能力回答 |
| --- | --- | --- |
| 客服、运营或财务修正同主体资金余额 | 按审批、凭证和来源形成独立调账事实；平衡入账；同 identity 重放不重复 | 业务订单是否应补偿、审批是否合规 |
| 佣金清算后确认原分配需扣回 | 追加 `AVAILABLE -X / ADJUSTMENT -X`，原佣金、清算、route、posting 与 entry 不改写 | 佣金规则、合同责任和税务处理 |
| 发卡行、处理商或外部余额系统已有终局差错事实 | 消费上游已归一的终局事件、余额快照、责任、审批、凭证和重新对账引用，修正同主体余额 | 外部协议 finality、责任裁决或 rail 状态映射 |

该能力的公共边界是“同主体、同币种、同账本周期、明确来源的受控资金余额更正”，不是任意 `setBalance`。退款、赔付、手续费、商户转账、跨主体补偿、跨币种调整、信用额度和预算控制不得借此入口实现；前四类走明确资金交易或清结算事实，信用额度继续走 `LIMIT_ADJUST`，预算控制只改控制视图。

该产品合同不新增通用策略引擎或并行资金语义，不声明会计、合规或生产普适性。

#### 9.8.9 余额调账非负 Public contract

**Owner 决策**：Human Owner 接受 A“无兼容删除负余额 Public 输入”。当前没有生产 Consumer，也没有 `capte-domain` 调用或行为测试证明 Consumer 可以权威签发负余额策略、单笔/累计额度和风险状态；现实现只验证这些自报字段存在、金额为正且币种一致，并未执行额度或验证 authority。该能力不满足公共资金能力的真实复用与可验证准入条件。

目标 Public 合同只保留“同主体、同币种、明确来源、默认非负”的余额更正。`FundsBalanceAdjustRequest` 删除以下 `6` 个字段：`allowNegativeBalance`、`negativeAvailablePolicyCode`、`negativeAvailableRiskStatus`、`negativeAvailableSingleLimit`、`negativeAvailableCumulativeLimit`、`negativeAvailableAgingStartedAt`。`adjustReason`、`adjustEvidenceRef`、`approvalRef`、来源事实、责任和对账引用继续保留；它们证明审计与来源关联，不代表 Provider 替上游审批或定责。

本卡不改变 signed `ADJUSTMENT`：调增继续形成 `ADJUSTMENT DEBIT / AVAILABLE CREDIT`，调减继续形成 `AVAILABLE DEBIT / ADJUSTMENT CREDIT`。普通 `BALANCE_ADJUST` 与 `LIMIT_ADJUST` 调减统一不得令目标 normal balance 小于零。Ledger 内部 `allowNegative`、profile/catalog integrity 和 `LedgerBalanceConstraintType.ALLOW_NEGATIVE` 继续作为 Ledger 内部能力保留，但不得再由余额调账 Public Request 或任意 `contextVariables` 选择。

该选择直接采用 breaking removal，不保留 deprecated 字段、alias、兼容 setter、V2 Request、raw context fallback、bridge 或双入口。若未来真实 Consumer 确需负余额，必须带来可查询的 authority、额度窗口、并发累计、撤销/到期和恢复证据，重新进入独立 Contract Inquiry；不得自动恢复本轮删除字段，也不得在 Funds 内建设审批、风险或通用策略引擎。

该合同必须同时拒绝通过 `contextVariables` 偷运已删除的负余额策略，且不因未来真实 Consumer 出现而自动恢复旧字段；新的 authority、额度窗口、累计、撤销和恢复合同必须重新接受。

### 9.9 `MIG-07` Reconciliation 与 Stage 产品合同

#### 9.9.1 产品结论与实际价值

MIG-07 选择 `CORE_FIRST / STAGE_BOUNDARY_ONLY`：完整设计可跨场景复用的对账事实、严格核对、差异和 Gate，只冻结 Stage 消费 Gate 的交接边界，不在本卡重做 clearing、settlement、payout 或 recovery 生命周期。

这项能力解决的不是“把两份文件对上”，而是四个长期问题：

1. 把不同业务系统、API、query、report、event、statement 或人工证据先归一为稳定来源快照，载体改变不改变经济事实身份。
2. 由 Reconciliation 自己证明本次范围是否完整、两侧是否唯一命中且语义严格相等，不再信任调用方提交的 `EXACT_MATCH`、`RULE_MATCH` 或 `trusted=true`。
3. 把不匹配、责任处置和资金修复分开。发现 Difference 不等于已定责，更不等于自动调账、退款、追偿或损失。
4. 让 clearing/settlement/payout 等 Stage 在真正执行前，机械确认所有必需对账维度仍是 current-lineage 且无阻断，而不是复用一张过期的 PASS 凭证。

直接业务价值如下：

| 场景 | 本能力给出的稳定结果 | 不由本能力回答 |
| --- | --- | --- |
| 平台交易与内部 Ledger 核对 | 指定 tenant/scope/window 下，每个 comparison identity 是否唯一、同币 Money 与 normalized status 严格相等。 | 订单是否履约、客户是否满意。 |
| 内部 payout 与银行/执行方结果核对 | 区分执行结果、银行到账证据、缺失/冲突，并形成 current run 与 Difference。 | beneficiary finality、rail 法律终局。 |
| 费用、税项、FX 差额核对 | principal、fee、tax、FX shortfall 各自作为独立 comparison fact 核对；其 `claim kind + economic component + direction` 必须逐项一致。 | 费用或损失最终由谁承担。 |
| Stage 放行 | 按 Stage Owner 冻结的 `GateRequirement` 合取多个必需 pair 的 current run，给出本次可执行/阻断证据。 | 自动发起资金修复，或把 Gate PASS 当成全局成功。 |
| 人工修正 | 有权 Owner 追加 correction/aggregation/writeoff/decision evidence，来源侧形成新快照并触发新 run。 | 直接修改旧 MatchResult、人工把 run 改成 Balanced。 |

#### 9.9.2 来源是能力抽象，不是文件抽象

Source Owner/Adapter 负责 raw source 的认证、authority、scope，并按已签收 pair comparison rule 输出不可变 `ReconciliationSourceSnapshot`。文件只是 carrier 之一；API、query、report、event、statement 和受控人工证据都可以形成同一抽象。Pair Comparison Rule Owner 负责签收两侧 source role/namespace、Owner-local DomainOutcome 到 `ComparisonStatus` 的映射、`claim kind + economic component + direction`、scope、effective period 和 rule reference/version；两侧 Adapter 不能各自定义同名状态。Reconciliation 不按 carrier 分支，也不解析 raw rail/business status，只校验调用权限、tenant/scope、source type、共同 rule reference/version、字段完整性和 evidence refs。

每个 snapshot 必须冻结：tenant/object/account scope、时间范围与时间语义、timezone、currency、source version、共同 comparison rule reference/version、snapshot version、成员数量与 digest、coverage/watermark 和 evidence refs。coverage 或 watermark 不完整时，本次 run 不能 Balanced。

Snapshot 内的 `NormalizedComparisonFact` 至少表达稳定 source fact identity、comparison identity、Money、规则范围内的 `ComparisonStatus`、结构性 `comparisonProven`、`claim kind + economic component + direction`、共同 comparison rule reference/version、semantic digest 与 evidence refs。原始 `DomainOutcome` 只在各自 Owner 契约内解释；只有上游能按同一已签收 pair rule 唯一、明确映射时，才可给出 `comparisonProven=true`，UNKNOWN、缺映射或多映射均不可比较。

#### 9.9.3 首包匹配、Difference 与 Gate

- 首包只支持 normalized `1:1 strict exact`：两侧均 `comparisonProven=true`，且同 tenant/scope/comparison identity、同币 Money、同 `claim kind + economic component + direction`、引用同一有效 pair comparison rule、comparison status 相同，两侧各恰好一条。双侧 UNKNOWN 即使 code 相同也不可比较；零命中是 missing，多命中或同 identity 异语义是 conflict；禁止 first/latest/closest wins。
- `1:N/N:1` 只能由来源 Owner 先形成不可变 aggregate fact，并冻结 member count、member digest 和来源证据，再作为一个 comparison fact 进入 `1:1`。本项目不建设通用聚合、容差、netting、FX 或规则路由引擎。
- 每个 mismatch/missing/conflict 都耐久保存 MatchResult。只有需要跟踪、分派、阻断或受控处置时才创建 Difference Case；没有 Case 不能隐藏 run 的不平衡结果。
- Difference 创建时责任中立。只有后续 liability/fee/loss/recovery evidence 才能分别形成专业责任和资金动作。`RESOLVED` 需要受控 action evidence 加后继 current-lineage Balanced run；`INVALIDATED` 仅限来源或匹配证据被正式 supersede。
- Stage Owner 提供不可变、版本化 `GateRequirement`，列明 exact stage identity、scope/rule version、全部必需 pair/source roles 与 evidence refs。首包固定为所有 required pair 必须 current、Completed、Balanced 且零 blocker，不提供开放式 blocking policy 或可选 pair。每个 exact stage identity 同一时刻只能有一个 current/effective requirement head；Gate 按 stage binding 自动解析该 head，调用方不能选旧版本或漏掉不利 pair。普通 Gate query 只展示；Stage 执行必须在自己的本地事务内重新锁定 requirement head、current lineages、blockers 与 stage state，再与 stage state/资金动作原子提交，并保存本次消费的 gate evidence/digest。

`Matched/Balanced/Gate PASS` 只证明本次对账维度，不证明 capture、settlement、payout、beneficiary arrival、rail finality、Ledger/Balance 或全局业务完成。Gate 本身零资金、零账务、零 Stage 副作用。

#### 9.9.4 身份、重放与不可变证据

- delivery identity、source fact identity 和 comparison identity 三者分离。
- source fact identity 在 tenant/scope/source namespace 内唯一；同 identity + semantic digest 重放复用，同 identity 异 Money/status/comparison semantics/rule reference/digest 进入 conflict。
- `semanticDigest` 覆盖归一后的 source namespace/identity、Money、ComparisonStatus、`claim kind + economic component + direction`、共同 comparison rule reference/version 和归一语义版本；`evidenceBundleDigest` 覆盖 delivery/report/query/file 等证据关联。相同经济事实经不同 carrier 到达时复用 normalized fact，只追加 evidence association，不改写事实。
- 同 scope/snapshot/rule/digest 重放同一 run；scope、snapshot、rule、coverage 或 digest 任一变化均创建新 run 和新 current lineage。旧 run/result/difference/action 永久只读。
- manual 不能覆盖旧事实。它只能形成可审计的新 evidence，由来源侧产出新 normalized fact，再启动新 run。

#### 9.9.5 行业校准、现状差距与停止线

Stripe 的 reporting/payout reconciliation 以不可变 Balance Transaction 和稳定 source 关联支持逐项追溯；Adyen 同时提供 transaction-level 与 batch-level settlement report，体现载体/粒度可变但核对事实需稳定；Modern Treasury 将 reconciliation rule 与人工匹配证据显式化，并保持 Ledger Transaction posted 后不可变。这些实践支持“来源抽象、不可变事实、版本化规则和差异追加”，但其厂商对象、rule engine 与状态名不进入本项目 DSL。来源：[Stripe reporting and reconciliation](https://docs.stripe.com/plan-integration/get-started/reporting-reconciliation)、[Stripe payout reconciliation](https://docs.stripe.com/payouts/reconciliation)、[Adyen settlement reports](https://docs.adyen.com/reporting/settlement-reconciliation/transaction-level/settlement-details-report/)、[Modern Treasury reconciliation rules](https://docs.moderntreasury.com/payments/docs/defining-reconciliation-rules)，核验日期 `2026-08-17`。

外部参考证据卡：

- 规则来源：Stripe、Adyen、Modern Treasury 官方在线文档，仅作行业架构校准。
- 版本或发布日期：在线文档访问快照 `2026-08-17`；未取得 provider contract/API pinned version。
- 适用范围：source abstraction、immutable facts、rule/evidence separation 与 reconciliation layering；不适用于本项目 runtime status mapping、法域、资金责任或 finality。
- 核验日期：2026-08-17
- 确认方：Reconciliation Product Owner 与 System Architecture Owner 仅确认设计参考用途；真实 provider/rail 规则仍由 Host/Adapter Owner 签收。

当前 Provider 已按冻结的两侧 normalized facts 执行 strict-exact，比较 Money、comparison status、claim semantics、rule、identity 和 coverage，并由系统固化有限结果 kind、run、Difference 与 versioned GateRequirement；真实 source authority/adapter、宿主 Consumer、重启恢复与 E4 仍未闭合。该实现证明 Provider 计算职责已落地，不等于真实来源和生产能力已可用。

该产品合同不保留旧 caller-trusted path，也不建立 bridge、alias、双 DTO、双读/双写、V2 平行入口或 carrier-specific flow。具体物理切换、验证和执行状态统一见 OpenSpec、系分与 TDD。
