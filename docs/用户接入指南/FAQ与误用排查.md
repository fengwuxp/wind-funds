# wind-funds FAQ 与误用排查

## 1. 文档定位

本文面向第一次接入 wind-funds 的产品、业务、研发、测试、运营、财务、风控、安全和合规评审方，回答常见概念问题，并列出容易导致资金风险或评审阻断的误用方式。

本文不是 API 手册，也不是合规、会计、税务或上线批准。真实资金处理仍必须回到 PRD、DSL、系分、TDD、接入评审清单和 Execution Grant。

## 2. 业务目标和非目标

| 项 | 说明 |
| --- | --- |
| 业务目标 | 降低接入方理解资金底座的门槛，提前识别概念混用、流程断点、资金安全红线和生产准入缺口。 |
| 用户价值 | 产品能判断边界，研发能判断接口和契约，测试能判断验收，运营财务能判断差错和审计，风控安全能判断外部规则和敏感数据。 |
| 非目标 | 不定义新能力，不新增公共契约，不替代接入申请，不替代专业确认，不承诺生产可用。 |
| 成功指标 | 接入方能在提交评审前自查：该不该接、接哪层能力、是否需要专项准入、哪些情况必须阻断。 |

## 3. 能力地图

| 能力域 | 常见问题 | 正确理解 | 易错风险 |
| --- | --- | --- | --- |
| 钱包账户和内部主体能力 | 钱包是不是支付工具。 | 钱包账户域管理 FundingAccount、CreditAccount、BudgetGroup、平台账户角色、支付工具绑定和余额查询；支付工具只是路由和外部引用。 | 把卡、VA、银行账户、钱包标识或 token 当账本主体。 |
| 支付工具 | 外部账户能不能入账。 | 外部账户只能做脱敏引用、工具或 route 输入。 | 外部账户直接成为 ledger subject。 |
| VCC 预付卡和共享卡 | 预付卡或共享卡是不是账户。 | VCC 卡、prepaid virtual card 和 shared card 都先是 PaymentInstrument；预付资金责任、授信额度、预算约束或资金来源另行解析到内部主体。 | 因 prepaid/shared 名称自动创建 FundingAccount、CreditAccount、BudgetGroup 或账本主体。 |
| 直接交易 | capture 成功是不是商户可提现。 | capture 只表示收款资金事实成立，仍需清分、清算、结算和出款门禁。 | 把待清分或待清算展示成可提现。 |
| 授权交易 | 授权成功是不是消费完成。 | 授权成功只是占用；完成、撤销、过期、退款和拒付必须按原事实链路处理。 | 授权拒绝生成 route 或 ledger entry。 |
| 余额控制 | 冻结是不是扣款。 | 冻结只做同主体 AVAILABLE 与 FROZEN 控制。 | 把冻结当消费、扣划或跨主体转移。 |
| 对账清结算 | 对账差错能不能直接改账。 | 差错必须通过差错单、审批、补事实、冲正、追偿、核销和重新对账闭环。 | 后台直接改历史分录、余额或投影。 |
| 归档重放 | 重放能不能补资金事实。 | 重放只能重建投影或输出差异报告。 | 用重放生成 route、posting 或 ledger entry。 |
| P2 业务能力包 | ACH、VCC、收单能不能直接做进底座。 | 上层业务先归一外部事件，wind-funds 只承接标准资金事实和底座能力。 | 把外部协议全集、风控模型或 KYC/KYB 沉入资金内核。 |

## 4. 对象模型、字段口径和生命周期

| 对象 | 字段口径 | 生命周期 | 状态 | 不变量 |
| --- | --- | --- | --- | --- |
| 资金事实 | businessSn、idempotencyKey、requestDigest、amount、currency、subject、reference。 | 上层归一 -> 准入 -> route -> posting -> ledger entry -> projection -> 审计。 | 已接收、准入失败、处理中、成功、失败、待人工。 | 同键同摘要复用，同键不同摘要阻断，失败无错误资金副作用。 |
| FundingAccount | subject、accountType、currency、ledgerProfile、balanceBucket。 | 显式建账 -> 绑定工具或资金来源 -> 交易使用 -> 查询和审计。 | 可用、冻结、禁用、关闭、待确认。 | 不表达信用、预算、支付工具或外部账户本身。 |
| CreditAccount | creditOwner、limit、available、authorization、ruleVersion。 | 显式建账 -> 设额 -> 授权占用 -> 撤销/释放/调额 -> 查询和审计。 | 可用、冻结、禁用、关闭、待确认。 | 不表达现金余额、商户待结算或共享卡本体。 |
| BudgetGroup | budgetOwner、period、limit、available、authorization、ruleVersion。 | 创建预算 -> 配置周期 -> 授权占用 -> 撤销/释放/调额 -> 查询和审计。 | 可用、冻结、过期、关闭、待确认。 | 不表达真实资金池、信用授信责任或支付工具本身。 |
| PaymentInstrument | instrumentType、externalReference、maskedValue、bindingSubject。 | 创建 -> 绑定 -> 换绑 -> 历史快照 -> route 输入。 | 可用、解绑、过期、禁用。 | 只做引用和 route 输入，不表达余额。 |
| RouteSnapshot | routeCode、leg、source、destination、ruleVersion。 | 正向生成 -> 后续事件引用 -> 回放或审计。 | 有效、已引用、缺失、待人工补证据。 | 退款、撤销、拒付、退费和解冻等后续事件不得重新选路兜底。 |
| LedgerEntry | ledgerTransactionSn、subject、account、bucket、direction、amount、period。 | 由 posting 生成 -> 余额投影消费 -> 对账和审计。 | 已写入、冲正引用、差错引用。 | 余额事实源，不允许业务方直接改。 |
| Projection | sourceFact、projectionType、balance、status、watermark。 | 从事实派生 -> 查询展示 -> 可重建。 | 正常、延迟、待重放、差异。 | 只读派生，不反写交易事实或账本事实。 |

## 4.1 核心决策、接口契约和数据一致性

| 维度 | FAQ 口径 | 误用风险 |
| --- | --- | --- |
| 核心决策 | 接入优先依赖 `core`、`*-face`、Request、Query、DTO、Spec 和枚举，业务能力包不反向污染统一资金内核。 | 业务方直接依赖 impl、Entity、Mapper 或内部状态机。 |
| 职责边界 | wind-funds 承接资金事实、账户、路由、账务、投影、对账清结算和治理边界，不承接外部协议全集、业务审批和风控最终判断。 | 把通道、风控、KYC/KYB 或外部规则塞进资金底座。 |
| 接口契约 | 入参必须表达业务流水、幂等键、请求摘要、主体、金额、币种、来源引用和操作者；出参必须能解释状态、失败原因和审计引用。 | 公共契约只服务日志排查，不能服务使用者解释和测试验收。 |
| 错误码 | 错误必须区分准入失败、幂等冲突、路由失败、账务失败、投影失败、外部非终态和对账差错。 | 把资金失败压成通用系统异常。 |
| 幂等 | 同键同摘要复用，同键不同摘要失败。 | 重试换键导致重复入账。 |
| 数据方案 | 余额来自 ledger entry 和投影，报表、日志、运营备注和外部文件只能做证据或只读输入。 | 报表或日志反向修余额。 |
| 事务边界 | route、posting、ledger entry 和交易事实必须在设计中说明一致性边界。 | 半截入账、重复入账或失败后留下成功事实。 |
| 补偿和对账 | 差错通过补事实、冲正、调账、追偿、核销和重新对账闭环。 | 对账差错直接改历史分录。 |
| 验证方案 | 测试必须覆盖状态、金额、账户类型、`normalBalanceSide`、route、posting、entry、projection、借贷平衡、余额影响、幂等、审计、失败无副作用和回归范围。 | 只用接口联调成功作为验收。 |

## 4.2 借贷平衡和 DSL 权威表 FAQ

| 问题 | 答案 | 评审动作 |
| --- | --- | --- |
| 接入方只写“账务影响：扣用户、加商户”可以吗。 | 不够。必须回挂 DSL 资金场景借贷平衡与账务期望表，说明命中行、不适用行、账户类型、`normalBalanceSide`、借贷平衡和余额影响。 | 退回补资金事实说明卡和接入申请。 |
| 借方是不是一定等于付款方，贷方是不是一定等于收款方。 | 不是。借贷方向是 `EntrySide` 和账户 normal balance 的组合，不是简单来源方和目标方语义。 | 按 DSL 权威表和账本配置确认，不现场口头推导。 |
| `LedgerEntry.amount` 能不能用负数表达扣减。 | 不应这样表达。金额保持非负，余额增减由 entry side、账户类型和 `normalBalanceSide` 推导。 | 检查测试断言是否覆盖余额影响，而不是只看 entry 数量。 |
| 一个接入场景可以复用相邻场景行吗。 | 可以引用相邻场景作对照，但必须说明本场景命中哪些行、哪些行不适用。 | 在资金不变量和借贷平衡引用中填写不适用行及原因。 |
| 失败路径要不要填借贷表。 | 要填 forbidden facts。准入失败、幂等冲突、路由失败、账务失败、外部规则未确认等都必须证明无 route、posting、ledger entry 或余额副作用。 | TDD must-fail 需要覆盖失败无副作用。 |

## 5. 业务流程和状态机 FAQ

| 问题 | 答案 | 评审动作 |
| --- | --- | --- |
| 业务还在审批中，可以先进 wind-funds 占个状态吗。 | 不可以。审批中不是已成立资金事实，应留在业务系统。 | 阻断接入，等审批形成确定资金事实。 |
| 通道返回 accepted，可以展示出款成功吗。 | 不可以。accepted 不是终态成功，必须等待外部终态、对账或人工确认。 | 展示处理中或待确认。 |
| 退款时用户已经换绑卡了，能按新卡路由吗。 | 不能默认按新卡路由。退款、拒付、退费等后续事件应引用原 route snapshot。 | 检查原 route snapshot 和缺失处理。 |
| 授权拒绝后要不要记录账务。 | 不应生成 route、posting 或 ledger entry；可保留请求审计和拒绝原因。 | 测试 must-fail：授权拒绝无资金副作用。 |
| 冻结后确认提现，能不能把冻结单状态改成扣款。 | 不建议。冻结是控制事实，扣划或出款确认应形成独立资金事实并引用原冻结单。 | 检查原冻结单引用和出款结果终态。 |
| VCC 预付卡是不是 FundingAccount。 | 不是。prepaid virtual card 是卡产品资金模式，卡本体仍是 PaymentInstrument；只有经财务、合同或合规确认的预付资金责任主体才可能解析为 FundingAccount、平台责任账户、预收待付或权益责任。 | 检查工具注册、预付资金来源、财务确认引用和 `TDD-WALLET-015`。 |
| 共享卡是不是 CreditAccount。 | 不是。shared card 是使用和绑定模式，信用额度、预算约束或资金来源要通过 CreditAccount、BudgetGroup、FundingAccount 或平台账户角色分别表达。 | 检查绑定版本、预算组、资金来源关系、唯一 FundingAllocationDecision 和 `TDD-WALLET-016`。 |
| 能不能按卡产品形态自动创建账户。 | 不能。账户类型只能按真实资金、授信额度、预算控制或支付工具四类需求选择。 | 检查内部能力选择结论和 `TDD-WALLET-017`。 |
| 对账差错发现少记了一笔，能不能直接补一条分录。 | 不能绕过白名单和审批。应生成差错单，走补事实、冲正、调账、追偿或核销流程。 | 检查处理单、审批、证据和重新对账。 |
| 归档后发现投影不一致，重放能不能修账。 | 不能。重放只能重建投影或输出差异报告，不生成资金事实。 | 检查 Manifest、checkpoint、watermark 和差异报告。 |

## 6. 规则矩阵和误用排查

| 规则对象 | 触发条件 | 正确判断逻辑 | 优先级 | 误用信号 |
| --- | --- | --- | --- | --- |
| 幂等规则 | 重复提交、重试、回调重复。 | 同键同摘要复用结果；同键不同摘要失败。 | P0 | 为了重试换幂等键，导致重复入账。 |
| 主体规则 | 用户、商户、平台、支付工具或外部账户参与资金变化。 | 先解析可记账主体，只读引用不得入账。 | P0 | 外部账户、业务订单、卡 token 直接入账。 |
| 金额规则 | 金额、手续费、补贴、税费、FX、权益参与计算。 | 金额为正、币种一致、组件闭合、累计不超剩余金额。 | P0 | 手续费和商户应收净额混记，退款分摊不可解释。 |
| 路由规则 | 正向交易、退款、撤销、拒付、出款或补事实。 | 正向可选当前 route；逆向必须引用原 route snapshot。 | P0 | 逆向事件按当前绑定重新选路。 |
| 账务规则 | route 转 posting 和 ledger entry。 | 借贷口径回挂 DSL 权威表，posting plan 独立平衡，entry 主体、账目、周期、方向和金额正确。 | P0 | 只看交易成功，不看账户类型、`normalBalanceSide`、余额桶和分录平衡。 |
| 运营规则 | 差错、调账、追偿、出款失败、归档异常。 | 必须有处理单、审批、凭证、白名单命令和重新对账。 | P0 | 后台直接改余额或改历史分录。 |
| 外部规则 | 卡组织、ACH、银行、PSP、跨境、税务、会计或合规。 | 未确认来源、版本、生效日期、适用范围、核验日期和确认方时阻断自动处理。 | P0 | 用“通道说可以”替代规则核验。 |

## 7. 运营、数据和审计 FAQ

| 问题 | 正确口径 | 验收证据 |
| --- | --- | --- |
| 运营需要看到什么。 | 至少能看到业务流水、外部 reference、transactionSn、route snapshot、ledger entry、投影状态、处理单和审计。 | 运营时间线和排障上下文。 |
| 财务需要看到什么。 | 账本交易、分录、清结算批次、差错核销、手续费、补贴、税费和报表输入口径。 | 账务证据和报表输入说明。 |
| 风控和安全需要看到什么。 | 冻结、解冻、争议、拒付、敏感数据、规则版本、操作者、审批和异常告警。 | 权限、脱敏、规则核验和审计证据。 |
| 报表能不能修正余额。 | 不能。报表只能消费资金事实或只读投影。 | 报表只读边界和数据来源说明。 |
| 日志能不能保存完整外部凭证。 | 不能。只能保存摘要、脱敏值、文件编号或外部 reference。 | 日志脱敏和证据最小化说明。 |

## 8. 阻断清单

| 阻断项 | 为什么阻断 | 回到哪里补 |
| --- | --- | --- |
| 谁的钱、当前归属、最终归属说不清。 | 资金主体不清会导致误扣、误付、误结算。 | 产品设计和资金事实说明卡。 |
| 外部账户、支付工具或业务订单直接入账。 | 账本主体错误会破坏资金事实源。 | 概念映射和账户建模。 |
| VCC 预付卡、共享卡、卡组或持卡人被自动建成资金账户、信用账户或预算组。 | 工具层和内部责任主体混用会导致余额、额度、预算和历史回放不可解释。 | 内部能力选择、支付工具绑定、资金来源关系和 VCC 分册。 |
| 外部非终态被展示为成功。 | 用户、商户和财务看到错误资金状态。 | 展示状态和外部结果处理。 |
| 授权、冻结、清算、结算、出款状态混用。 | 不同资金语义被混成同一种成功。 | 状态机和使用者解释视图。 |
| 对账差错直接改账。 | 破坏审计链路和重新对账能力。 | 差错单、审批、白名单补事实。 |
| 借贷方向按付款方和收款方口头推导。 | 会把账务方向、账户类型和余额影响混用。 | DSL 资金场景借贷平衡与账务期望表。 |
| 重放生成资金事实。 | 治理任务反向污染账本事实。 | 归档重放和治理边界。 |
| 未确认外部规则却自动处理真实资金。 | 存在合规、通道、税务、会计或金融红线风险。 | 专业确认和外部规则核验。 |

## 9. 自检评分

接入方提交评审前，可以先按下表自评。低于 90 分的维度需要补材料；低于 80 分时建议先不要进入正式评审。

| 维度 | 90 分以上标准 | 常见扣分 |
| --- | --- | --- |
| 产品可理解性 | 目标、非目标、使用者、展示口径和运营动作清楚。 | 只写接口诉求，不写用户和运营如何理解。 |
| 资金安全 | 主体、账户类型、`normalBalanceSide`、金额、币种、route、posting、entry、projection、借贷平衡、余额影响、幂等和审计闭合。 | 只证明交易成功，不证明账务和余额变化。 |
| 系统边界 | wind-funds、业务系统、通道适配层、运营后台和外部机构责任清楚。 | 把外部协议、风控或审批沉入资金内核。 |
| 测试可验证性 | 正向、逆向、失败、并发、幂等、重放和 must-fail 用例明确。 | 只有联调成功，没有失败无副作用断言。 |
| 生产准入 | 权限、审计、告警、Runbook、灰度、回滚和停止条件清楚。 | 失败靠人工查库或线下修数。 |
| 外部规则 | 规则来源、版本或发布日期、生效日期、适用范围、核验日期、确认方和确认状态清楚。 | 只写待确认，不写谁确认、确认什么、未确认前不能做什么。 |

## 10. 宣讲时推荐讲法

| 顺序 | 主题 | 要传达的重点 |
| --- | --- | --- |
| 1 | wind-funds 是什么 | 它是资金底座，不是业务产品、通道网关、风控系统、会计总账或合规结论。 |
| 2 | 接入前先问什么 | 谁的钱、因什么业务变化、谁确认、如何记账、如何验收、哪些不能做。 |
| 3 | 四流边界 | 业务流、支付信息流、账户/账务流、真实资金流必须拆开看。 |
| 4 | 常见误用 | 支付工具当账户、冻结当扣款、授权当消费、外部 pending 当成功、差错直接改账。 |
