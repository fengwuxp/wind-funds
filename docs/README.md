# 支付资金底座设计文档总入口

## 目录定位

本目录承载 `wind-funds` 的稳定设计基线，用于产品评审、系统分析、DSL 契约承接、TDD 设计、接入评审和生产交付复核。

本目录不承载过程计划、历史任务、历史演进材料或临时评审流水。历史评估和预研材料统一放入归档目录；如与当前权威设计包冲突，以本文档列出的入口为准。

## 生产交付目标驱动层

`wind-funds` 以基础资金公共能力提供者为定位，生产交付目标不是实现完整业务系统，也不依赖真实生产宿主、真实流量或上线后观测来证明仓库完成。项目必须用同一套钱包、交易、路由、账目、账本、余额投影、清分清算、结算出款和对账追偿能力，持续验证以下六类业务场景；不得为任一场景复制平行资金内核。

| 业务验证场景 | 资金底座必须证明 | 不属于本项目的完整业务能力 |
| --- | --- | --- |
| VCC 交易处理 | 支付工具准入、授权预留、完成/撤销/退款原路径回放、Spend Rule 控制事实、清结算与对账。 | 发卡、卡组织协议、issuer processor、风控决策和卡账单产品。 |
| 全球账户收付款 | 外部账户只作引用，入金确认、出款、在途/失败/退汇、费用、FX 快照、对账和差错可解释。 | 开户、VA 分配、SWIFT/本地网络协议、换汇执行和跨境合规裁决。 |
| 收单 | payment/capture/refund/dispute 归一资金事实、商户待结算资金、手续费、清分清算、结算出款和对账。 | 商户入网、PSP/收单行协议、卡组织消息和经营系统。 |
| 代理分佣结算 | 已确认应得项、归因/规则版本、退款争议阻断、清分清算、结算出款、追偿和解释。 | 代理关系、GMV/利润/KPI 计算、薪税和激励政策决策。 |
| 平台或商家优惠让利 | 本金与让利出资分离、平台/商户责任账户、退款处置、清结算拆分、对账差异和审计。 | 营销资格、券核销、活动规则和优惠决策引擎。 |
| ACH | 归一后的 Credit/Debit/return/NOC/reversal 资金影响、外部引用、在途/退回、追偿、对账和敏感数据边界。 | ACH 产品、Nacha/ODFI/RDFI 规则、Debit 授权判断、文件生成提交和 return code 解释。 |

仓库级完成证据统一来自 `tests` 模块：单元/纯契约测试、公共契约和架构边界测试、Spring/H2 集成测试、端到端资金流程测试、并发/幂等/重放/失败回滚测试，以及目标 MySQL 的 DDL、迁移、锁和隔离级别专项测试。最终结论还必须经过未参与实现的 Checker 复核。宿主接入、部署、真实流量、生产指标和线上 Runbook 属于使用方交付责任，可作为部署验收，不能反向成为本仓库 Goal 的完成锚点；仓库结论也不得外推为某个宿主已经上线稳定运行。

## 最小交付原则

支付资金底座按最小可验证闭环推进交付。任一工程变更都必须先证明一条资金事实从请求、路由、账务、余额投影、查询解释到失败无副作用形成证据链，再扩展到更复杂的业务能力。

| 问题 | 必须成立 |
| --- | --- |
| 能否闭环 | 一笔资金事实能被解释、核对、重建和测试验证。 |
| 范围是否最小 | 只覆盖当前目标场景，不顺手扩业务包、外部协议、运营后台、报表或治理能力。 |
| 红线是否足够 | 余额、账本、幂等、审计、敏感数据、权限和外部规则待确认都有保护。 |
| 扩展是否清楚 | 未覆盖能力、外部确认、回归影响和后续门禁写清楚，不提前实现。 |

## 资金业务专家真实场景模拟验证 Loop

每轮设计完善先选一个真实资金场景，不从模块、表或接口出发。资金业务专家先判断“钱、主体、状态和风险是否说得通”，再由产品、架构、TDD 和代码设计分别承接；任一角色无法给出证据时，本轮只补缺口，不进入实现。

| 角色 | 必须回答 | 证据入口 | 阻断信号 |
| --- | --- | --- | --- |
| 资金业务专家 | 谁的钱、属于谁、因什么业务变化、当前是可用/冻结/在途/待清算/已结算哪种状态。 | 产品设计 01/02/03/05，业务补充分册 06/07/08/09。 | 外部受理当到账、冻结当消费、清分当清算、退款/退汇/拒付混用、客户资金和平台资金混用。 |
| 产品 owner | 使用者、运营、财务和风控能否理解成功、失败、阻断和人工处理。 | 产品验收矩阵、用户接入指南。 | 只有后台状态，没有用户账单、商户账单、运营时间线或失败原因。 |
| 架构 owner | 场景是否落到正确模块、公共契约、状态机、事务边界和只读投影。 | DSL 设计、系分设计、模块依赖边界测试。 | wallet 写交易事实、ledger 反持交易生命周期、route 写账、治理/对账反写主链事实。 |
| TDD owner | 是否能转成 Red、服务级测试、余额断言、幂等断言和 must-fail 红线。 | TDD 设计、目标测试资产、H2 schema。 | 只能人工解释，不能准备数据、执行动作或断言余额桶/posting/entry/投影。 |
| 代码设计 owner | 是否已有代码能力可复用；若没有，最小写入范围和停止条件是什么。 | 当前代码、测试、`Justfile` 验证命令。 | 为 P2 或未确认规则新增生产 Service/DTO/Mapper、返回空结果的占位实现、单行透传抽象。 |

| 取样场景 | 先验证什么 | 当前处理 |
| --- | --- | --- |
| 用户/商户入金、转账、付款、退款、提现 | 标准交易是否能形成 route、posting、ledger entry、余额投影和幂等证据。 | 已有交易主链和测试资产，新增场景优先复用。 |
| 授权交易、Spend Rule、冻结/解冻 | 授权占用、控制额度、冻结桶和实际消费是否分离。 | 已有 wallet/transaction 分层，继续防止控制对象入账。 |
| 商户清结算、出款、对账差错 | 清分不入账、清算确认才入账、出款非终态不展示成功、差错不改历史账。 | 当前首切片只证明部分门禁，整域仍需 DDL/H2 和服务测试。 |
| 全球账户、多币种、日切、备付金 | 外部 accepted、错币种、退汇费用、法主体日切和账实对账是否能被 Red 表达。 | 只做 P2 设计验证；缺专业确认和真实来源模型时不写代码。 |

## SDD / Harness 任务规划口径

本节只定义工程任务的依赖顺序和准入字段，不记录临时状态、执行流水或历史计划。任务状态以当前 Git 基线、任务交付说明、验证命令和提交记录为准；未获明确授权时，不创建外部 `.superpowers/sdd/` 工作区。

| 波次 | 任务范围 | 先做 | 准出证据 |
| --- | --- | --- | --- |
| Wave 0 | 基线对齐 | PRD、DSL、系分、TDD、用户接入指南、代码基线、未提交差异和目标测试资产对齐。 | 任务能说明设计输入、写入范围、禁止范围、AC/TDD 映射、验证命令和停止条件。 |
| Wave 1 | 账本、钱包、账户和余额投影 | 账本事实、余额桶、账户能力、支付工具绑定、资金责任和 Spend Rule 控制事实。 | 服务级测试、H2 schema、边界测试和资金红线能证明 wallet 不写交易事实、ledger 不反持交易生命周期。 |
| Wave 2 | 交易内核和投影 | 直接交易、授权交易、余额控制、让利出资、route replay 和交易投影。 | 正向资金流、失败无副作用、原路径回放、幂等冲突和投影解释均有测试证据。 |
| Wave 3 | 清结算与对账 | `TDD-B7-RED-001` 至 `TDD-B7-RED-009`、清分结果快照、结算策略快照、对账数据分段和出款生命周期。 | Red 先失败，清分不入账、清算确认才入账、账单模式不进 `SETTLEMENT`、外部非终态不展示成功。 |
| Wave 4 | 资金数据治理 | Manifest、checkpoint、watermark、余额快照、投影重放、差异报告和大数据消费边界。 | `TDD-B8-RED-001` 至 `TDD-B8-RED-005` 先失败，治理任务不反写交易、账本、钱包事实。 |
| Wave 5 | P2 业务能力包 | VCC、全球账户、收单和外部轨道只作为业务场景包复用 P0/P1 能力。 | 外部规则、敏感数据、资金归属、客户资金/机构资金隔离、多币种日切和专业确认不完整时，只能 contract-only、阻断或转人工。 |
| Wave 6 | 生产交付场景验证 | 用六类业务流程横向复核已交付的 P0/P1/P2 能力，不新增平行内核。 | 每类场景用正向、逆向和异常测试证明业务事实映射；共享资金能力用并发、幂等、重放和失败无副作用测试证明稳定性；关键跨能力流程补组合测试，并完成目标 MySQL 专项与独立 Checker。 |

每个进入实现的任务必须保留最小执行字段：任务标识、owner、执行状态、写入范围、只读范围、禁止事项、依赖顺序、AC/TDD 映射、验证命令、停止条件、评审 owner、状态记录位置和恢复方式。任务评审同时检查规格符合度和代码质量；单个任务通过不等于整体准出，跨任务公共契约、状态机、DDL/H2、测试证据和文档漂移仍需最终复核。

## 核心设计骨架

| 骨架项 | 当前设计结论 | 权威入口 | 工程门禁 |
| --- | --- | --- | --- |
| 核心概念 | 可入账主体是资金账户、信用账户，以及平台账户角色解析后的平台资金账户。支付工具、外部账户、支出控制范围、Spend Rule、业务主体、订单和通道账户都不能直接作为 ledger subject。 | 产品设计 01、产品设计 README、DSL 主体和账务表、系分设计 01。 | 新增主体、字段或枚举必须证明不会把控制对象变成资金来源，不会让投影反写事实。 |
| 能力优先级 | 账本账目 > 钱包 > 交易层。支付工具、VCC、全球账户和外部轨道作为业务能力包接入；收单能力仅保留设计，不进入默认实现范围。 | 产品设计 01、产品设计 02/03/05 和业务补充分册。 | 每个能力进入工程前必须有最小交付场景、写入范围、禁止范围、资金不变量和验证命令。 |
| 系统模块 | `core` 承载资金语义和端口；`wallet` 承载账户、支付工具、资金责任和支出控制；`transaction` 承载资金事实和生命周期；`ledger` 承载账本事实和余额投影；`reconciliation` 承载清结算与对账；`governance` 承载归档、重放和差异报告。 | 系分设计 01 和 AGENTS.md 模块边界。 | 禁止 `wallet` 写交易事实、`route` 写账本事实、`ledger` 反持交易生命周期、投影或治理任务反写资金事实。 |
| 架构分层 | 契约层暴露 face/Request/Query/DTO/Spec；应用层承接 use-case facade、幂等、生命周期和编排；领域层承接路由、账务计划、余额规则；基础设施层只做 Mapper/Entity/MapStruct/消息适配；读模型层只读派生、可重放、可重建。 | 系分设计 01、系分 README、系统分层图。 | 公共契约、application 包、DTO、表结构、状态机或依赖方向变化必须补设计、测试和边界验证。 |
| 能力地图 | 产品能力地图说明业务能力，系统能力地图说明模块和事实归属，TDD 能力地图说明目标测试资产。三者必须以同一组主体、账目、状态、快照和红线编号互相追踪。 | 产品设计、DSL设计、系分设计、TDD设计。 | 任一能力无法从产品验收追踪到 DSL case、系分服务和 TDD 断言时，只能继续补设计或做差距复核。 |

| 产品目标、角色、场景、能力边界和验收口径是什么。 | 产品设计 01-05，业务专项看 06-08，Spend Rule 专项看 09，ACH 看 ACH 边界。 | DSL、系分、TDD 只承接稳定产品语义，不重新定义业务目标。 |

| 业务接入方如何准备材料、填事实说明卡和通过接入评审。 | 用户接入指南。 | 用户接入指南只做使用者翻译，不替代 PRD、DSL、系分或 TDD 权威口径。 |

## 生产交付证据

生产交付不是一份新 PRD 或一张图，而是一组能让产品、架构、测试、SRE、财务、风控、安全和合规共同复核的证据。

| 证据项 | 必须包含 | 缺失时结论 |
| --- | --- | --- |
| 产品签出 | 使用者、业务事实、验收 ID、可见结果、外部规则状态、未覆盖范围和业务 owner。 | 只能作为设计输入。 |
| 架构签出 | 服务入口、模块边界、公共契约、表/索引、状态机、事务边界、幂等、补偿、观测、安全和取舍记录。 | 不能进入发布评审。 |
| 资金证据 | 主体、账户类型、账目、币种、route snapshot、posting plan、ledger entry、余额投影、借贷平衡、幂等和失败无副作用。 | 涉及资金变化时阻断。 |
| 测试验证 | `tests` 模块单元/契约/边界、Spring/H2 集成、业务流程、并发/幂等/重放/失败回滚、目标 MySQL 专项、静态检查和当前验证命令。 | 不能声明仓库能力生产可交付；未执行时必须列为待补证据。 |
| 恢复与可运维契约 | 通过测试证明错误可定位、状态可发现、重复命令可重放、失败可回滚或进入受控差错；对宿主暴露必要查询和恢复边界。 | 缺少可测试恢复路径时阻断对应能力；不要求真实生产指标或线上演练作为仓库准出锚点。 |
| 专业确认 | 法务、合规、财务、税务、通道、银行、卡组织、安全或数据责任人的确认状态、适用范围、有效期和脱敏证据引用。 | 影响资金释放、出款、敏感数据或外部规则时阻断。 |
| 残余风险 | 未覆盖范围、已知缺口、回退方案、下一门禁、风险接受人和复核时间。 | 不得声明完整生产可用。 |

## 阻断和降级口径

| 情况 | 处理 |
| --- | --- |
| 产品场景、DSL caseId、系分服务入口或 TDD 用例任一侧缺失。 | 阻断，先补齐跨文档映射。 |
| 有资金变化但未断言余额桶、posting plan、ledger entry、投影和幂等。 | 阻断，补测试证据或缩小交付范围。 |
| 新增或修改公共契约、服务入口、枚举、Request/Query/DTO、状态机或表结构，但未声明写入范围。 | 阻断，回到工程变更边界。 |
| 清结算、对账或出款通过运营动作追加资金事实，但缺业务语义明确的受控命令、来源单据、审批证据、幂等键、原事实引用或失败无副作用测试。 | 阻断，补对应资金命令和红线测试。 |
| 使用 `CONTRACT_ONLY` JSON 样例、请求态权益快照或 `contextVariables` 过渡字段作为生产事实源。 | 阻断，改为不可变事实源和服务级测试证据，或降级为契约承载。 |
| 专业确认证据包缺失、过期、被撤销、适用范围不匹配或证据引用含敏感原文。 | 阻断或降级，补确认记录、有效期、范围、撤销处理和脱敏证据引用。 |
| 清结算、对账、归档、重放或指标边界只有设计，没有 DDL/H2、服务级测试或边界测试。 | 只能声明设计输入；若目标是生产完成，必须先补实现和测试证据。 |
| 声称 MySQL 生产可交付，但未在 `tests` 模块专用测试库执行迁移、回读、锁与隔离级别专项测试。 | 阻断 MySQL 交付结论；H2 和静态 DDL 契约不能替代目标数据库证据。 |

## 统一术语映射

| 产品表达 | DSL / 系分 / TDD 表达 | 语义边界 |
| --- | --- | --- |
| 授权结算 | 授权完成，事件使用 `AUTHORIZATION_TRANSACTION / COMPLETE`。 | 指授权占用转为实际消费、扣款或待清算结果；不等同于商户结算单或出款。 |
| 授权部分结算 | 授权部分完成，事件仍使用 `COMPLETE`，以原授权为引用。 | 指只完成部分授权金额；累计完成金额不得超过原授权金额。 |
| 已结算金额 | 授权链路中优先称为已完成金额。 | 指原授权已经完成的累计金额；只用于约束退款、拒付、可信撤销和迟到事件；过期事件不得据此释放资金。 |
| 结算后退款 | 授权完成后退款，事件使用 `AUTH_REFUND` 或对应退款链路。 | 必须基于原授权完成路径反向，不按当前绑定关系重新选路。 |
| 授权撤销 | 外部明确撤销或冲正，事件使用 `REVERSAL`。 | 释放剩余授权占用，终态为撤销；不能和系统过期混成同一结果。 |
| 授权过期 | 到期、超时或通道未返回只进入提醒、差错候选或运营处理。 | 不提供 `EXPIRE` 事件或 `expire` 服务入口，不生成资金交易、route、posting、ledger entry 或余额变化。 |
| 无前置授权强制完成 | 使用 `COMPLETE` 的强制完成模式。 | 不新增独立强制完成事件，不伪造授权占用；必须有策略、上限、外部原事实引用、凭证、原因和审计。 |
| 结算锁定 | 清结算链路的 `AVAILABLE -> SETTLEMENT`。 | 指商户、合作方或企业出款前锁定可结算余额；不代表外部出款成功。 |
| `SETTLEMENT` 账目 | 出款中或结算处理中锁定资金。 | 是余额桶，不是授权生命周期的 `COMPLETE` 动作。 |
