# 支付资金底座设计文档总入口

## 目录定位

本目录承载支付资金底座的稳定设计基线，用于产品评审、系分设计、DSL 契约承接、测试驱动设计和生产准入评审。

本目录的权威入口只保留稳定设计口径，不承载任务拆解或过程记录；交付评审以本文档包完成代码、测试、DDL 和现有实现差距复核。历史评估和预研材料统一放入归档目录，并按归档说明降级使用。

## MVP 约规

支付资金底座默认先做最小可用 MVP 版本。每一轮产品设计、DSL、系分、TDD 或编码准入都必须先选择一个能端到端证明资金闭环的最小切片，完成后再评估是否扩展。

MVP 只纳入本轮验收必须的业务事实、资金动作、账务断言、查询解释和失败红线；不提前铺设大而全的业务能力包、通用平台、规则引擎、全量外部协议、完整运营后台、复杂报表或跨业务扩展点。任何“为了未来可能需要”的扩展，必须先证明它是当前闭环不可缺少的约束，否则进入未覆盖范围或后续独立评审。

MVP 评审时优先回答四个问题：

| 问题 | 必须成立 |
| --- | --- |
| 能否闭环 | 一笔资金事实能从请求、路由、账务、余额投影、查询解释到失败无副作用形成证据链。 |
| 范围是否最小 | 只覆盖本轮目标场景，不顺手扩业务包、外部协议、运营后台、报表或治理能力。 |
| 红线是否足够 | 余额、账本、幂等、审计、敏感数据、权限和外部规则待确认都有最低保护。 |
| 后续如何扩展 | 扩展点写成未覆盖范围、后续评审条件和回归影响，不在 MVP 中提前实现。 |

### 设计与任务对齐约规

设计结论必须能直接转成任务边界。任何 PRD、DSL、系分或 TDD 调整，如果不能说明本轮 MVP 场景、验收编号、写入范围、禁止范围和未覆盖范围，就只能作为设计输入，不得进入工程任务。

| 对齐项 | 设计侧必须说明 | 任务侧必须承接 |
| --- | --- | --- |
| MVP 场景 | 本轮服务哪个使用者、处理哪类资金事实、证明哪条最小闭环。 | `mvpScenario`、目标 AC/DSL/TDD/RED、首批验证命令。 |
| 范围裁剪 | 哪些能力进入 MVP，哪些只是后续扩展。 | `writeScope`、`noWriteScope`、`notDoneScope`。 |
| 资金证据 | 账务、余额、幂等、失败无副作用和审计最低证据。 | `moneyInvariant`、首批 Red、核心断言。 |
| 扩展门禁 | 清结算、资金数据治理、P2 业务、外部协议和运营后台是否独立评审。 | `nextGate`、独立任务或独立授权条件。 |

## 核心设计骨架

本节只做跨文档总控，不替代 PRD、DSL、系分或 TDD 正文。评审核心概念、产品能力、系统模块、架构分层和能力地图时，先按下表统一语言，再进入对应分册核对细节。

| 骨架项 | 当前设计结论 | 权威入口 | 编码前门禁 |
| --- | --- | --- | --- |
| 核心概念 | 默认可入账主体是资金账户（含平台角色解析后的平台资金账户和 VCC 资金子账户）和信用账户（含 VCC 信用子账户）；VCC 发卡专项不新增独立 `VCC_ACCOUNT` 发卡财务账户。支付工具、外部账户、预算组、Spend Rule、业务主体、订单和通道账户都不能直接作为 ledger subject。预算组是 scope、展示和审计边界，Spend Rule 是授权前控制规则，交易投影是统一只读读模型。 | 产品设计 01 的核心概念、产品设计 README 的四层对齐裁决、DSL 主体和账务表。 | 任何新增主体、字段或枚举都必须证明不会把控制对象变成资金来源、不会让投影反写事实；VCC 卡必须绑定资金子账户或信用子账户入账，不得恢复 `VCC_ACCOUNT`、支付工具账本、卡号账本或预算组账本。 |
| 产品能力 | P0 保护钱包、账本、账目、余额投影、对账清分清算结算和资金数据治理证据；P1 承接直接交易、授权交易、余额控制、交易投影；P2 只作为 VCC、全球账户、收单、ACH/银行转账等业务能力包接入，不新增平行资金内核。 | 产品设计 01 的产品能力地图、产品设计 02/03/05、业务补充分册 06/07/08 和 ACH 边界。 | 每个能力进入工程前必须有 MVP 场景、AC/DSL/TDD/RED 映射、写入范围、禁止范围和 Not Done 边界。 |
| 系统模块 | `core` 承载资金语义和端口；`wallet` 承载账户、支付工具、资金责任解析和钱包 application facade；`transaction` 承载资金事实、生命周期、路由快照和交易投影编排；`ledger` 承载账本事实、分录和余额投影；`reconciliation` 承载对账清结算运营闭环；`governance` 承载归档、Manifest、重放和差异报告；`tests` 承载契约、流程、红线和边界证据。 | 系分设计 01 的能力域边界和模块依赖、系分设计 02/03/04/05、AGENTS.md 模块边界。 | 禁止 `wallet` 写交易事实、`route` 写账本事实、`ledger` 反持交易生命周期、投影或治理任务反写资金事实。 |
| 架构分层 | 契约层暴露 face/Request/Query/DTO/Spec；应用层承接 use-case facade、幂等、生命周期和编排；领域层承接路由、账务计划、余额规则；事实端口层隔离过账、快照、审计和事件；基础设施层只做 Mapper/Entity/MapStruct/消息适配；读模型层只读派生、可重放、可重建。 | 系分设计 01 的架构分层、系分 README 的架构设计入口、系统分层图。 | 公共契约、application 包、DTO、表结构、状态机或依赖方向变化必须进入 Execution Grant，必要时补架构边界测试。 |
| 能力地图 | 产品能力地图说明业务能力，系统能力地图说明模块和事实归属，TDD 能力地图说明目标测试资产。三者必须以同一组主体、账目、状态、快照和红线编号互相追踪。 | 产品设计 01 的能力地图到架构和验收矩阵、系分设计 01 的能力域到系统架构矩阵、TDD 设计覆盖矩阵。 | 任一能力无法从产品验收追踪到 DSL case、系分服务和 TDD 断言时，只能继续补设计或做差距复核，不得写生产代码、测试代码或 schema。 |

### 权威裁决矩阵

当评审中出现“这件事到底看哪份文档”的分歧时，按下表裁决，避免在 PRD、DSL、系分和 TDD 中复制同一份规则。

| 争议问题 | 权威入口 | 其他文档的角色 |
| --- | --- | --- |
| 产品目标、角色、场景、能力边界和验收口径是什么。 | 产品设计 01-05，业务专项看 06-08 和 ACH 边界。 | DSL、系分、TDD 只承接稳定产品语义，不重新定义业务目标。 |
| 某个资金场景的主体、账户示例、账户类型、借贷平衡、余额影响和失败红线是什么。 | DSL 的 [资金场景借贷平衡与账务期望表](DSL设计/支付资金底座DSL承载层设计.md#51-资金场景借贷平衡与账务期望表)。 | PRD 只保留产品资金影响摘要，系分只说明实现承接，TDD 只转成断言。 |
| 服务入口、模块边界、状态机、表职责、事务、幂等和观测如何落地。 | 系分设计 01-05。 | 产品设计给目标和规则，DSL 给契约语义，TDD 给验证证据。 |
| 哪些用例、红线、余额断言、幂等断言和验证命令必须覆盖。 | TDD 设计和产品验收矩阵。 | 产品、DSL、系分提供输入，TDD 不发明业务目标、DSL 字段或系统接口。 |
| 业务接入方如何准备材料、填事实说明卡和通过接入评审。 | 用户接入指南。 | 用户接入指南只做使用者翻译，不替代 PRD、DSL、系分或 TDD 权威口径。 |
| 是否可以编码、是否可以上线、是否可以声明生产 Done。 | Execution Grant、OpenSpec/Harness、实现证据、测试和外部确认共同裁决。 | 设计文档只能作为准入输入，不能单独授权代码、测试、DDL 或上线。 |

### 四层对齐裁决入口

当争议集中在“谁可以入账、支付工具是否承载余额、预算组和 Spend Rule 是否要生成交易记录、交易投影到底归属哪里”时，以 [产品设计 README 的四层对齐裁决](产品设计/README.md#prd-dsl-系分和-tdd-四层对齐裁决) 为第一裁决入口。该表已经把 PRD、DSL、系分和 TDD 的角色拆开：产品设计定语义和验收边界，DSL 定结构化事实与失败红线，系分定服务、状态、表和事务边界，TDD 定可执行断言；任何一层不得单独扩大可入账主体、资金来源或事实写入范围。

## 跨文档追踪关系

| 从 | 到 | 追踪重点 |
| --- | --- | --- |
| 产品设计 | DSL 设计 | 产品场景是否能落到资金事实、主体、账户、账目、路由、账务和投影。 |
| DSL 设计 | 系分设计 | DSL 对象、事件和不变量是否有模块、接口、表结构和状态机承接。 |
| 产品设计 | 系分设计 | 产品流程和能力边界是否被拆成清晰的系统职责、服务能力和数据边界。 |
| 产品设计 / DSL 设计 / 系分设计 | TDD 设计 | 每个资金变化是否能被状态、余额桶、账本分录、投影、幂等和异常路径证明。 |
| 产品设计 / DSL 设计 / 系分设计 / TDD 设计 | 用户接入指南 | 业务接入方是否能理解接入前置、能力成熟度、可用边界、禁止项和验收证据。 |

## 设计准入评估总控

本设计包用于产品和开发团队做进入编码设计、TDD 拆解和差距复核前的准入评估，不等同于上线批准、合规结论、财务处理结论、税务判断或外部机构规则确认。涉及真实资金、客户资金、商户待结算资金、支付资质、备付金、反洗钱、个人信息、卡组织、银行、清算网络、跨境或外汇规则时，必须由法务、合规、财务、风控、数据安全或通道负责人给出最终确认。

### 设计评审准入口径

设计评审不要只问“功能有没有设计完”，而要按下列顺序检查设计是否真的可被生产、运营和测试使用。任一项无法回答时，优先补产品、DSL、系分或 TDD 证据，不进入编码授权。

| 顺序 | 评审视角 | 必须回答的问题 | 补强方向 |
| --- | --- | --- | --- |
| 1 | 可用性 | 这条能力在正常、失败、重试、人工处理和只读查询下是否都有明确入口和终态。 | 补齐主流程、逆向流程、失败终态、人工兜底、查询口径和 Runbook 触发条件。 |
| 2 | 资金安全 | 是否能证明不重复入账、不半截入账、不绕过账本、不跨主体误转、不把投影当事实源。 | 补 route snapshot、posting plan、ledger entry、余额桶、幂等键、唯一约束、审批和审计证据。 |
| 3 | 金融红线 | 是否存在资质、客户资金、商户待结算资金、外部规则、敏感数据或合规确认缺口。 | 写清待确认方、确认项、未确认前不覆盖范围和必须失败场景。 |
| 4 | 易用性 | 用户、商户、运营、财务、风控和客服能否理解“发生了什么、为什么、下一步怎么办”。 | 补用户账单、商户账单、运营时间线、错误原因、审批状态、差错责任和处理建议。 |
| 5 | 可理解性 | 同一概念在 PRD、DSL、系分和 TDD 中是否同名同义，状态、事件、账目和周期是否不会混用。 | 回到统一术语映射、caseId、AC/TDD/RED 映射和测试命名，消除同词异义。 |

评估必须同时覆盖下列维度：

| 维度 | 产品设计要回答 | DSL 设计要回答 | 系分设计要回答 | TDD 设计要回答 | 阻断信号 |
| --- | --- | --- | --- | --- | --- |
| 设计可用性 | 场景、角色、目标、非目标和人工处理是否清楚。 | 业务事实、事件类型、主体、金额和引用是否可结构化。 | 服务入口、状态机、表设计和异常路径是否能落地。 | 是否能转成正常、异常、边界、幂等和并发用例。 | 只能描述“成功/失败”，无法解释输入事实、资金路径、状态变化和下一步处理。 |
| 资金安全 | 客户资金、商户待结算资金、平台自有资金、手续费、补贴、成本和保证金是否隔离。 | 可记账主体、route snapshot、posting plan、LedgerEntry 是否能证明路径。 | 事务、唯一约束、幂等、审批、审计和失败无副作用是否明确。 | 是否断言余额桶、账本周期、分录平衡、投影一致和红线失败。 | 外部账户入账、平台账户角色混用、投影或后台改余额、重复出款、缺审批调账。 |
| 金融红线 | 法域、资质、客户资金、KYC/KYB/AML、敏感信息和外部规则是否列为待确认。 | DSL 是否保留规则来源、版本或发布日期、生效日期、适用主体或适用范围、适用法域、核验日期、确认方、确认状态、证据引用和脱敏边界。 | 权限、审计、敏感字段、导出、外部协议和生产红线是否落地。 | 是否有敏感信息、外部账户、争议证据和合规待确认的 must-fail 用例。 | 把内部清分清算写成持牌清算结论；把待结算资金泛称客户备付金；绕过 KYC/KYB/AML；保存完整 PAN、CVV、密钥或明文敏感凭证。 |
| 易用性 | 用户、商户、运营、财务和风控能否理解余额、账单、冻结、授权、清算、退款和争议状态。 | DSL 字段是否能支撑可解释展示和操作原因。 | 查询、投影、时间线、错误原因和人工处理入口是否完整。 | 是否覆盖用户账单、商户账单、运营时间线和失败提示断言。 | 授权展示成最终消费、冻结展示成扣款、待清算展示成可提现、争议退款被普通退款吞掉。 |
| 可理解性 | 概念是否稳定，术语是否和总入口统一映射一致。 | 枚举、事件、状态和 JSON 示例是否避免同词异义。 | 模块、表、状态和 API 命名是否承接产品/DSL。 | 测试命名是否能反查产品验收和 DSL 契约。 | 授权完成和商户结算混用，账本周期、清算账期、报表周期、归档水位或规则窗口混用。 |
| 可开发性 | 能力边界、强规则、配置项、待确认项和非目标是否明确。 | 契约对象、不变量和失败边界是否足够稳定。 | 模块边界、依赖方向、数据模型、事务边界和观测指标是否可实施。 | 目标测试资产、真实执行路径和验证命令是否明确。 | 规则只存在口头描述，失败只能人工改库，公共契约需要边做边改但无 Execution Grant。 |
| 可测试性 | 验收矩阵是否覆盖主流程、逆向、异常、人工、报表和红线。 | 契约样例是否能驱动断言。 | 系分是否提供状态、表、服务和观测落点。 | TDD 是否能证明状态、金额、账户类型、`normalBalanceSide`、route、posting、entry、projection、借贷平衡、余额影响、audit 和 no-side-effect。 | 只断言接口不报错、交易状态或 entry 数量，不断言余额桶、分录平衡和幂等副作用。 |

准入结论只允许三种：

| 结论 | 含义 | 准入动作 |
| --- | --- | --- |
| 通过 | 四类设计入口在本次范围内闭合，资金路径、契约、系统落点和 TDD 断言都可追溯。 | 进入交付差距复核，并在 Execution Grant 中声明允许触碰范围。 |
| 带条件通过 | 本次任务能力链路可拆解，但存在不影响核心资金不变量的待确认项。 | 写清条件、负责人、补齐时点和不覆盖范围；编码任务不得越过待确认边界。 |
| 阻断 | 存在资金安全、金融红线、主体不清、路径不可追溯、契约不稳、验收不可测或外部规则未确认的关键缺口。 | 暂停编码，先补产品、DSL、系分、TDD 或合规/财务/通道确认。 |

### 设计交付评分复核口径

设计交付评分不是文档篇幅评估，而是准入风险评估。低于 90 分的维度必须回到本表补证据；补证据后仍无法闭合时，准入结论只能是带条件通过或阻断。

| 维度 | 90 分以上必须具备的证据 | 常见扣分点 | 补强入口 |
| --- | --- | --- | --- |
| 金融红线 | 外部规则、合规、会计、税务、敏感数据、客户资金和持牌事项都有规则来源、版本或发布日期、生效日期、适用主体或适用范围、适用法域、核验日期、确认方、确认状态和不覆盖范围。 | 只写“待确认”，未说明谁确认、确认什么、未确认前不能做什么。 | 产品设计 01 的待确认项和本文件生产准入检查清单。 |
| 系分可开发性 | 每个实现切片都有服务入口、表职责、状态、幂等键、事务边界、观测指标和失败副作用。 | 表设计过粗、接口和状态落点不清、实现时需要临时决定公共契约。 | 系分 README 的实现承接清单和各分册表设计章节。 |
| TDD 可验证性 | 每个 MVP 任务有 AC/DSL/TDD/RED 显式映射、最小断言集、失败无副作用和验证命令。 | 只说明测试范围，未说明要证明哪些资金事实。 | TDD 设计的覆盖证明卡和测试证据链。 |
| 可理解性 | 评审角色能按固定路径读文档，并能用同一术语解释产品、DSL、系分和 TDD。 | 同一概念多名、周期混用、授权完成和商户结算混用。 | 本文件统一术语映射和各 README 阅读顺序。 |
| 交付门禁 | 编码前有 MVP 任务准入卡，明确范围、允许触碰项、TDD 清单、验证命令和待确认不覆盖范围。 | 跳过 Execution Grant，直接把设计包当作全量编码授权。 | OpenSpec Harness Plan 和下方 MVP 任务准入卡。 |

## 按角色使用路径

不同角色使用本设计包时关注点不同，但最终都必须回到同一条证据链：产品场景、DSL 契约、系分落点和 TDD 断言。

快速评审时先读本文件的准入评估总控、统一术语映射和 MVP 任务准入卡；再按角色进入对应分册。不要从任意长表开始评审，否则容易只看到字段或用例，忽略资金语义和红线。

| 使用者 | 先读 | 必须拿到的结论 | 不应跳过 |
| --- | --- | --- | --- |
| 产品和业务负责人 | 产品设计/01、产品设计/05 | 场景是否真实、目标是否清楚、哪些能力属于 P0 资金底座内核、P1 交易与读模型扩展、P2 业务模式能力包或外部待确认。 | 概念边界、非目标、产品红线和验收矩阵。 |
| 运营、财务和风控 | 产品设计/03、产品设计/05、系分设计/05 | 异常如何阻断、清结算和对账如何闭环、谁有权限处理、处理后如何留痕。 | 差错单、审批、凭证、核销、重新对账和追偿链路。 |
| 架构和研发 | DSL设计、系分设计/01、相关系分分册 | 资金事实如何进入 DSL，落到哪些模块、服务、表、状态机和事务边界。 | 账本事实源、route snapshot、幂等键、唯一约束和金融红线。 |
| 测试 | 产品设计/05、TDD设计、系分设计/05 | 每个场景的正常、异常、边界、并发和 must-fail 用例如何落到测试资产。 | 余额桶断言、posting plan 平衡、ledger entry、投影和失败无副作用。 |
| 安全、合规和审计 | 产品设计/01、系分设计/05、外部参考清单 | 敏感数据、权限、导出、审批、外部规则和合规待确认项是否清楚。 | 本设计不替代法务、税务、会计、合规或持牌机构最终确认。 |

## 统一术语映射

授权链路和商户结算链路都会出现“结算”字样。为了避免产品、DSL、系分和测试之间混用，本文档包采用以下映射：

| 产品表达 | DSL / 系分 / TDD 表达 | 语义边界 |
| --- | --- | --- |
| 授权结算 | 授权完成，事件使用 `AUTHORIZATION_TRANSACTION / SETTLE`。 | 指授权占用转为实际消费、扣款或待清算结果；不等同于商户结算单或出款。 |
| 授权部分结算 | 授权部分完成，事件仍使用 `SETTLE`，以原授权为引用。 | 指只完成部分授权金额；累计完成金额不得超过原授权金额。 |
| 已结算金额 | 授权链路中优先称为已完成金额。 | 指原授权已经完成的累计金额；只用于约束退款、拒付、过期释放和迟到事件。 |
| 结算后退款 | 授权完成后退款，事件使用 `AUTH_REFUND` 或对应退款链路。 | 必须基于原授权完成路径反向，不按当前绑定关系重新选路。 |
| 授权撤销 | 外部明确撤销或冲正，事件使用 `REVERSAL`。 | 释放剩余授权占用，终态为撤销；不能和系统过期混成同一结果。 |
| 授权过期 | 系统根据授权有效期释放剩余占用，事件使用 `EXPIRE`。 | 可复用授权释放账务路径，但状态、释放原因、审计和过期金额必须保留 `EXPIRE` 语义。 |
| 无前置授权强制完成 | 使用 `SETTLE` 的强制完成模式。 | 不新增独立强制完成事件，不伪造授权占用；必须有策略、上限、外部原事实引用、凭证、原因和审计。 |
| 通道预处理与事件编排类场景 | 上层业务或通道适配层归一后的场景。 | 不作为资金底座默认 DSL 和系分场景；资金底座只接收明确资金事实。 |
| 结算锁定 | 清结算链路的 `AVAILABLE -> SETTLEMENT`。 | 指商户、合作方或企业出款前锁定可结算余额；不代表外部出款成功。 |

### 首批 MVP 任务切片准入顺序

首批任务不追求一次落完目标态，先用最小可验证切片证明现有资金内核的状态、金额、账户类型、`normalBalanceSide`、route、posting、entry、projection、借贷平衡、余额影响、幂等和审计证据链。每个任务只选择下表一个切片；清结算、对账、归档和治理属于独立能力域，必须拿到独立 Execution Grant 后再进入写入范围，不能混入交易主线任务。

| `writeScope` | 允许修改的模块、包、公共契约、枚举、Request/Query/DTO、状态机、表结构、H2 schema、测试资源和运行时配置。 |
| `noWriteScope` | 只读范围、禁止范围、不得触碰的资金语义、外部协议、历史事实和 Not Done 结论。 |
| `physicalLanding` | 复用既有模块、新增 face/impl、暂不落物理模块或 contract-only；依赖方向、端口边界、DTO、Entity、Mapper 和边界测试。 |
| `firstRedSet` | 首批 Red、必须失败行为、目标测试资产、失败断言、测试层级和验证命令。 |
| `moneyInvariant` | 金额闭合、主体、账户类型、`normalBalanceSide`、账目、币种、周期、route、posting、entry、projection、借贷平衡、余额影响、幂等、失败无副作用和审计断言。 |
| `operationGovernanceGate` | 清结算、对账、出款、归档、重放、指标水位、运营补事实白名单、Manifest、checkpoint、差异报告和人工处理入口。 |
| `externalRuleStatus` | 规则来源、版本或发布日期、生效日期、适用主体或范围、适用法域、核验日期、确认方和确认状态。 |
| `verificationAndStop` | 验证命令、失败停止条件、Not Done 条件和回到设计或人工确认的触发器。 |

### 编码准入材料包

进入编码前，Execution Grant 或等价任务说明至少应包含下列材料。缺失材料可以继续做设计评审、差距复核或 TDD 分析，但不得写生产代码、测试代码、DDL/H2 schema 或运行时配置。

| 材料 | 必填内容 | 判定口径 |
| --- | --- | --- |
| MVP 任务封面 | 任务切片编号、目标能力、PRD 章节、DSL caseId、系分章节、TDD/RED 编号、Git 基线和当前工作树状态。 | 不能说明 authority baseline 时只能做 Round 0。 |
| 范围锁定卡 | `writeScope`、`noWriteScope`、允许修改文件类型、禁止触碰能力、是否允许公共契约或表结构变更。 | 未列入 `writeScope` 的模块只能只读复核。 |
| DSL 执行化清单 | `dslCaseId -> fixturePath -> fixtureLevel -> targetTestClass -> coreAssertions -> notDone`。 | 未被测试读取的 caseId 只能作为设计依据。 |
| 首批 Red 卡 | 目标测试类、失败断言、数据准备、真实执行路径、替身边界、验证命令和红变绿停止条件。 | 只断言状态、数量或不报错时不准实现。 |
| 资金不变量卡 | 主体、账户类型、`normalBalanceSide`、账目、币种、账本周期、route、posting、entry、projection、借贷平衡、余额影响、幂等、审计和失败无副作用。 | 金额变化缺任一适用证据时阻断。 |
| 数据落点卡 | 表、索引、唯一键、H2 schema、Entity、Mapper、迁移影响、只读不落库原因。 | 涉及持久化但未授权 DDL/H2 时阻断。 |
| 独立授权判定 | 是否触碰清结算/对账、归档/治理、P2 业务能力包、外部规则或敏感数据。 | 命中 B7/B8/P2 时必须切到独立 Execution Grant。 |
| 验证和停止卡 | 必跑命令、可接受失败、不可接受失败、回滚或回到设计的触发条件。 | 验证命令缺失时只能声明设计输入态。 |

资金不变量卡必须引用 DSL 的 [资金场景借贷平衡与账务期望表](DSL设计/支付资金底座DSL承载层设计.md#51-资金场景借贷平衡与账务期望表)。完整借贷表只在 DSL 维护；PRD 只保留产品资金影响摘要，系分和 TDD 只承接引用和验证要求。凡涉及金额变化、余额桶变化、清结算、对账差错、权益金额、调账、出款、归档重放或投影重建，Execution Grant 需要说明本任务命中哪些表行、哪些行不适用，以及参与方账户示例、账户类型、借贷平衡公式、余额影响和对应 TDD 断言。

### A0 基线核验卡

A0 是进入编码前的只读核验任务，用于把设计、规格、任务和当前工程状态对齐成同一条 authority baseline。A0 不写生产代码、测试代码、DDL/H2 schema 或运行时配置；发现缺口时只输出差距、扩权建议、首批 Red 建议和停止条件。

| baselineItem | mustCheck | evidence | passCondition | stopCondition |
| --- | --- | --- | --- | --- |
| Git 基线和工作树 | 当前分支、最近提交、未提交变更、未跟踪文件和本任务允许读取范围。 | `git status --short`、`git rev-parse --short HEAD`、本任务说明。 | 能区分已冻结基线、用户既有变更和本任务可触碰范围。 | 工作树存在会影响判断的未知代码或 schema 变更，且无法确认来源。 |
| 文档基线 | PRD、DSL、系分、TDD 是否都能反查本任务 AC、DSL case、服务入口和 Red。 | 四类 README、专题分册、交叉映射表。 | 目标能力没有孤立 PRD、孤立 DSL、孤立系分或孤立测试。 | 任一侧缺失导致无法说明资金事实、系统落点或测试证据。 |
| OpenSpec / Harness | 是否已有 change、plan、Execution Grant 或等价任务说明。 | OpenSpec/Harness 文件、任务说明、人工确认记录。 | 能写清 `abilityBatch`、`authorityBaseline`、`writeScope`、`noWriteScope` 和 `firstRedSet`。 | 缺 Execution Grant 但准备写代码、测试、schema 或运行时配置。 |
| 现有代码范围 | 目标模块、公共契约、表结构、测试资产和边界测试是否可定位。 | `core`、`wallet-*`、`transaction-*`、`ledger-*`、`tests` 的只读复核结果。 | 能说明本任务只读范围、可改范围和禁止范围。 | 需要改公共契约、状态机或表结构但未授权。 |
| H2 / DDL 现状 | 本任务是否触碰持久化、Mapper、Entity、查询或状态字段。 | `tests/src/test/resources/jdbc-schema.sql` 和目标表设计差距。 | 不触碰数据库时写明不适用；触碰数据库时 DDL/H2 写入范围已授权。 | 生产表或 H2 schema 需要变更但未纳入 `writeScope`。 |
| 目标测试资产 | 首批 Red、目标测试类、fixture、验证命令和最小资金断言。 | TDD Red 卡、DSL 执行化盘点、现有测试类清单。 | 每个资金变化都有状态、DSL 借贷表命中行、账户类型、`normalBalanceSide`、route、posting、entry、projection、借贷平衡、余额影响、幂等和审计断言计划。 | 只能证明接口不报错、状态变化或 entry 数量。 |
| 验证环境 | JDK、Maven/just、私有仓库、目标测试命令和可接受失败边界。 | `just mvn-version` 或等价命令计划、验证命令清单。 | 能区分代码问题与环境、网络、凭据或缓存问题。 | 验证命令缺失，或失败原因无法归类。 |
| 独立能力域判定 | 是否触碰 B7 清结算对账、B8 资金数据治理或 P2 业务能力包。 | 能力域判定、独立授权需求和 Not Done。 | A0-A4 与 B7/B8/P2 边界清楚。 | 交易主线任务需要顺手写清结算、对账、治理或业务专项能力。 |

A0 输出必须形成一页可评审结论，而不是零散检查记录。建议按下列模板写入任务说明或 Execution Grant 附件：

| 输出项 | 填写口径 |
| --- | --- |
| `a0Conclusion` | `PASS`、`CONDITIONAL_PASS` 或 `BLOCKED`；只读核验不产生 Done。 |
| `baselineCommit` | 当前 Git 提交、工作树未提交变更摘要和哪些变更不纳入本任务基线。 |
| `docCoverage` | 本任务覆盖的 PRD、DSL、系分、TDD 章节和缺口。 |
| `writeScopeProposal` | 拟开放的写入范围、禁止范围和是否需要公共契约、DDL/H2 或测试资源授权。 |
| `firstRedProposal` | 首批 Red、目标测试类、核心断言和验证命令。 |
| `stopReasons` | 需要回到产品、DSL、系分、TDD、外部规则确认或独立 Execution Grant 的触发条件。 |

### TDD 分析准入卡

进入 TDD 分析不等于进入编码。TDD 分析只允许产出测试资产设计、首批 Red 排序、DDL/H2 范围、服务级测试范围、边界测试、外部规则核验和残余风险矩阵；生产代码、测试代码、DDL/H2 schema 和运行时配置写入仍必须等待 Execution Grant。

| 能力域 | 可进入 TDD 分析的条件 | TDD 分析必须产出 | 仍然禁止 |
| --- | --- | --- | --- |
| 钱包、账本、账目和余额投影 | PRD、DSL、系分和现有测试能说明主体、账目、周期、route、posting、entry 和余额桶。 | AC/RED/TDD 映射、余额桶断言、posting 平衡断言、幂等和失败无副作用测试清单。 | 未授权修改公共契约、表结构、H2 schema 或生产实现。 |
| 清结算与对账 | 产品 03/05、DSL、系分 03/05 已明确清分、清算、结算、出款、对账、差错、追偿和运营补事实边界。 | `CLS-GATE-*`、`TDD-B7-RED-*`、DDL/H2 范围、服务级 H2 流程、并发重跑、权限审计、使用者解释、外部规则和 Not Done 矩阵。 | 不得把出款前准入候选能力当完整生命周期；不得写生产代码、测试代码或 schema。 |
| 资金数据治理 | 产品 02/03/05 已拆分承接 Manifest、checkpoint、watermark、余额快照、重放、差异报告、人工处理和指标只读边界；04 仅保留兼容索引。 | `GOV-GATE-*`、`TDD-B8-RED-*`、治理物理落点候选、Manifest/H2 范围、dry-run/apply、指标水位隔离、治理导出和大数据消费边界测试矩阵。 | 不得创建空壳模块，不得让治理任务反写资金事实，不得用普通指标快照替代余额确认。 |
| VCC、全球账户和收单业务支持 | 业务 PRD 06/07/08 已明确只通过场景交易 capability pack 接入统一资金内核。 | 业务状态映射、外部引用、脱敏证据、资金事实映射、P0/P1 回归测试和外部规则待确认矩阵。 | 不得新增平行钱包、平行账本、平行清结算、平行对账或平行归档链路。 |

## 生产交付判定

本设计包的交付口径是目标一致，可作为设计评审、差距复核和编码准入输入。生产交付必须按 MVP 任务切片证明，不能因为文档齐备就替代已完成实现、已通过测试、已同步 DDL/H2 schema、已确认外部规则和已完成上线审批。若工作树存在未提交代码、测试或其他草稿变更，未提交内容只作为未纳入基线的评审输入，提交或纳入 Execution Grant 前不得替代已冻结基线。

交付状态分三态：

| 状态 | 可作为 | 不可作为 |
| --- | --- | --- |
| 评审输入态 | 设计讨论、CR 输入、差距复核材料。 | 冻结基线、Execution Grant 依据、Done 证据。 |
| 基线准入态 | 已提交或明确纳入基线的设计、OpenSpec、Harness Plan 和测试要求。 | 生产 Done 证据，除非同步具备代码、测试、DDL/H2、验证命令和审计证据包。 |
| 生产交付态 | MVP 任务范围内实现、测试、验证、审批、审计证据和残余风险闭合后的交付结论。 | 超出 Execution Grant 范围的能力完成声明。 |

| 设计域 | 目标一致性 | 生产交付判定 | 进入生产交付前必须补齐 |
| --- | --- | --- | --- |
| 02 交易、路由、钱包、账目与投影 | 已对齐。PRD、DSL、系分和 TDD 都围绕资金事实、权益快照、route snapshot、posting plan、ledger entry、余额投影、交易投影和审计证据链展开；VCC 发卡通过卡绑定资金/信用子账户、主账户约束和统一交易/账本/投影边界承接。 | 可进入 A0 至 A4 的差距复核和编码准入；权益金额组件进入编码时还需明确公共契约、枚举、route/posting/replay 消费、目标态范围和权益准入证明；VCC 账户层级、支付工具能力准入、资金责任解析和 Spend Rule 控制进入编码时必须走 B2/B4 或 P2 独立 Execution Grant。 | 目标测试资产、余额断言、失败无副作用、幂等、公共契约授权、表结构、H2 schema、权益快照事实源、零实付表达、独立伴随指令原子性、退款分摊确定性规则、补充权益事实模型、专业确认状态、审计证据包、使用者解释视图、证据最小化、外部规则核验状态、卡绑定子账户与主账户约束证据和 `fixtureLevel` 差距复核。 |
| 03 清结算与对账 | 已对齐。清分、清算、结算、出款、对账、差错、调账核销和追偿对象边界清楚。 | 可进入 TDD 分析；整体编码准入未打开。即使存在实现草案、模块骨架或候选能力，也只能作为差距复核输入；未纳入独立 Execution Grant、DDL/H2、服务级测试和外部规则确认前，不能声明清结算、对账或出款生命周期 Done。 | 独立 OpenSpec change、Execution Grant、是否扩展出款前准入候选能力、`CLS-GATE-*`、运营补事实命令白名单、清结算与对账首批 Red、DDL/H2 schema、Entity/Mapper、服务契约、状态机、NFR 假设、观测告警、对账和清结算服务级测试。 |
| B8 资金数据治理边界 | 已对齐。余额检查点和交易投影重放拆入产品 02，清结算批次视图重放拆入产品 03，工程门禁和指标只读边界拆入产品 05；04 仅保留兼容索引。 | 可进入 TDD 分析；已有局部交易投影重放基线不等于 Manifest、余额快照、异常人工处理和指标边界生产完成，整体编码准入未打开。 | 独立 Execution Grant、`GOV-GATE-*`、治理物理落点、B8 首批 Red、Manifest、账本余额快照覆盖模式、权益快照冷热读取、指标水位隔离、范围锁、回滚/续跑、差异报告、人工处理闭环、大数据消费边界、NFR 假设、观测告警和边界测试。 |
| 外部规则、合规、税务、会计、轨道和敏感数据 | 已列出待确认项和不覆盖范围。 | 不作为生产启用结论。 | 规则来源、版本或发布日期、生效日期、适用主体或适用范围、适用法域、核验日期、确认方、确认状态、审计和敏感数据处理方案。 |

### 生产交付签出证据包

生产交付签出不是一份新 PRD 或一张图，而是一组能让产品、架构、测试、SRE、财务、风控、安全和合规共同复核的证据。每个 MVP 任务进入生产交付评审前，必须把下列证据汇总到任务说明、OpenSpec/Harness、发布评审或交付说明中。

| 证据项 | 必须包含 | 缺失时结论 |
| --- | --- | --- |
| 产品签出 | `productGoal`、`mvpScenario`、验收 ID、使用者解释、外部规则状态、Not Done 范围和业务 owner。 | 不能声明产品可交付，只能作为设计输入态。 |
| 架构签出 | 服务入口、模块边界、公共契约、表/索引、状态机、事务边界、幂等、补偿、观测、安全和 ADR/取舍记录。 | 不能进入 Harness/GSD/CAD 或生产发布评审。 |
| 资金证据 | 主体、账户类型、账目、币种、route snapshot、posting plan、LedgerEntry、余额投影、借贷平衡、幂等和失败无副作用。 | 涉及资金变化时阻断。 |
| 测试验证 | 首批 Red 变绿、服务级测试、契约测试、边界测试、H2/DDL、静态检查和本任务验证命令。 | Not Done；未执行时必须说明环境限制和替代证据。 |
| 运行证据 | 指标、日志、trace、告警、Dashboard、Runbook、灰度开关、回滚或暂停动作和人工兜底。 | 涉及生产行为时阻断或降级为 Conditional Done。 |
| 专业确认 | 法务、合规、财务、税务、通道、银行、卡组织、安全或数据责任人的确认状态、适用范围、有效期和脱敏证据引用。 | 影响资金释放、出款、敏感数据或外部规则时阻断。 |
| 残余风险 | 未覆盖范围、已知缺口、回退方案、下一门禁、风险接受人和复核时间。 | 不得声明 Done。 |

首轮编码从 A0 基线核验进入：先复核钱包账户、支付工具、账本、账目、余额投影、现有测试资产、工作树和验证环境，再由用户确认 A1 至 A4 的 Execution Grant。A1 至 A4 只覆盖交易主链路、授权、余额控制和 DSL 执行化；支付工具与 Spend Rule 生产可用性必须先走 B2/B4 Round 0 准入卡；B7/B8 仍只进入 TDD 分析和独立授权准备。

### 生产 Done 证据门禁

生产 Done 不是设计结论，而是 Execution Grant 范围内的实现、测试、验证、审计和外部确认共同成立。任一门禁缺失时，交付结论只能写成 Conditional Done、Not Done、设计输入态或 TDD 分析完成。

| 门禁 | Done 必须具备 | 缺失时结论 |
| --- | --- | --- |
| Execution Grant 闭合 | `abilityBatch`、`authorityBaseline`、`writeScope`、`noWriteScope`、`firstRedSet`、`verificationAndStop` 均已确认。 | Not Done；只能做设计、差距复核或 TDD 分析。 |
| 写入范围内实现完成 | 代码、公共契约、状态机、表结构、H2 schema 和运行时配置只在授权范围内变更。 | Not Done；越权变更必须回退、拆分或重新授权。 |
| 测试资产通过 | 首批 Red 已变绿，服务级测试、契约测试、边界测试和回归命令按范围通过。 | Not Done；未执行时必须说明环境或依赖限制。 |
| 资金不变量成立 | 状态、主体、账户类型、`normalBalanceSide`、账目、币种、route snapshot、posting plan、LedgerEntry、余额投影、借贷平衡、余额影响、幂等和失败无副作用均有证据。 | Not Done；不得用状态或数量断言替代。 |
| DDL/H2 一致 | 涉及持久化时生产 DDL、H2 schema、Entity/Mapper、唯一键和索引同步闭合。 | Not Done；不涉及时写明不适用。 |
| 观测审计可解释 | traceId、业务引用、审批号、凭证摘要、差异报告、告警、人工处理入口和脱敏证据可追溯。 | Conditional Done 或 Not Done；触碰真实资金、高危操作或敏感数据时缺失即阻断。 |
| 外部规则确认 | 通道、银行、卡组织、ACH、PSP、FX、合规、税务、会计或敏感数据规则有确认状态和不覆盖范围。 | Conditional Done；影响资金释放、出款或敏感数据时 Not Done。 |
| 回滚和 Runbook | 涉及生产行为、批处理、出款、归档 apply 或高危运营动作时，有暂停、重试、补偿、重放、回滚和人工兜底。 | Conditional Done 或 Not Done；无人工兜底的资金写入能力不得上线。 |
| Not Done 清单 | 未覆盖范围、残余风险、后续任务和阻断条件写清楚。 | 不得声明 Done；交付说明必须降级。 |

MVP 任务交付说明应显式给出 Done 判定，避免只列测试结果却不说明生产边界：

| 输出项 | 填写口径 |
| --- | --- |
| `deliveryConclusion` | `DONE`、`CONDITIONAL_DONE` 或 `NOT_DONE`。 |
| `doneScope` | 本结论覆盖的能力、文件、模块、表、测试和验证命令。 |
| `moneyEvidence` | 资金不变量证据，至少覆盖 DSL 借贷表命中行、不适用行、主体、金额、账户类型、`normalBalanceSide`、账目、route、posting、entry、projection、借贷平衡、余额影响、幂等和审计中的适用项。 |
| `notDoneScope` | 未覆盖能力、未执行验证、未确认外部规则、未落 DDL/H2 或未补 Runbook 的范围。 |
| `nextGate` | 后续进入 A1-A4、B7、B8 或 P2 的准入条件。 |

### 阻断和降级口径

交付评审中发现下列情况时，结论必须从“通过”降为“带条件通过”或“阻断”，不能写成普通建议项。

| 情况 | 结论 | 处理 |
| --- | --- | --- |
| 产品场景、DSL caseId、系分服务入口或 TDD 用例任一侧缺失。 | 阻断。 | 先补齐跨文档映射，再进入编码或验收。 |
| 有资金变化但未断言余额桶、posting plan、ledger entry、投影和幂等。 | 阻断。 | 补测试证据或缩小交付范围。 |
| 新增或修改公共契约、服务入口、枚举、Request/Query/DTO、状态机或表结构，但 Execution Grant 未授权。 | 阻断。 | 回到任务授权，明确允许范围和目标态语义。 |
| 含权益任务缺 Phase 能力边界、JSON 夹具级别、权益快照事实源、零实付表达、平台补贴表达、独立伴随指令原子性、储值预付口径、退款分摊粒度、退款分摊确定性规则、历史无快照处理策略、补充权益事实模型、专业确认状态、审计证据包、使用者解释视图、证据最小化或外部规则核验状态。 | 阻断或降级为 contract-only。 | 补权益准入证明；未补前不得进入生产资金流 Done。 |
| 清结算、对账或出款通过运营动作追加资金事实，但缺运营补事实命令白名单、审批证据、幂等键、原事实引用或失败无副作用测试。 | 阻断。 | 补白名单命令和 B7 首批 Red；未列入白名单的动作只能生成处理单、差异报告或审计记录。 |
| 事实留存、重放、余额快照、指标边界或大数据消费缺治理物理落点、边界测试、指标水位隔离测试或 B8 首批 Red。 | 阻断或降级为 dry-run。 | 先补 Execution Grant 决策、B8 首批 Red 和边界测试，再进入 apply 或正式水位推进。 |
| 使用 `CONTRACT_ONLY` JSON 样例、请求态权益快照或 `contextVariables` 过渡字段作为 route/posting/replay、清结算、对账、投影、归档、冷热读取或治理重放生产 Done 证据。 | 阻断。 | 改为资金流夹具、不可变事实源和服务级测试证据；或降级为契约承载。 |
| 专业确认证据包缺失、过期、被撤销、适用范围不匹配或证据引用含敏感原文。 | 阻断或降级为 contract-only。 | 补确认记录、有效期、范围、撤销处理和脱敏证据引用。 |
| 清结算、对账、归档、重放或指标边界只有设计，没有 DDL/H2、服务级测试或边界测试。 | 设计评审可作为输入或带条件通过；生产完成或 MVP 编码任务 Done 评审为阻断。 | 只能声明设计输入态；若目标是生产完成，必须先补实现和测试证据。 |
| 外部规则、合规、税务、会计、通道或敏感数据缺确认。 | 带条件通过或阻断。 | 写清规则来源、版本或发布日期、生效日期、适用主体或适用范围、适用法域、核验日期、确认方、确认状态、补齐时点和不覆盖范围；影响资金释放或敏感数据时阻断。 |

### 结论映射

文档评审和 MVP 编码任务使用不同结论词，必须按下表映射，不能把设计输入态或设计评审通过等同于生产完成。

| 中文评审结论 | OpenSpec/Harness 结论 | 使用边界 |
| --- | --- | --- |
| 通过 | 可进入 Done 评审。 | 设计闭环已成立；只有 Execution Grant 范围内的代码、契约、DDL/H2、测试、验证和待确认边界都闭合时，才能声明 Done。 |
| 带条件通过 | Conditional Done，或仅作为设计评审带条件。 | 本任务 P0/P1/P2 能力证据闭合，但外部规则、非本任务扩展、性能容量或人工确认项仍有明确不覆盖范围；若缺少本任务生产目标必需的 DDL/H2、服务级测试或审计证据，则不能写 Conditional Done。 |
| 阻断 | Not Done。 | 资金红线、公共契约授权、DDL/H2、服务级测试、失败无副作用、幂等或审计证据缺失时使用；先补齐缺口再继续。 |

### 评审执行路径

评审时按下列步骤走，避免只看单份文档或只看测试结果。

| 步骤 | 动作 | 输出 |
| --- | --- | --- |
| 1. 确认范围 | 选择本次评审的设计域、MVP 任务切片、覆盖索引、产品验收 ID、DSL caseId、TDD 用例和红线编号。 | 评审范围和非目标。 |
| 2. 检查设计闭环 | 从 PRD 反查 DSL、系分、TDD，再从 TDD 反查 PRD，确认没有孤立场景或孤立测试。 | 通过、带条件通过或阻断。 |
| 3. 检查授权边界 | 对照 Execution Grant，确认公共契约、服务入口、枚举、Request/Query/DTO、状态机、表结构、模块边界和生产行为是否被授权。 | 允许写入范围和禁止事项。 |
| 4. 检查实现证据 | 核对代码、DDL/H2 schema、服务契约、状态机、幂等、观测审计和架构边界证据。 | 实现证据包。 |
| 5. 检查测试证据 | 核对测试资产、核心断言、验证命令、结果、未覆盖项和残余风险。 | 测试证据包。 |
| 6. 给出结论 | 按阻断和降级口径判定通过、带条件通过或阻断；MVP 编码任务按 Done、Conditional Done、Not Done。 | 评审结论和准入动作。 |

## 资金安全总控

资金安全不是单一功能，而是贯穿产品、DSL、系分和 TDD 的共同控制。任一新增能力纳入稳定设计或进入编码实现时，都必须能落到下列控制面。

| 控制面 | 必须成立 | 主要证据 |
| --- | --- | --- |
| 主体安全 | 入账主体只能是资金账户、信用账户、预算组或解析后的平台账户角色。 | PRD 概念边界、Route DSL、LedgerEntry 断言。 |
| 金额安全 | 金额为正、币种明确、精度合法、累计处理不超剩余可处理金额。 | DSL JSON、金额临界值测试、posting plan 平衡。 |
| 路径安全 | 正向交易按当前合法关系选路，逆向交易优先按原 route snapshot 回放。 | RouteSnapshot、RoutingDecision、Route Replay 测试。 |
| 账务安全 | 余额只能由账本分录派生，投影、日志、报表和指标不得反写事实。 | LedgerEntry、BalanceProjection、红线失败测试。 |
| 操作安全 | 调账、核销、结算锁定、出款、归档 apply 和敏感导出必须有权限、审批和审计。 | 操作日志、审批号、凭证、traceId、权限测试。 |
| 生产安全 | 清结算、对账、事实留存和重放必须有范围、幂等、差异报告、告警和人工兜底。 | 系分 03/04/05、TDD 并发和红线用例。 |

## 准入结论

本文档包可作为支付资金底座生产落地设计评审和交付差距复核的基线。若新增能力无法至少定位到产品场景、DSL 契约、系分模块或 TDD 断言中的一个入口，应先补设计归属；进入编码前还必须补齐产品场景、DSL 契约、系分模块和 TDD 断言的完整映射。

### 编码准入裁决

| 项 | 裁决 | 约束 |
| --- | --- | --- |
| 设计文档变更 | 可作为提交前设计基线候选。 | 提交或明确纳入 Execution Grant 前仍是评审输入态，不得替代冻结基线、编码依据或 Done 证据。 |
| P0 钱包、账本、账目、余额投影、对账、清分、清算、结算、账本余额快照和资金数据治理证据 | 条件准入或未准入，取决于对应 Execution Grant。 | 钱包、账本、账目和余额投影可作为基础事实条件准入候选；清结算与对账、资金数据治理可进入 TDD 分析，但仍需独立 OpenSpec change 和 Execution Grant，不得因 P0 优先级被默认授权进入编码。 |
| P1 直接交易、授权交易、余额控制、交易投影和重投影 | 条件准入。 | 只允许在冻结基线后，通过 A1 至 A4 的 Execution Grant 逐切片进入；每个切片必须列明写入范围、公共契约、DDL/H2、目标测试、验证命令和不覆盖范围。涉及交易投影或重投影时，必须在对应切片列明投影断言、重投影验证和只读边界。 |
| P2 VCC、全球账户和收单业务支持 | 不开放默认编码准入。 | 只能通过业务专项 PRD、系分、TDD 和 Execution Grant 使用资金底座能力；不得把业务模式、轨道协议、风控或合规结论沉入统一资金内核。ACH 或银行转账只作为上层业务或外部轨道输入，资金底座只承接归一资金事实、外部引用、对账差错、追偿、调账核销和审计；若业务专项使用 ACH 或银行转账，必须回挂 `ACH-BOUNDARY-001` 至 `ACH-BOUNDARY-006`、`AC-RAIL-002A` 至 `AC-RAIL-007`、`TDD-RAIL-002` 至 `TDD-RAIL-007`。 |
| 代码和测试变更 | 当前不授权。 | 本次范围只覆盖设计文档、OpenSpec 和 Harness Plan；生产代码、测试代码、DDL/H2 schema 或运行时配置的写入必须等待明确编码授权。 |
