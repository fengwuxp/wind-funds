# 支付资金底座设计文档总入口

## 目录定位

本目录承载支付资金底座的最终版设计基线，用于产品评审、系分设计、DSL 契约承接、测试驱动设计和进入编码前的生产准入评审。

本目录只保留最终设计口径，不承载过程任务拆解或变更过程说明。编码前的第一步是基于本文档包做代码、测试、DDL 和现有实现差距复核。

## 按角色使用路径

不同角色使用本设计包时关注点不同，但最终都必须回到同一条证据链：产品场景、DSL 契约、系分落点和 TDD 断言。

| 使用者 | 先读 | 必须拿到的结论 | 不应跳过 |
| --- | --- | --- | --- |
| 产品和业务负责人 | `产品设计/01`、`产品设计/05` | 场景是否真实、目标是否清楚、哪些能力属于默认主链路、哪些是扩展或外部待确认。 | 概念边界、非目标、产品红线和验收矩阵。 |
| 运营、财务和风控 | `产品设计/03`、`产品设计/05`、`系分设计/05` | 异常如何阻断、清结算和对账如何闭环、谁有权限处理、处理后如何留痕。 | 差错单、审批、凭证、核销、重新对账和追偿链路。 |
| 架构和研发 | `DSL设计`、`系分设计/01`、相关系分分册 | 资金事实如何进入 DSL，落到哪些模块、服务、表、状态机和事务边界。 | 账本事实源、route snapshot、幂等键、唯一约束和金融红线。 |
| 测试 | `产品设计/05`、`TDD设计`、`系分设计/05` | 每个场景的正常、异常、边界、并发和 must-fail 用例如何落到测试资产。 | 余额桶断言、posting plan 平衡、ledger entry、投影和失败无副作用。 |
| 安全、合规和审计 | `产品设计/01`、`系分设计/05`、外部参考清单 | 敏感数据、权限、导出、审批、外部规则和合规待确认项是否清楚。 | 本设计不替代法务、税务、会计、合规或持牌机构最终确认。 |

## 统一术语映射

授权链路和商户结算链路都会出现“结算”字样。为了避免产品、DSL、系分和测试之间混用，本文档包采用以下映射：

| 产品表达 | DSL / 系分 / TDD 表达 | 语义边界 |
| --- | --- | --- |
| 授权结算 | 授权完成，事件使用 `AUTHORIZATION_TRANSACTION / SETTLE`。 | 指授权占用转为实际消费、扣款或待清算结果；不等同于商户结算单或出款。 |
| 授权部分结算 | 授权部分完成，事件仍使用 `SETTLE`，以原授权为引用。 | 指只完成部分授权金额；累计完成金额不得超过原授权金额。 |
| 已结算金额 | 授权链路中优先称为已完成金额。 | 指原授权已经完成的累计金额；只用于约束退款、拒付、过期释放和迟到事件。 |
| 结算后退款 | 授权完成后退款，事件使用 `AUTH_REFUND` 或对应退款链路。 | 必须基于原授权完成路径反向，不按当前绑定关系重新选路。 |
| 授权撤销 | 外部明确撤销或冲正，事件使用 `REVERSAL`。 | 释放剩余授权占用，终态为撤销；不能和系统过期混成同一结果。 |
| 授权过期 | 系统根据授权有效期释放剩余占用，事件使用 `EXPIRE`。 | 可复用授权释放账务路径，但状态、释放原因、审计和过期金额必须保留 `EXPIRE` 语义。 |
| 无前置授权强制完成 | 使用 `SETTLE` 的强制完成模式。 | 不新增独立强制完成事件，不伪造授权占用；必须有策略、上限、原因和审计。 |
| 通道预处理与事件编排类场景 | 上层业务或通道适配层归一后的场景。 | 不作为资金底座默认 DSL 和系分场景；资金底座只接收明确资金事实。 |
| 结算锁定 | 清结算链路的 `AVAILABLE -> SETTLEMENT`。 | 指商户、合作方或企业出款前锁定可结算余额；不代表外部出款成功。 |
| `SETTLEMENT` 账目 | 出款中或结算处理中锁定资金。 | 是余额桶，不是授权生命周期的 `SETTLE` 事件。 |

| 检查项 | 准入要求 |
| --- | --- |
| 文档范围 | 最终设计只以 `产品设计`、`DSL设计`、`系分设计`、`TDD设计` 为入口。 |
| 最终口径 | 最终文档不得依赖历史过程材料或变更过程说明。 |
| 版本控制 | 最终设计目录下的新文档必须能被 Git 正常追踪，不能因 ignore 规则丢失。 |
| 术语一致 | 产品表达、DSL 事件、系分状态和 TDD 用例必须能按“统一术语映射”互相解释。 |
| 场景闭合 | 正向、逆向、异常、人工处理、幂等、重放、对账差错和红线用例必须有验收承接。 |
| 资金红线 | 不得绕过账本事实、不得直接改余额投影、不得用日志或报表修复余额、不得混同冻结和消费。 |

| 外部规则 | 外部机构、卡组织、ACH、银行、PSP、Highnote、Stripe 等公开资料只作参考；上线前必须确认版本、法域、生效日期、确认方和确认结论。 |
| 编码入口 | 进入编码前必须先做代码、测试、DDL 和现有行为差距复核，再拆分开发任务。 |

## 资金安全总控

资金安全不是单一功能，而是贯穿产品、DSL、系分和 TDD 的共同控制。任一新增能力进入设计或编码前，都必须能落到下列控制面。

| 控制面 | 必须成立 | 主要证据 |
| --- | --- | --- |
| 主体安全 | 入账主体只能是资金账户、信用账户、预算组或解析后的平台账户角色。 | PRD 概念边界、Route DSL、LedgerEntry 断言。 |
| 金额安全 | 金额为正、币种明确、精度合法、累计处理不超剩余可处理金额。 | DSL JSON、金额临界值测试、posting plan 平衡。 |
| 路径安全 | 正向交易按当前合法关系选路，逆向交易优先按原 route snapshot 回放。 | RouteSnapshot、RoutingDecision、Route Replay 测试。 |
| 账务安全 | 余额只能由账本分录派生，投影、日志、报表和指标不得反写事实。 | LedgerEntry、BalanceProjection、红线失败测试。 |
| 操作安全 | 调账、核销、结算锁定、出款、归档 apply 和敏感导出必须有权限、审批和审计。 | 操作日志、审批号、凭证、traceId、权限测试。 |
| 生产安全 | 清结算、对账、归档和重放必须有范围、幂等、差异报告、告警和人工兜底。 | 系分 03/04/05、TDD 并发和红线用例。 |

## 准入结论

本文档包可作为支付资金底座进入生产落地设计评审和编码前差距复核的基线。若新增能力无法落到产品场景、DSL 契约、系分模块和 TDD 断言中的至少一个明确位置，应先补齐设计再进入编码。
