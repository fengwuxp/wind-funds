# 收单业务系统边界与落地计划

## 1. 系统结论

`wind-funds` 应以资金底座方式支撑收单业务。系统架构上推荐采用“外部收单产品 / 支付网关 / 商户风控系统 + wind-funds 资金底座”的边界，而不是立即在本仓库新增完整收单系统。

当前不建议直接新增 `acquiring-face` / `acquiring-impl` 物理模块。更稳妥的方式是先定义逻辑边界和端口：外部收单系统通过中立收单事件或资金指令接入，`wind-funds` 内部继续由交易、路由、钱包账户、账本、清结算、对账、投影和治理能力承接资金结果。只有当业务明确要求本仓库承接支付订单、支付尝试、通道状态和收单生命周期编排时，再通过独立 ADR 与 Execution Grant 判断是否新增收单模块。

## 1.1 需求背景、问题和不做的风险

需求背景是未来可能出现收单业务，但业务模式、主体角色、支付轨道、法域、资质和外部规则尚未确定。当前需要先把资金底座的可承接范围沉淀下来，避免后续编码时把收单产品、支付网关、通道协议、商户风控和资金账务混成一个系统。

核心问题是收单链路天然横跨业务订单、支付尝试、通道清算、商户结算、银行到账、拒付争议和财务核对。如果边界不清，`wind-funds` 很容易从资金底座膨胀为完整收单系统。

不做的风险包括外部账户直接入账、授权和清算状态混用、对账差异直接改账、敏感卡数据进入资金快照、未确认规则进入默认放行路径，以及未获得编码授权就改动公共契约或表结构。

## 1.2 目标、非目标和系统边界

目标是定义 `wind-funds` 对收单业务的系统边界、接口契约、数据边界、安全边界、测试设计和分期落地计划。

非目标是不设计完整收单系统、不新增生产代码、不修改既有 PRD/DSL/系分/TDD/OpenSpec、不声明任何法务合规、财税会计、PCI 或外部规则的最终结论。

系统边界是外部收单产品维护支付订单和支付尝试，支付网关维护 PSP/银行/卡组织协议，风控合规系统维护商户准入和风险策略，`wind-funds` 只承接确认后的资金事件、资金账户、账本、清结算、对账、出款、投影和治理。

数据边界是资金底座只保存外部引用、脱敏摘要、digest、规则版本和审计引用，不保存 PAN、CVV、密钥、完整原始报文或生产通道配置。

安全边界是敏感数据、通道密钥、Token Vault、PCI 范围系统和外部规则核验材料必须在专门系统或专业确认流程中处理；`wind-funds` 只保存最小化证据引用和确认状态。

## 1.3 概要设计、核心方案和关键依赖

概要设计采用端口隔离方式：外部系统通过收单事件接入端口、通道对账来源端口、风险合规决策端口和支付尝试引用端口向资金底座提供事实或引用；内部模块继续沿交易、路由、钱包账户、账本、清结算、对账、投影和治理链路推进。

核心方案是先以逻辑端口承接中立收单事件，不新增物理收单模块；后续如果业务确认需要在本仓库维护支付订单、支付尝试和通道状态，再用 ADR 判断是否新增 `acquiring-face` / `acquiring-impl`。

关键依赖包括外部收单产品的事件最终性、支付网关的外部引用和对账文件、风控合规的阻断结论、财务会计的金额口径确认、法务合规的外部规则确认和现有资金底座的账务不变量。

同步关系只允许外部系统提交已确认事件或查询只读视图；异步关系用于通道通知、对账文件、出款回单、投影更新、归档重放和告警事件。

## 2. 上下文边界

| 系统或模块 | 职责 | 与 wind-funds 的关系 |
| --- | --- | --- |
| 业务交易系统 | 订单、履约、售后、商户结算诉求。 | 上游业务事实来源，只传业务引用和已确认结果。 |
| 外部收单产品 | 支付订单、支付尝试、授权、扣款、退款、通道通知、补单。 | 上游支付信息流来源，向资金底座发送中立事件。 |
| 支付网关 / 通道适配 | PSP、银行、收单行、卡组织协议、签名、加密、重试。 | 外部系统，提供通道引用、回调结果、对账文件和回单。 |
| 商户 / 风控 / 合规系统 | 商户资料、KYB、MCC、风险等级、名单筛查、结算阻断。 | 外部系统，提供规则版本、阻断结论和专业确认状态。 |
| wind-funds | 资金事实、账户、路由、账本、清结算、对账、出款、投影、归档。 | 本仓库职责。 |
| 财务 / 数据仓库 | 财务凭证、审计、报表和经营分析。 | 只读消费治理导出、账务报表和审计摘要，不反写资金事实。 |

## 3. 内部能力落点

| 能力 | 当前推荐落点 | 说明 |
| --- | --- | --- |
| 收单事件准入 | transaction 入口或未来独立接入端口 | 接收中立事件、校验幂等、构造资金指令。 |
| 支付尝试引用 | transaction context / DSL 引用对象 | 保存 `paymentOrderId`、`paymentAttemptId`、通道引用和脱敏摘要，不保存敏感卡数据。 |
| 资金路由 | transaction-impl route resolver | 解析商户、平台、费用、补贴、预留和追偿路径。 |
| 商户账户 | wallet / transaction 资金账户模型 | 商户经营主体需要解析为内部资金账户或平台账户角色后才能入账。 |
| 账本事实 | ledger | 只接收 posting plan，不理解通道协议。 |
| 清结算与对账 | reconciliation 逻辑能力 | 承接可清分明细、清分批次、清算候选、清算批次、结算单、出款单和差错。 |
| 投影 | transaction projection / ledger projection | 商户账单、运营时间线、财务对账视图只读派生。 |
| 归档重放 | governance 逻辑能力 | 负责归档、重放、差异报告和人工处理引用，不重新入账。 |

## 4. 端口和契约

本节是接口设计，不代表当前已经新增 Java 公共契约。编码前必须通过独立 OpenSpec change 和 Execution Grant 明确是否允许新增 DTO、Request、Query、枚举、表结构和 H2 schema。

### 4.1 外部输入端口

| 端口 | 输入 | 处理要求 |
| --- | --- | --- |
| AcquiringEventIngestPort | 外部收单事件、事件类型、金额、币种、商户、外部引用、摘要。 | 幂等、乱序容忍、敏感字段过滤、失败无副作用。 |
| PaymentAttemptReferencePort | 支付订单和支付尝试引用。 | 只读引用，不反向调用外部收单产品重算资金结果。 |
| ChannelReconciliationSourcePort | 通道流水、清分文件、银行流水、出款回单。 | 进入对账批次和差错闭环，不直接改账。 |
| RiskAndComplianceDecisionPort | 风控结论、名单筛查、结算阻断、规则版本。 | 可阻断清算、结算和出款，必须保留确认状态。 |

### 4.2 内部输出端口

| 输出 | 使用方 | 边界 |
| --- | --- | --- |
| FundsTransactionCreated | 外部业务、运营、投影 | 只表达资金事实已创建，不等于外部到账。 |
| LedgerPosted | 余额投影、交易投影、清结算 | 账本已过账，后续清分可引用。 |
| ClearingCandidateReady | 清结算模块 | 只表示可进入清结算候选，不自动入账。 |
| SettlementOrderReady | 商户/运营/财务 | 只表示结算单已生成或锁定，不等于出款成功。 |
| PayoutResultChanged | 商户/财务/对账 | 外部受理、成功、失败、退回、金额不一致必须分开。 |
| ReconciliationExceptionRaised | 运营/财务/风控 | 差错进入处理，不直接修正历史事实。 |

## 4.3 详细设计、模块和数据设计

| 模块 | 详细设计要点 | 数据设计要点 |
| --- | --- | --- |
| transaction-face | 定义资金指令、收单事件引用、支付尝试引用、拒付引用和敏感证据引用的契约。 | 只定义 DTO / Request / Query，不暴露 Entity。 |
| transaction-impl | 校验事件幂等、摘要、状态、金额币种和外部引用，编排 route resolver 和 ledger 写入。 | 需要唯一键、幂等键、事件摘要、外部引用索引和处理状态。 |
| route resolver | 将收单事件解析为商户、平台、费用、补贴、预留和追偿路径。 | route snapshot 必须保留原路径，支持退款、拒付和重放。 |
| wallet / account | 提供商户资金账户、平台账户角色和余额桶约束。 | 待清算、可结算、结算锁定、在途、预留和追偿必须分桶。 |
| ledger | 承接 posting plan 并生成账本交易和分录。 | 分录必须平衡，余额投影可重建，不保存外部协议细节。 |
| reconciliation | 处理对账任务、匹配结果、差错、清分、清算、结算、出款和追偿。 | 清分批次、清算批次、结算单、出款单和差错单分别建模。 |
| governance | 处理归档、重放、差异报告和人工处理引用。 | Manifest、checkpoint、watermark、digest、审计引用和差异报告独立管理。 |

## 5. DSL 调整方向

未确认业务模式前不建议新增完整卡组织或 PSP 专用 DSL。建议先按中立引用补充：

| DSL 元素 | 作用 | 边界 |
| --- | --- | --- |
| `AcquiringEventRef` | 记录外部收单事件来源、事件号、事件类型、摘要和确认时间。 | 不保存原始报文和敏感支付数据。 |
| `PaymentAttemptRef` | 记录支付订单、支付尝试、通道、支付方式和外部引用。 | 不承接支付尝试生命周期状态机。 |
| `ChannelSettlementRef` | 记录通道清分、结算文件、银行流水或回单引用。 | 只用于对账和审计，不直接生成账务。 |
| `DisputeRef` | 记录拒付、争议、检索或追偿引用。 | 与退款区分，保留原因、凭证和审计摘要。 |
| `SensitiveEvidenceRef` | 记录脱敏证据、digest、权限和确认状态。 | 不保存 PAN、CVV、密钥、完整原文。 |

## 6. 状态机和一致性边界

| 链路 | 状态边界 | 系统要求 |
| --- | --- | --- |
| 支付信息流 | initiated、authorized、captured、failed、refunded、disputed。 | 外部收单产品维护，`wind-funds` 只接收已确认事件。 |
| 资金事实流 | instruction accepted、transaction created、route resolved、ledger posted。 | 由 transaction / ledger 保证事务和幂等。 |
| 清结算流 | split ready、clearing candidate、clearing confirmed、settlement locked。 | 由 reconciliation 逻辑能力承接，前置对账和阻断规则不可绕过。 |
| 出款流 | payout prepared、submitted、accepted、in transit、paid、failed、returned。 | 外部受理不等于到账，成功需要回单或对账确认。 |
| 差错流 | detected、classified、blocked、adjusting、resolved、reconciled。 | 差异必须经过审批、凭证、调账和重新对账。 |

### 6.1 主流程、异常流程、补偿流程和人工介入

主流程是外部收单事件进入接入端口后，先完成幂等和敏感数据过滤，再生成或引用资金指令，随后完成交易生命周期、route snapshot、posting plan、ledger entry、余额投影、交易投影和清结算候选。

异常流程包括重复事件、乱序事件、外部引用缺失、金额币种不一致、风控阻断、清算前置对账失败、结算锁定冲突、出款回单冲突、拒付与退款碰撞、归档重放范围不完整。

补偿流程只能追加补事实、冲正、调账、追偿或重新对账，不能覆盖原交易、原分录、原 route snapshot 或原投影事实。

人工介入入口包括事件隔离、差错复核、证据补录、结算阻断解除、调账审批、追偿处理、重放范围确认和审计导出审批。

## 7. 数据和安全边界

1. 资金底座不得保存 PAN、CVV、完整有效期、磁道数据、通道密钥、原始敏感报文。
2. 卡、VA、外部账户、通道商户号、银行账户只能作为引用或对账来源，不得作为账务主体。
3. 外部规则核验状态至少包含规则来源、版本或发布日期、生效日期、适用范围、适用法域、核验日期、确认方和确认状态。
4. 商户待结算资金、客户资金、平台自有资金、保证金、风险预留、手续费收入和通道成本必须拆分表达。
5. 报表数仓、BI 和离线指标只能通过治理导出或只读投影消费，不允许反写资金事实。

## 8. TDD 和验收矩阵

测试设计按契约测试、服务级流程测试、数据库/H2 测试、架构边界测试、红线测试和回归测试分层。未进入编码前，本节只作为未来 ACQ 批次的测试准入矩阵。

| 用例 | 测试目标 | 必须失败 |
| --- | --- | --- |
| ACQ-TDD-001 | 外部收单支付成功事件生成资金交易、route、posting 和商户 `CLEARING`。 | 重复事件重复入账。 |
| ACQ-TDD-002 | 支付尝试失败或授权拒绝不生成 route、posting、entry。 | 失败事件写账。 |
| ACQ-TDD-003 | capture 后进入商户待清算，但不直接可结算。 | capture 成功直接进入 `AVAILABLE`。 |
| ACQ-TDD-004 | 清分确认只固化候选，不触发账务。 | 清分批次确认写账。 |
| ACQ-TDD-005 | 清算确认必须经过前置对账和阻断规则。 | 重大差错仍放行。 |
| ACQ-TDD-006 | 结算锁定不等于出款成功。 | 外部受理展示为到账。 |
| ACQ-TDD-007 | 退款、撤销、冲正、拒付沿原路径回放。 | 工具换绑后按当前关系重选路。 |
| ACQ-TDD-008 | 拒付与退款可区分，并保留原因、凭证和审计摘要。 | 拒付压缩成普通退款。 |
| ACQ-TDD-009 | 通道文件晚到、重复、金额不一致进入差错。 | 静默覆盖或直接改账。 |
| ACQ-TDD-010 | 敏感卡数据和原始报文不进入日志、快照、归档或导出。 | 保存 PAN、CVV 或密钥原文。 |

非功能、性能、容量、可用性、兼容性和生产就绪要求必须在具体编码批次补齐。至少包括事件吞吐、通道文件批量大小、批次锁、重试窗口、幂等冲突、告警指标、Runbook、灰度开关、回滚或补偿方案。

## 9. OpenSpec 和编码准入

未来若进入编码，应新增独立 change，例如 `acquiring-funds-boundary`。该 change 不应默认打开完整收单产品开发，只能按批次打开：

| 批次 | 范围 | 准入条件 |
| --- | --- | --- |
| ACQ-B0 | 设计和 OpenSpec 对齐。 | 只改文档和规格，不改生产代码。 |
| ACQ-B1 | 中立收单引用契约。 | 契约夹具、must-fail、敏感数据红线。 |
| ACQ-B2 | 单一正向收单资金事件。 | route/posting/ledger/余额断言和幂等测试。 |
| ACQ-B3 | 清结算候选和对账来源。 | 清分、对账差错和清算前置门禁测试。 |
| ACQ-B4 | 逆向和争议资金影响。 | 退款、拒付、追偿、负余额和原路径回放测试。 |
| ACQ-B5 | 出款和归档重放。 | 出款结果、重放、差异报告、边界测试和 PMD。 |

每个批次必须明确：

1. 允许写入范围和只读范围。
2. 是否允许新增公共契约、枚举、DTO、表结构和 H2 schema。
3. 外部规则、合规、财务、税务和会计确认状态。
4. 回滚、补偿、人工处理和观测告警。
5. 验证命令和 Done / Conditional Done 口径。

## 10. 架构风险

| 风险 | 影响 | 防护 |
| --- | --- | --- |
| 在业务模式未定时新增收单模块 | 模块无主、契约膨胀、后续回滚成本高。 | 先以逻辑端口和中立引用承接，业务确认后再 ADR。 |
| 外部协议污染核心 DSL | 核心模型被 PSP、卡组织或银行字段绑定。 | Scheme / PSP 差异留在外部适配层，核心只保留资金语义。 |
| 账务主体混乱 | 外部卡、VA、通道账户直接入账导致账本失真。 | 入账前必须解析为内部资金账户、信用账户、预算组或平台账户角色。 |
| 状态混用 | 授权成功、capture、清算、结算和到账被误展示。 | 投影必须包含事实状态、展示状态、操作状态和不可操作原因。 |
| 对账差异直接修账 | 审计断裂，资金风险扩大。 | 差错、审批、凭证、调账、重新对账和核销闭环。 |
| 敏感信息泄露 | PCI、安全、审计风险。 | token/ref/digest/脱敏摘要，禁止原文进入资金底座。 |

## 11. 推荐下一步

研发计划不在本轮打开，只建议设定里程碑：先完成设计评审，再完成 OpenSpec change，再完成契约夹具，再选择单一资金事件试点，最后再评估清结算、对账、逆向和归档重放。
